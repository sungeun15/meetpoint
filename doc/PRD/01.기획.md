# MeetPoint 기획안

## 1\. 프로젝트 개요

### 1.1 프로젝트명

MeetPoint

### 1.2 한 줄 소개

MeetPoint는 친구와 위치를 공유하고 간단한 댓글형 채팅을 주고받으며, 현재 위치 또는 사용자가 선택한 출발 위치를 기준으로 공정한 약속 장소를 추천해주는 웹 서비스이다.

### 1.3 프로젝트 배경

약속 장소를 정할 때 사용자는 보통 메신저, 지도 앱, 장소 검색 서비스를 각각 따로 사용해야 한다. 이 과정은 번거롭고, 특히 서로 다른 위치에 있는 두 사람이 공정한 약속 장소를 빠르게 정하기 어렵다는 문제가 있다.

또한 실제 약속에서는 항상 현재 위치에서 출발하지 않으며, 단순히 중간 지점만 맞춘다고 해서 사용자가 만족할 만한 장소가 추천되는 것도 아니다.

MeetPoint는 이 문제를 해결하기 위해 위치 공유, 출발 위치 선택, 채팅, 중간 지점 계산, 장소 추천을 하나의 흐름으로 연결한 웹 서비스를 목표로 한다.

---

## 2\. 문제 정의

현재 약속을 잡는 과정에는 다음과 같은 불편함이 존재한다.

*   친구와 대화를 나누는 공간과 장소를 검색하는 공간이 분리되어 있다.
*   서로의 위치를 기준으로 공정한 만남 장소를 찾기 어렵다.
*   현재 위치가 실제 약속 당일의 출발 위치와 다를 수 있어 추천 기준이 왜곡될 수 있다.
*   단순히 중심점 근처라는 이유만으로 추천하면 실제로 갈 만한 장소가 적은 지역이 나올 수 있다.
*   카페, 식사, 놀거리처럼 만남 목적이 다른데도 추천 기준이 이를 반영하지 못할 수 있다.
*   장소를 찾더라도 각자에게 얼마나 적절한 위치인지 직관적으로 판단하기 어렵다.
*   여러 앱을 오가며 정보를 조합해야 하므로 사용 흐름이 끊긴다.

MeetPoint는 이러한 불편을 줄이기 위해 약속 준비에 필요한 핵심 기능을 하나의 화면에서 제공한다.

## 3\. 프로젝트 목표

### 3.1 서비스 목표

*   친구와의 약속 장소를 정하는 과정을 단순화한다.
*   지금 만나기와 나중에 만나기 상황을 모두 수용하는 추천 경험을 제공한다.
*   위치 기반으로 공정하면서도 실제로 갈 만한 장소를 추천하는 경험을 제공한다.
*   핵심 사용자 흐름이 안정적으로 동작하는 완성도 있는 MVP를 구현한다.

### 3.2 개발 목표

*   Next.js 16 기반 풀스택 구조로 프론트엔드와 백엔드를 일관되게 구현한다.
*   Supabase와 Kakao API를 활용하여 MVP 개발 속도와 안정성을 확보한다.
*   GitHub, 브랜치 전략, Jira 활용을 통해 팀 협업 과정을 명확히 남긴다.

## 4\. 핵심 가치 제안

MeetPoint가 제공하는 핵심 가치는 다음과 같다.

*   통합성: 채팅, 위치 공유, 추천 기능을 한 서비스 안에서 제공한다.
*   공정성: 한 사람에게만 유리한 장소가 아니라 두 사람 모두에게 적절한 장소를 추천한다.
*   유연성: 현재 위치 기반 번개 약속과 미래 출발 위치 기반 약속을 모두 지원한다.
*   단순성: 최소한의 회원가입과 로그인만 두고, 실시간 처리 없이도 핵심 경험을 빠르게 제공한다.
*   명확성: 추천 기준과 입력 흐름이 명확하여 사용자가 전체 과정을 쉽게 이해할 수 있다.

## 5\. 대상 사용자

### 5.1 주요 사용자

*   친구와 약속 장소를 자주 정하는 대학생
*   위치를 기준으로 중간 지점에서 만나야 하는 사용자
*   복잡한 절차 없이 빠르게 장소를 정하고 싶은 사용자

### 5.2 사용 상황

*   학교 수업 후 친구와 바로 만나기 위한 번개 약속
*   주말이나 며칠 뒤 약속을 위해 미리 출발 위치를 정하고 장소를 고르기
*   서로 다른 지역에서 출발해 카페, 식당, 놀거리 목적에 맞는 장소를 찾기
*   메신저로 대화하면서 바로 장소를 정하고 싶은 상황

## 6\. 핵심 사용자 시나리오

1.  사용자는 서비스를 실행하고 닉네임과 비밀번호로 회원가입하거나 로그인한다.
2.  친구 닉네임을 입력하여 친구를 추가한다.
3.  친구 목록에서 대화할 친구를 선택한다.
4.  댓글형 채팅창에서 메시지를 주고받는다.
5.  사용자는 지금 만나기 또는 나중에 만나기 모드를 선택한다.
6.  지금 만나기 모드에서는 위치 공유 버튼으로 현재 위치를 저장하고, 나중에 만나기 모드에서는 주소 검색, 핀 지정, 저장된 출발 위치 선택 중 하나로 출발 위치를 정한다.
7.  사용자는 카페, 식사, 놀거리 중 만남 목적 카테고리를 선택한다.
8.  추천 버튼을 눌러 두 사람의 출발 기준 위치를 바탕으로 중간 지점 근처 장소를 추천받는다.
9.  추천된 장소 3개와 지도 마커를 확인하고 약속 장소를 결정한다.

이 흐름이 본 프로젝트의 핵심 MVP 사용자 흐름이다.

## 7\. MVP 범위

### 7.1 포함 기능

#### 1\. 회원가입 및 로그인

*   서비스 시작 시 닉네임과 비밀번호로 회원가입하거나 로그인한다.
*   JWT를 httpOnly 쿠키에 저장해 브라우저 새로고침 이후에도 사용자 식별을 유지한다.

#### 2\. 친구 추가 및 목록 조회

*   친구 닉네임을 입력하여 친구를 추가한다.
*   좌측 패널에서 친구 목록을 확인할 수 있다.

#### 3\. 댓글형 채팅

*   친구를 선택하면 채팅창이 표시된다.
*   메시지는 저장형 구조로 관리되며 실시간 소켓은 사용하지 않는다.
*   일정 주기 재조회 방식으로 최신 메시지를 반영한다.

#### 4\. 위치 공유

*   사용자가 버튼을 누를 때만 현재 위치를 저장한다.
*   실시간 추적이 아닌 수동 공유 방식이다.

#### 5. 출발 위치 선택

*   나중에 만나기 모드에서는 현재 위치 대신 출발 위치를 직접 선택할 수 있다.
*   출발 위치는 주소 검색, 지도 핀 지정, 저장된 출발 위치 선택 방식으로 입력한다.

#### 6. 만남 목적 카테고리 선택

*   사용자는 카페, 식사, 놀거리 중 약속 목적을 선택할 수 있다.
*   추천 로직은 선택된 카테고리에 맞지 않는 후보에 패널티를 부여한다.

#### 7. 지도 표시

*   지도에 사용자 위치, 친구 위치, 중심점을 표시한다.
*   위치 상태와 장소 결과를 시각적으로 보여준다.

#### 8. 중간 지점 계산 및 장소 추천

*   두 사용자의 출발 기준 좌표 평균으로 중심점을 계산한다.
*   중심점 주변 장소 후보를 검색한다.
*   거리, 공정성, 카테고리 적합도, 지역 활성도를 반영해 상위 3개 장소를 추천한다.
*   후보 부족 시 검색 반경을 단계적으로 확장한다.

### 7.2 제외 기능

*   실시간 GPS 추적
*   WebSocket 기반 실시간 채팅
*   닉네임 찾기 기능
*   비밀번호 재설정 기능
*   친구 요청 및 수락 시스템
*   추천 이력 고도화 기능
*   일정 캘린더 및 약속 일정 관리 기능
*   복수 저장 위치 관리 및 즐겨찾기 편집 기능

### 7.3 MVP 구현 확정안

본 프로젝트의 MVP 구현 기준은 다음과 같이 확정한다.

#### 1\. 사용자 식별 방식

*   닉네임 + 비밀번호 기반 회원가입과 로그인 방식을 사용한다.
*   users 테이블에는 nickname, nickname\_normalized, password\_hash 를 저장한다.
*   로그인 성공 시 서버가 JWT를 발급하고 httpOnly 쿠키에 저장한다.
*   이후 보호 API의 사용자 식별은 JWT 쿠키 검증 기준으로 처리한다.

#### 2\. 친구 추가 방식

*   친구 추가는 단순 문자열 저장이 아니라 사용자 테이블 기반 연결 방식으로 처리한다.
*   친구 닉네임으로 사용자를 조회한 뒤 관계를 저장한다.
*   friends는 `user_id`와 `friend_id` 구조를 기준으로 설계한다.

#### 3\. 추천 결과 처리 방식

*   MVP 단계에서는 추천 결과를 별도 테이블에 저장하지 않는다.
*   추천 요청 시마다 서버에서 계산 후 바로 반환한다.

#### 4. 추천 입력 기준

*   추천 요청은 지금 만나기 또는 나중에 만나기 모드 기준으로 처리한다.
*   지금 만나기 모드에서는 현재 위치 공유값을 사용한다.
*   나중에 만나기 모드에서는 주소 검색, 핀 지정, 저장된 출발 위치 선택 중 하나로 정한 위치를 사용한다.
*   추천 요청 시 카페, 식사, 놀거리 중 하나의 카테고리를 함께 전달한다.

#### 5. 추천 탐색 방식

*   중심점 기준 반경 1km에서 후보를 먼저 조회한다.
*   후보가 부족하면 2km, 3km 순서로 확장한다.
*   지역 활성도는 각 후보 장소 주변 500m 안의 관련 후보 수를 기준으로 계산한다.
*   MVP 단계에서는 Kakao Local API 검색 결과 수를 지역 활성도 대체 지표로 사용한다.

#### 6. 채팅 동기화 방식

*   메시지 조회는 5초 폴링을 기본으로 한다.
*   친구 선택 직후와 메시지 전송 직후에는 즉시 재조회한다.

#### 7. 외부 API 호출 방식

*   Kakao Local API는 브라우저에서 직접 호출하지 않는다.
*   Next.js 16 서버 Route Handler를 통해 호출한다.
*   추천 계산 로직도 서버에서 함께 처리한다.

## 8\. 기능 상세 기획

### 8.1 친구 추가

*   사용자는 친구 닉네임을 입력해 친구를 추가한다.
*   복잡한 요청 절차 없이 즉시 추가 가능한 흐름을 우선한다.
*   친구 추가 후 목록에 바로 반영되어야 한다.
*   친구 추가는 users 조회 후 friends 관계를 저장하는 방식으로 구현한다.
*   등록되지 않은 닉네임은 추가하지 않고 안내 메시지를 제공한다.

### 8.2 채팅

*   채팅은 댓글형 메시지 저장 방식으로 구현한다.
*   실시간 동기화 대신 5초 주기 재조회 방식을 사용한다.
*   사용자는 간단한 메시지를 입력하고 저장할 수 있어야 한다.
*   친구 선택 시 즉시 메시지를 불러오고, 메시지 전송 직후에도 즉시 재조회한다.

### 8.3 위치 공유 및 출발 위치 선택

*   지금 만나기 모드에서는 위치 공유 버튼 클릭 시 Geolocation API로 좌표를 획득한다.
*   획득한 현재 위치는 데이터베이스에 저장한다.
*   마지막 위치 공유 시각을 함께 표시해 사용자가 최신 상태를 인지할 수 있도록 한다.
*   나중에 만나기 모드에서는 주소 검색, 핀 지정, 저장된 출발 위치 선택으로 출발 위치를 입력한다.
*   저장된 출발 위치 사용은 MVP에서 최근 저장 위치 또는 사전 등록 위치 재사용 수준으로 한정한다.
*   미래 약속용 출발 위치는 추천 요청의 입력값으로 우선 사용한다.

### 8.4 지도 표시

*   지도는 약속 장소 추천의 핵심 시각화 요소이다.
*   지금 만나기 모드에서는 사용자와 친구의 현재 위치를 마커로 표시한다.
*   나중에 만나기 모드에서는 사용자가 선택한 출발 위치와 친구 출발 위치를 마커로 표시한다.
*   추천 기능 실행 시 중심점과 추천 장소도 지도에 함께 표시한다.

### 8.5 추천 기능

*   사용자는 카페, 식사, 놀거리 중 하나의 만남 목적을 선택한다.
*   중심점은 두 출발 좌표의 평균값으로 계산한다.
*   중심점 근처 장소 후보는 Kakao Local API를 통해 조회한다.
*   반경 1km에서 후보를 조회하고, 부족하면 2km와 3km로 확장한다.
*   후보 장소마다 두 사용자와의 거리를 계산한다.
*   평균 이동거리, 거리 편차, 카테고리 패널티, 지역 활성도 패널티를 합산해 점수를 계산한다.
*   같은 카테고리 안에서도 거리, 공정성, 지역 활성도를 비교해 후보 장소 품질을 구분한다.
*   최종적으로 점수가 낮은 상위 3개 장소를 추천한다.

### 8.6 만남 모드

*   사용자는 지금 만나기 또는 나중에 만나기 모드를 선택할 수 있어야 한다.
*   지금 만나기 모드는 현재 위치 공유 기반 추천에 적합하다.
*   나중에 만나기 모드는 미래 출발 위치를 지정해 추천하는 흐름에 적합하다.

## 9\. 화면 구성 기획

### 9.1 시작 화면

## 10\. 정보 구조 및 데이터 설계 방향

### 10.1 users

*   사용자 식별 정보 관리
*   닉네임, 정규화 닉네임, 비밀번호 해시, 위치 좌표, 위치 갱신 시간 저장
*   회원가입과 로그인 처리의 기준 테이블로 사용한다.
*   초기 사용자 상태를 위해 위치 관련 컬럼은 비어 있을 수 있다.
*   현재 위치는 지금 만나기 모드의 추천 입력 기준으로 사용한다.

### 10.2 friends

*   사용자와 친구 간 연결 관계 저장
*   `user_id`와 `friend_id` 기반 관계 테이블로 관리한다.
*   동일 친구 중복 추가를 방지하는 방향으로 설계한다.

### 10.3 messages

*   송신자, 수신자, 메시지 내용, 생성 시간 저장
*   댓글형 채팅 흐름에 맞춰 생성 시간 기준으로 조회한다.

### 10.4 recommendations

*   추천 결과 저장이 필요할 경우를 위한 확장 테이블
*   MVP 단계에서는 사용하지 않으며, 추천 결과는 요청 시 계산 후 반환한다.

### 10.5 추천 요청 입력 기준

*   추천 계산 입력에는 만남 모드, 사용자 출발 좌표, 친구 출발 좌표, 카테고리가 포함된다.
*   나중에 만나기 모드의 출발 위치는 주소 검색, 핀 지정, 저장된 출발 위치 선택 중 하나로 결정한다.
*   향후 저장 위치 또는 약속 테이블로 확장할 수 있는 구조를 고려한다.

### 10.6 데이터 설계 확정 기준

*   사용자 식별은 JWT를 저장한 httpOnly 쿠키 기준으로 처리한다.
*   nickname은 nickname\_normalized 기준으로 중복을 허용하지 않는다.
*   password는 평문 저장이 아니라 해시 저장을 원칙으로 한다.
*   users의 위치 관련 컬럼은 초기 상태에서 null을 허용한다.
*   friends는 `user_id`와 `friend_id`의 조합이 중복되지 않도록 설계한다.

## 11\. 추천 알고리즘 개요

### 11.1 추천 입력 기준

추천 계산은 아래 입력을 기준으로 수행한다.

*   모드: 지금 만나기 / 나중에 만나기
*   사용자 A 출발 좌표
*   사용자 B 출발 좌표
*   만남 목적 카테고리

### 11.2 중심점 계산

중심 위도와 중심 경도는 다음 식으로 계산한다.

```
중심 위도 = (A 위도 + B 위도) / 2
중심 경도 = (A 경도 + B 경도) / 2
```

### 11.3 후보 검색 반경 확장

후보 검색은 아래 순서로 진행한다.

1.  중심점 기준 1km 반경 검색
2.  후보 부족 시 2km로 확장
3.  그래도 부족 시 3km로 확장

### 11.4 거리 계산

*   사용자 A와 장소 간 거리 계산
*   사용자 B와 장소 간 거리 계산
*   거리 계산에는 Haversine 공식을 사용한다.

### 11.5 카테고리 패널티

*   사용자가 선택한 목적과 후보 장소 카테고리를 비교한다.
*   목적과 잘 맞는 후보는 패널티를 낮게 두고, 관련성이 낮은 후보는 패널티를 높인다.
*   MVP 단계에서는 패널티를 거리 점수처럼 합산 가능한 수치로 단순화한다.

예시는 다음과 같다.

*   카페 선택 + 카페 후보: 0점
*   카페 선택 + 베이커리 또는 디저트 후보: 200점
*   카페 선택 + 식당 후보: 800점
*   식사 선택 + 한식, 중식, 일식, 양식 후보: 0점
*   식사 선택 + 카페 후보: 600점
*   놀거리 선택 + 영화관, 노래방, 게임, 문화시설 후보: 0점
*   놀거리 선택 + 카페 후보: 400점
*   전혀 관련 없는 후보: 1000점

### 11.6 지역 활성도 패널티

*   후보 장소 주변 500m 안에 관련 장소 후보가 얼마나 있는지 계산한다.
*   주변 후보가 많을수록 패널티를 낮게 두고, 적을수록 패널티를 높인다.
*   MVP 단계에서는 중심점 주변 검색 결과 안에서 각 후보의 주변 후보 수를 비교하는 방식으로 단순 계산한다.

패널티 기준 예시는 다음과 같다.

*   주변 500m 내 후보 수 10개 이상: 0점
*   주변 500m 내 후보 수 6~9개: 200점
*   주변 500m 내 후보 수 3~5개: 500점
*   주변 500m 내 후보 수 1~2개: 800점
*   주변 500m 내 후보 수 0개: 1200점

### 11.7 점수 계산

추천 점수는 평균 이동거리, 거리 편차, 카테고리 적합도, 지역 활성도를 함께 반영한다.

```
score = 평균 이동거리 + 거리 편차 + 카테고리 패널티 + 지역 활성도 패널티
```

세부 계산식은 다음과 같다.

```
평균 이동거리 = (A 거리 + B 거리) / 2
거리 편차 = |A 거리 - B 거리|
카테고리 패널티 = 선택한 목적과 장소 카테고리가 안 맞을수록 증가
지역 활성도 패널티 = 주변에 갈 만한 장소가 적을수록 증가
```

점수가 낮을수록 두 사람 모두에게 더 적절한 장소로 판단한다.

## 12\. 시스템 구성 방향

### 12.1 전체 구조

*   사용자 브라우저에서 UI와 지도 화면을 제공한다.
*   Next.js 16 서버에서 데이터 처리와 API 연동을 담당한다.
*   Supabase는 사용자, 친구, 메시지, 위치 정보를 저장한다.
*   Kakao Map API는 지도 렌더링과 마커 표시를 담당한다.
*   Kakao Local API는 Next.js 16 Route Handler를 통해 서버에서 호출한다.
*   추천 계산 로직은 서버에서 수행하고 결과만 클라이언트에 반환한다.
*   주소 검색과 장소 추천 후보 조회는 모두 서버에서 Kakao Local API를 통해 처리한다.

### 12.2 처리 흐름

1.  사용자가 만남 모드와 카테고리를 선택한다.
2.  서버는 쿠키 기준으로 현재 사용자를 식별한다.
3.  지금 만나기 모드이면 현재 위치를, 나중에 만나기 모드이면 선택한 출발 위치를 추천 입력값으로 사용한다.
4.  중심점을 계산한다.
5.  Route Handler 내부에서 Kakao Local API로 후보 장소를 반경 단계별로 조회한다.
6.  각 후보의 거리, 카테고리 패널티, 지역 활성도 패널티를 계산한다.
7.  상위 결과 3개를 정렬해 반환한다.
8.  프론트엔드에서 지도와 카드 UI로 결과를 표시한다.

## 18\. 예상 질문 대응 포인트

### Q. 실시간 위치 추적 서비스인가요?

아니다. 버튼 클릭 시에만 위치를 저장하는 수동 공유 방식이다.

### Q. 꼭 현재 위치로만 추천하나요?

아니다. 지금 만나기 모드에서는 현재 위치를 사용하고, 나중에 만나기 모드에서는 사용자가 직접 출발 위치를 검색하거나 핀으로 지정하고, 필요하면 저장된 출발 위치를 선택해 추천을 받을 수 있다.

### Q. 단순히 API만 사용한 프로젝트인가요?

아니다. 위치 저장, 출발 위치 선택, 채팅 흐름, 중심점 계산, 반경 확장, 카테고리 적합도, 지역 활성도 기반 추천 점수화 로직을 직접 설계하고 구현하는 것이 핵심이다.

### Q. 왜 실시간 채팅을 구현하지 않았나요?

과제 범위와 안정성을 고려해 MVP 단계에서는 댓글형 저장 방식으로 단순화했다.

## 20\. 결론

MeetPoint는 위치 공유, 출발 위치 선택, 댓글형 채팅, 중간 지점 계산, 장소 추천을 통합한 웹 서비스이다. 본 프로젝트는 약속 장소를 정하는 과정을 단순화하고, 현재 약속과 미래 약속 모두에 대응하는 공정 추천이라는 명확한 가치를 제시한다. 또한 오픈소스 기술과 협업 도구를 적극 활용하여 기술 구현과 팀 프로젝트 운영 역량을 함께 보여주는 과제 결과물을 목표로 한다.
