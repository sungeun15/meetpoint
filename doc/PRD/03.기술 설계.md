# MeetPoint 기술 설계

## 1\. 문서 목적

이 문서는 MeetPoint의 기획 문서와 구조 설계 문서를 실제 구현 단위로 연결하기 위한 기술 설계 문서이다.

03번 문서의 목적은 다음과 같다.

*   현재 Team A 소스 기준으로 어떤 페이지, 컴포넌트, 상태 훅이 실제로 사용되는지 정리한다.
*   현재 UI-only 구현 범위와 후속 Route Handler, 인증, DB, 추천 엔진 통합 범위를 분리한다.
*   Kakao Maps JS SDK, Daum Postcode, 로컬 상태 기반 추천 UI 흐름을 어떤 구조로 유지할지 고정한다.
*   구현 순서와 테스트 기준을 현재 UI 단계와 후속 통합 단계로 나누어 해석 차이를 줄인다.

---

## 2\. 기술 설계 범위

본 문서의 범위는 현재 Team A UI 구현과 그 이후 통합 준비 설계를 함께 다루는 기준으로 한정한다.

포함 범위:

*   Next.js 16 App Router 기반 페이지 구성
*   랜딩, 인증, friends 허브, chat 상세, 추천 결과 화면 구성
*   friends-screen, chat-screen, use-chat-screen-state, use-recommendation-flow-state 기반 로컬 상태 처리
*   Kakao Maps JS SDK 와 Daum Postcode 기반 주소 검색, 핀 지정, 지도 미리보기 UI
*   지금 만나기 / 나중에 만나기 모드 분기 처리
*   저장 위치 레이어, 추천 결과 카드, 지도 패널 UI 흐름
*   후속 Route Handler, JWT, Supabase, Kakao Local API 통합 설계 초안

제외 범위:

*   현재 단계에서의 실제 JWT + httpOnly 쿠키 발급 및 보호 라우트 적용
*   현재 단계에서의 실제 Supabase users, friends, messages 저장
*   현재 단계에서의 5초 폴링 기반 채팅 동기화
*   WebSocket 기반 실시간 채팅
*   실시간 GPS 추적
*   닉네임 찾기 기능
*   비밀번호 재설정 기능
*   추천 이력 저장 기능
*   추천 결과 통계 및 분석 기능

## 3\. 구현 기준 요약

기술 설계의 기본 원칙은 다음과 같다.

*   페이지 라우팅은 App Router 기준으로 구현한다.
*   현재 화면 상태는 friends-screen 과 chat-screen 하위 훅에서 로컬 상태로 관리한다.
*   브라우저 SDK를 쓰는 지도, 주소 검색, 핀 지정 UI는 클라이언트 컴포넌트 안에서 닫힌 흐름으로 유지한다.
*   현재 구현에서는 목업 데이터와 UI 피드백을 우선 연결하고, 저장과 인증은 후속 통합 대상으로 남긴다.
*   후속 보호 데이터 접근은 Route Handler를 통해 처리한다.
*   후속 브라우저 데이터 저장은 Supabase 직접 접근이 아니라 Route Handler 경유 기준으로 통일한다.
*   후속 인증 식별은 meetpoint\_auth JWT 쿠키 기준으로 통일한다.
*   후속 추천 계산은 서버에서 수행하고 결과만 클라이언트에 반환한다.

## 5\. 페이지 설계

### 5.1 페이지 라우팅

MVP 기준 페이지 라우팅은 다음과 같이 설계한다.

| 경로      | 역할                | 구현 방식                                    |
| --------- | ------------------- | -------------------------------------------- |
| /         | 랜딩 페이지         | 서버 또는 정적 페이지 + 랜딩 히어로 컴포넌트 |
| /login    | 로그인 페이지       | 인증 화면 클라이언트 컴포넌트 렌더링         |
| /signup   | 회원가입 페이지     | 인증 화면 클라이언트 컴포넌트 렌더링         |
| /friends  | friends 허브 페이지 | friends 허브 화면 렌더링                     |
| /chat     | chat 상세 페이지    | friend searchParams 기반 chat 화면 렌더링    |
| /features | 기능 소개 페이지    | public 소개 콘텐츠 렌더링                    |
| /about    | 서비스 소개 페이지  | public 소개 콘텐츠 렌더링                    |

### 5.2 랜딩 및 인증 페이지 구현 기준

파일:

*   app/page.tsx
*   app/login/page.tsx
*   app/signup/page.tsx
*   app/components/home-hero.tsx
*   app/components/auth-screen.tsx

동작 기준:

1.  app/page.tsx 는 랜딩 히어로와 public CTA를 렌더링한다.
2.  랜딩 CTA는 현재 preview toggle 상태에 따라 /login 또는 /friends 로 분기된다.
3.  app/login/page.tsx 와 app/signup/page.tsx 는 auth-screen 을 모드별로 재사용한다.
4.  현재 구현에서는 인증 입력 UI를 우선 제공하고, 실제 POST /api/auth/* 호출과 /friends 이동은 후속 인증 연동 단계에서 연결한다.

### 5.3 friends 허브 페이지 구현 기준

파일:

*   app/components/friends-screen.tsx
*   app/components/friends/friends-sidebar.tsx

동작 기준:

1.  현재 friends-screen 은 로컬 친구 목록, 친구 검색, 친구 추가 입력 상태를 관리한다.
2.  친구 추가는 로컬 배열을 갱신하고 선택 친구 미리보기와 안내 문구를 함께 갱신한다.
3.  좌측 패널 검색은 기존 목록 필터링에만 사용한다.
4.  친구 선택 액션은 /chat?friend={id} 이동으로 연결한다.
5.  JWT 보호 라우트 검증은 후속 인증 연동 단계에서 적용한다.

### 5.4 chat 상세 페이지 구현 기준

파일:

*   app/chat/page.tsx
*   app/components/chat-screen.tsx
*   app/components/chat/use-chat-screen-state.ts
*   app/components/chat/use-recommendation-flow-state.ts

동작 기준:

1.  app/chat/page.tsx 는 searchParams.friend 값을 읽어 requestedFriendId 로 전달한다.
2.  chat-screen 은 좌측 친구 사이드바, 상단 상세 패널, 하단 추천 패널, 저장 위치 레이어를 함께 렌더링한다.
3.  use-chat-screen-state 는 선택 친구, 메시지, 위치 상태를 묶고 추천 관련 상태는 use-recommendation-flow-state 로 위임한다.
4.  추천 결과는 chat 페이지 내부 로컬 상태와 카드 빌더 함수로 확장한다.
5.  실제 메시지 저장, 위치 저장, 추천 API 연동은 후속 단계에서 같은 구조 위에 연결한다.

## 7\. 공통 타입 설계

현재 UI 구현에서는 app/components/friends/types.ts 와 app/components/chat/types.ts 가 실제 사용 타입의 기준이다. 아래 타입 묶음은 후속 서버·API 통합 단계에서 types/domain.ts 와 types/dto.ts 로 끌어올릴 때의 공통 타입 초안으로 본다.

types/domain.ts 와 types/dto.ts 에서 최소한 다음 타입을 정의한다.

```
type UserSummary = {
    id: string;
    nickname: string;
    lat: number | null;
    lng: number | null;
    locationUpdatedAt: string | null;
};

type FriendSummary = UserSummary & {
    relationId?: string;
};

type MessageItem = {
    id: string;
    senderId: string;
    receiverId: string;
    content: string;
    createdAt: string;
};

type RecommendationMode = "now" | "later";

type RecommendationCategory = "cafe" | "meal" | "fun";

type Coordinate = {
    lat: number;
    lng: number;
};

type DeparturePoint = Coordinate & {
    label: string;
    source: "search" | "pin" | "saved";
};

type DepartureInputState = {
    selected: DeparturePoint | null;
    query: string;
};

type DepartureSearchItem = DeparturePoint;

type DepartureSearchState = {
    loading: boolean;
    query: string;
    results: DepartureSearchItem[];
};

type SavedDepartureLocation = {
    id: string;
    label: string;
    lat: number;
    lng: number;
    locationKind: "recent" | "preset";
    lastUsedAt: string;
    createdAt: string;
    updatedAt: string;
};

type RecommendationPlace = {
    name: string;
    category: string;
    lat: number;
    lng: number;
    distanceA: number;
    distanceB: number;
    averageDistance: number;
    distanceGap: number;
    categoryPenalty: number;
    vitalityPenalty: number;
    score: number;
};

type RecommendationResult = {
    midpoint: { lat: number; lng: number };
    summary: { mode: RecommendationMode; category: RecommendationCategory; radiusUsed: number };
    places: RecommendationPlace[];
};

type MapViewState = {
    myLocation: { lat: number; lng: number } | null;
    friendLocation: { lat: number; lng: number } | null;
    midpoint: { lat: number; lng: number } | null;
    placeMarkers: RecommendationPlace[];
};

type LoadingFlags = {
    friends: boolean;
    messages: boolean;
    recommendation: boolean;
    location: boolean;
    savedDepartures: boolean;
    departureSearch: boolean;
};

type ErrorState = {
    global: string | null;
    friendAdd: string | null;
    message: string | null;
    departure: string | null;
    recommendation: string | null;
};
```

API 응답 타입은 다음 형식으로 통일한다.

```
type ApiSuccess<T> = { ok: true; data: T };
type ApiError = { ok: false; error: { code: string; message: string } };
type ApiResponse<T> = ApiSuccess<T> | ApiError;
```

## 8\. 후속 Route Handler 설계

현재 Team A 소스에는 app/api/* 가 아직 없다. 아래 내용은 현재 UI 구조를 유지한 채 인증, 저장, 추천 계산을 연결할 때 적용할 후속 기술 설계 초안이다.

### 8.1 구현 파일 목록

### 8.2 공통 처리 순서

보호 API의 공통 순서는 다음과 같다.

1.  요청 메서드 확인
2.  JWT 쿠키 검증
3.  입력값 검증
4.  관계 및 권한 검증
5.  repository 또는 service 호출
6.  성공 응답 또는 오류 응답 반환

공통 구현 유틸:

*   readJsonBody(request)
*   requireSession(request)
*   parseQuery(request)
*   ok(data)
*   fail(status, code, message)

## 9\. 후속 JWT 인증 기술 설계

현재 랜딩 화면의 CTA 분기는 home-hero 내부 preview toggle 로만 제어한다. 아래 JWT 설계는 실제 인증 연동과 보호 라우트 적용 단계에서 사용할 후속 기술 기준이다.

파일:

*   lib/auth/session.ts

필수 함수:

*   signAuthToken(payload)
*   verifyAuthToken(token)
*   setAuthCookie(response, payload)
*   clearAuthCookie(response)
*   getAuthFromCookies()
*   requireAuthOrThrow()

JWT payload 기준:

```
type AuthPayload = {
    userId: string;
    nickname: string;
    iat: number;
    exp: number;
};
```

구현 기준:

*   쿠키 이름은 meetpoint\_auth 로 고정한다.
*   JWT\_SECRET 기반 JWT 서명 또는 동등한 안전한 서명 방식을 사용한다.
*   쿠키 속성은 httpOnly, sameSite=lax, path=/ 를 기본으로 하고 운영 환경에서만 secure=true 로 설정한다.
*   쿠키 만료 시간은 7일 기준으로 고정하며, exp 와 쿠키 maxAge 를 동일하게 유지한다.
*   exp 만료 검증 실패 시 쿠키를 즉시 삭제한다.
*   브라우저에서는 auth payload를 직접 해석하지 않는다.
*   페이지 보호와 API 보호는 같은 검증 함수 하나를 공유한다.
*   currentUserId 는 검증된 JWT에서만 주입하며 요청 본문이나 query 에서 사용자 ID를 받지 않는다.

### 9.1 인증 함수별 계약

| 함수               | 입력                      | 출력                  | 실패 조건                               |
| ------------------ | ------------------------- | --------------------- | --------------------------------------- |
| signAuthToken      | AuthPayload               | string                | JWT\_SECRET 누락, payload 필수값 누락   |
| verifyAuthToken    | token string              | AuthPayload 또는 null | 서명 불일치, 만료, 형식 오류            |
| setAuthCookie      | NextResponse, AuthPayload | NextResponse          | response 객체 없음, payload 오류        |
| clearAuthCookie    | NextResponse              | NextResponse          | response 객체 없음                      |
| getAuthFromCookies | 없음                      | AuthPayload 또는 null | 쿠키 없음, 토큰 검증 실패               |
| requireAuthOrThrow | 없음                      | AuthPayload           | JWT 없음 또는 만료 시 UNAUTHORIZED 예외 |

### 9.2 인증 함수 예시

#### signAuthToken 예시

입력 예시:

```
{
    userId: "uuid",
    nickname: "민수",
    iat: 1770000000,
    exp: 1770604800
}
```

출력 예시:

```
"signed.jwt.token"
```

실패 조건 예시:

*   JWT\_SECRET 이 없으면 서버 시작 또는 호출 시점에 INTERNAL\_ERROR 로 처리한다.
*   userId 또는 exp 같은 필수 필드가 비어 있으면 토큰 발급을 중단한다.

#### verifyAuthToken 예시

입력 예시:

```
"signed.jwt.token"
```

성공 출력 예시:

```
{
    userId: "uuid",
    nickname: "민수",
    iat: 1770000000,
    exp: 1770604800
}
```

실패 조건 예시:

*   서명이 다르면 null 또는 UNAUTHORIZED 처리 기준으로 반환한다.
*   exp 가 현재 시각보다 이전이면 쿠키 삭제 대상이다.

## 10\. 후속 입력값 검증 설계

현재 UI 단계에서는 빈 입력, 저장 제목 누락, 추천 가능 여부처럼 화면 수준 검증만 로컬 상태에서 처리한다. 아래 검증 유틸은 Route Handler 와 공통 도메인 검증으로 확장할 때 적용할 기준이다.

파일:

*   lib/utils/nickname.ts
*   lib/utils/validation.ts

필수 함수:

*   normalizeNickname(value)
*   validateNickname(value)
*   validatePassword(value)
*   validateFriendNickname(value, currentNickname)
*   validateMessageContent(value)
*   validateCoordinates(lat, lng)
*   validateUuid(value)
*   validateMessageQuery(after, limit)
*   validateRecommendationMode(value)
*   validateRecommendationCategory(value)
*   validateSearchQuery(value)
*   validateLocationKind(value)
*   validateDeparturePoint(value)

구현 기준:

*   normalizeNickname은 trim, 연속 공백 축소, 영문 소문자 정규화를 수행한다.
*   validatePassword는 8자 이상 20자 이하와 허용 문자 기준을 검증한다.
*   validateMessageQuery는 기본 limit 50, 최대 100을 강제한다.
*   validateUuid는 friendId, departureLocationId 같은 UUID 입력 검증에 재사용한다.
*   validateRecommendationMode는 now, later 중 하나만 허용한다.
*   validateRecommendationCategory는 cafe, meal, fun 중 하나만 허용한다.
*   validateSearchQuery는 2자 이상 문자열만 허용한다.
*   validateLocationKind는 recent, preset 중 하나만 허용한다.
*   invalid input은 400 INVALID\_INPUT으로 통일한다.

### 10.1 검증 함수별 계약

| 함수                           | 입력                            | 출력                   | 실패 조건                          |
| ------------------------------ | ------------------------------- | ---------------------- | ---------------------------------- |
| normalizeNickname              | raw string                      | normalized string      | string 아님, 빈 값                 |
| validateNickname               | nickname string                 | 검증 통과 문자열       | 길이 제한 위반, 허용 문자 위반     |
| validatePassword               | password string                 | 검증 통과 문자열       | 길이 제한 위반, 허용 문자 위반     |
| validateFriendNickname         | friendNickname, currentNickname | 검증 통과 문자열       | 자기 자신과 동일, 형식 오류        |
| validateMessageContent         | content string                  | trim 된 content        | 빈 문자열, 500자 초과              |
| validateCoordinates            | lat, lng                        | { lat, lng }           | 범위 초과, 숫자 아님               |
| validateUuid                   | raw string                      | uuid string            | UUID 형식 불일치                   |
| validateMessageQuery           | after, limit                    | { after, limit }       | ISO datetime 아님, limit 초과      |
| validateRecommendationMode     | raw string                      | RecommendationMode     | 허용 값 아님                       |
| validateRecommendationCategory | raw string                      | RecommendationCategory | 허용 값 아님                       |
| validateSearchQuery            | raw string                      | string                 | 2자 미만, 빈 값                    |
| validateLocationKind           | raw string                      | recent 또는 preset     | 허용 값 아님                       |
| validateDeparturePoint         | raw object                      | DeparturePoint         | 좌표 누락, label 누락, source 오류 |

## 11\. 후속 Supabase 접근 설계

현재 Team A 소스는 friends, messages, saved departures 를 로컬 데이터와 상태 훅으로 유지한다. 아래 Supabase 접근 설계는 실제 저장 계층을 붙일 때 적용할 후속 구조이다.

파일:

*   lib/supabase/server.ts
*   lib/repositories/users.ts
*   lib/repositories/friends.ts
*   lib/repositories/messages.ts
*   lib/repositories/departure-locations.ts

구현 기준:

*   MVP는 Supabase Auth를 사용하지 않으므로 Route Handler 내부 서버 접근은 SUPABASE\_SERVICE\_ROLE\_KEY 기반으로 수행한다.
*   service role client 생성은 lib/supabase/server.ts 한 곳으로 제한한다.
*   repository 함수는 currentUserId 또는 명시적 대상 ID를 인자로 받아 조회 범위를 고정한다.
*   브라우저는 앱 데이터에 대해 Supabase 직접 read/write를 하지 않고, 모든 데이터 요청은 Route Handler를 경유한다.
*   DB 접근 로직은 Route Handler 안에 직접 쓰지 않고 repository 함수로 분리한다.
*   사용자 생성, 양방향 친구 관계 복구 같은 관리성 작업 외에는 범위가 넓은 update/delete 를 금지한다.

### 11.3 구현 제약, 관계, 인덱스 기준

실제 테이블 생성 시 반영해야 하는 최소 규칙은 다음과 같다.

| 테이블               | 필수 제약                                                                                                                            | 권장 인덱스                                                                                | 구현 메모                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| users                | unique(nickname\_normalized)                                                                                                         | index(location\_updated\_at), index(nickname\_normalized)                                  | nickname은 표시용, nickname\_normalized는 비교용으로 분리  |
| friends              | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id, unique(user\_id, friend\_id), check(user\_id \<> friend\_id) | index(user\_id), index(friend\_id)                                                         | 친구 추가 시 양방향 row 2건을 함께 upsert                  |
| messages             | foreign key(sender\_id) -> users.id, foreign key(receiver\_id) -> users.id                                                           | index(sender\_id, receiver\_id, created\_at), index(receiver\_id, sender\_id, created\_at) | 조회는 두 사용자 간 메시지를 created\_at 오름차순으로 반환 |
| departure\_locations | foreign key(user\_id) -> users.id, check(location\_kind in ('recent', 'preset')), check(label not blank)                             | index(user\_id, last\_used\_at desc), index(user\_id, location\_kind)                      | users 현재 위치와 분리해 저장된 출발 위치를 관리           |
| recommendations      | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id                                                               | index(user\_id, friend\_id, created\_at desc)                                              | MVP 1차에서는 생성하지 않고 후속 확장 시 추가              |

### 11.4 트랜잭션 및 동시성 기준

*   users 생성은 nickname\_normalized unique 제약을 전제로 구현하고, 동시 생성 충돌 시 기존 row 재조회로 수습한다.
*   친구 추가는 양방향 row 2건을 하나의 트랜잭션 또는 동등한 원자적 upsert 흐름으로 처리한다.
*   한쪽 관계만 남은 비정상 상태를 발견하면 누락된 반대 방향 row를 같은 요청 안에서 복구한다.
*   메시지 저장은 단건 insert 로 처리하되, 조회 정렬은 created\_at asc, id asc 로 고정한다.
*   나중에 만나기 모드의 출발 위치는 추천 요청 payload와 저장된 출발 위치 선택값을 함께 고려한다.
*   저장된 출발 위치 재사용은 departure\_locations 테이블을 기준으로 처리하고, users 의 현재 위치 공유값과 혼용하지 않는다.

## 12\. 후속 기능별 상세 처리 설계

현재 화면에서는 회원가입, 친구 추가, 메시지 전송, 위치 공유, 추천 결과 표시를 모두 UI와 로컬 상태로 우선 표현한다. 아래 상세 처리 설계는 같은 사용자 흐름을 서버 저장과 인증으로 치환할 때의 후속 처리 순서이다.

### 12.1 회원가입 및 로그인

Route:

*   POST /api/auth/signup
*   POST /api/auth/login

처리 순서:

1.  nickname과 password 입력값 검증
2.  회원가입 시 nickname\_normalized 기준 중복 검사
3.  회원가입 성공 시 password hash 저장
4.  회원가입 성공 시 JWT 쿠키 발급
5.  로그인 시 password hash 비교 검증
6.  로그인 성공 시 JWT 쿠키 발급
7.  user summary 반환

예외 기준:

*   닉네임 형식 오류: 400 INVALID\_INPUT
*   DB 생성 실패: 500 INTERNAL\_ERROR

```
{ "nickname": "민수" }
```

실패 예시:

*   nickname 검증 실패 시 400 INVALID\_INPUT
*   생성과 재조회 모두 실패하면 500 INTERNAL\_ERROR

Route:

*   GET /api/friends

처리 순서:

1.  세션 검증
2.  현재 사용자 기준 친구 관계 조회
3.  상대 사용자 정보 join 또는 후속 조회
4.  닉네임 오름차순 또는 생성 순 기준 반환

응답 예시:

```
{ "ok": true, "data": { "friends": [ { "id": "uuid-f", "nickname": "지은", "lat": 37.5, "lng": 127.0, "locationUpdatedAt": "2026-05-03T10:00:00.000Z" } ] } }
```

실패 예시:

*   세션이 없거나 만료되면 401 UNAUTHORIZED
*   친구 목록 조회 쿼리 실패 시 500 INTERNAL\_ERROR

### 12.4 메시지 저장

Route:

*   POST /api/messages

처리 순서:

1.  세션 검증
2.  friendId, content 검증
3.  친구 관계 확인
4.  messages row 저장
5.  저장된 메시지 반환

예외 기준:

*   친구 관계 없음: 403 FORBIDDEN\_RELATION

요청, 응답, 실패 예시:

요청 예시:

```
{ "friendId": "uuid-f", "content": "언제 만날까?" }
```

성공 응답 예시:

```
{ "ok": true, "data": { "message": { "id": "uuid-m", "senderId": "uuid-a", "receiverId": "uuid-f", "content": "언제 만날까?", "createdAt": "2026-05-03T10:01:00.000Z" } } }
```

실패 예시:

*   content 가 비어 있으면 400 INVALID\_INPUT
*   친구 관계가 없으면 403 FORBIDDEN\_RELATION

### 12.5 메시지 조회

Route:

*   GET /api/messages

쿼리 기준:

*   friendId: 필수
*   after: 선택
*   limit: 선택, 기본 50

처리 순서:

1.  세션 검증
2.  friendId, after, limit 검증
3.  친구 관계 확인
4.  기본 정렬 키는 createdAt asc, id asc 로 고정한다.
5.  after가 없으면 최신 limit 개를 desc 로 조회한 뒤 createdAt asc, id asc 순으로 다시 정렬한다.
6.  after가 있으면 after 이후 메시지만 조회한다.
7.  클라이언트 병합 기준으로 lastMessageCreatedAt 과 pollingIntervalSec = 5 를 함께 반환한다.

구현 메모:

*   MVP 1차에서는 query 를 단순화하기 위해 after 단일값을 유지한다.
*   같은 시각 메시지 경계에서 중복 표시가 생기지 않도록 클라이언트는 message.id 기준으로 병합한다.
*   대량 히스토리 페이지네이션은 MVP 범위에서 제외한다.

응답 예시:

```
{ "ok": true, "data": { "messages": [ { "id": "uuid-m", "senderId": "uuid-a", "receiverId": "uuid-f", "content": "언제 만날까?", "createdAt": "2026-05-03T10:01:00.000Z" } ], "lastMessageCreatedAt": "2026-05-03T10:01:00.000Z", "pollingIntervalSec": 5 } }
```

실패 예시:

*   friendId 가 UUID 형식이 아니면 400 INVALID\_INPUT
*   권한 없는 친구 대상이면 403 FORBIDDEN\_RELATION

### 12.6 위치 저장

Route:

*   POST /api/location

처리 순서:

1.  세션 검증
2.  lat, lng 검증
3.  users 테이블의 lat, lng, location\_updated\_at 갱신
4.  location summary 반환

요청, 응답, 실패 예시:

요청 예시:

```
{ "lat": 37.5665, "lng": 126.9780 }
```

성공 응답 예시:

```
{ "ok": true, "data": { "location": { "lat": 37.5665, "lng": 126.9780, "locationUpdatedAt": "2026-05-03T10:05:00.000Z" } } }
```

실패 예시:

*   좌표가 범위를 벗어나면 400 INVALID\_INPUT
*   DB 갱신 실패 시 500 INTERNAL\_ERROR

### 12.7 추천 결과 조회

Route:

*   POST /api/recommendations

처리 순서:

1.  세션 검증
2.  friendId, mode, category 검증
3.  친구 관계 확인
4.  mode 가 now 이면 현재 사용자와 친구의 마지막 위치 조회, mode 가 later 이면 departure 와 friendDeparture 검증
5.  입력 기준 위치 누락 여부 확인
6.  중심점 계산
7.  반경 1km, 2km, 3km 순서로 Kakao Local API 후보 조회
8.  후보가 없고 개발 환경 fallback이 켜져 있으면 fixture 후보 조회
9.  후보가 최종적으로 0건이면 200 정상 응답으로 빈 places 배열을 반환한다.
10.  후보가 있으면 거리 계산, 카테고리 패널티, 활성도 패널티, score 계산
11.  정렬 후 상위 3개와 summary 반환

예외 기준:

*   지금 만나기 모드 위치 미공유: 409 LOCATION\_REQUIRED
*   나중에 만나기 모드 출발 위치 누락: 409 DEPARTURE\_REQUIRED
*   Kakao API 실패: fallback 이 없거나 운영 환경이면 502 KAKAO\_API\_FAILED

응답 예시:

```
{ "ok": true, "data": { "midpoint": { "lat": 37.55, "lng": 127.01 }, "summary": { "mode": "later", "category": "cafe", "radiusUsed": 2000 }, "places": [ { "name": "중간카페", "category": "cafe", "lat": 37.551, "lng": 127.012, "distanceA": 420, "distanceB": 460, "averageDistance": 440, "distanceGap": 40, "categoryPenalty": 0, "vitalityPenalty": 200, "score": 680 } ] } }
```

빈 결과 예시:

```
{ "ok": true, "data": { "midpoint": { "lat": 37.55, "lng": 127.01 }, "summary": { "mode": "now", "category": "meal", "radiusUsed": 3000 }, "places": [] } }
```

실패 예시:

*   지금 만나기 모드에서 위치 정보가 부족하면 409 LOCATION\_REQUIRED
*   나중에 만나기 모드에서 출발 위치가 부족하면 409 DEPARTURE\_REQUIRED
*   운영 환경에서 Kakao API 가 실패하면 502 KAKAO\_API\_FAILED

## 13\. 후속 추천 엔진 설계

현재 추천 UI는 app/components/chat/data.ts 의 buildRecommendationCards, buildRecommendationSummary 와 use-recommendation-flow-state 를 통해 결과 패널을 갱신한다. 아래 엔진 설계는 실제 추천 계산을 서버 로직으로 옮길 때의 후속 기준이다.

파일:

*   lib/services/recommendation-service.ts
*   lib/utils/distance.ts
*   lib/kakao/local.ts
*   fixtures/places.ts

필수 함수:

*   calculateMidpoint
*   haversineDistance
*   fetchPlaceCandidatesByRadius
*   resolveCandidateRadius
*   computeCategoryPenalty
*   computeVitalityPenalty
*   scorePlaceCandidate
*   sortRecommendations
*   getRecommendations

추천 계산 순서:

1.  midpoint 계산
2.  mode 기준 출발 위치 확정
3.  Kakao Local API 후보 조회
4.  반경 확장 필요 여부 판단
5.  반경별 후보 병합 또는 최종 후보 선택
6.  각 후보에 대해 distanceA, distanceB 계산
7.  averageDistance 계산
8.  distanceGap 계산
9.  categoryPenalty 계산
10.  vitalityPenalty 계산
11.  score = averageDistance + distanceGap + categoryPenalty + vitalityPenalty
12.  score, distanceGap, averageDistance, name 순으로 정렬
13.  후보가 0건이면 빈 배열을 정상 응답으로 반환한다.

## 15\. 오류 처리 및 사용자 안내 설계

현재 UI 단계에서는 feedbackMessage, postcodeFeedbackMessage, mapErrorMessage 같은 로컬 문구로 먼저 안내한다. 아래 error.code 기준 매핑은 후속 API 연동 이후 프론트엔드 공통 규칙으로 적용한다.

프론트엔드는 error.code 를 기준으로 UI 문구를 분기한다.

| error.code          | 프론트엔드 안내                                                    |
| ------------------- | ------------------------------------------------------------------ |
| INVALID\_INPUT      | 입력값을 다시 확인해 주세요.                                       |
| UNAUTHORIZED        | 세션이 만료되었습니다. 다시 시작해 주세요.                         |
| FORBIDDEN\_RELATION | 친구 관계를 확인한 뒤 다시 시도해 주세요.                          |
| FRIEND\_NOT\_FOUND  | 해당 닉네임의 사용자를 찾을 수 없습니다.                           |
| LOCATION\_REQUIRED  | 지금 만나기에서는 두 사람 모두 위치를 공유해야 추천할 수 있습니다. |
| DEPARTURE\_REQUIRED | 나중에 만나기에서는 두 사람의 출발 위치가 모두 필요합니다.         |
| KAKAO\_API\_FAILED  | 장소 정보를 가져오지 못했습니다. 잠시 후 다시 시도해 주세요.       |
| INTERNAL\_ERROR     | 요청을 처리하지 못했습니다. 잠시 후 다시 시도해 주세요.            |

구현 기준:

*   서버 로그에는 내부 오류 원인을 남긴다.
*   추천 후보가 0건인 경우는 오류가 아니라 ok: true 와 빈 places 배열로 응답한다.
*   Route Handler 는 requestId 또는 동등한 추적 값을 로그에 포함해 장애 분석 단위를 남긴다.
*   사용자에게는 시스템 내부 구현 세부 정보나 비밀값을 노출하지 않는다.

### 15.1 오류 처리 계약

| 구분                | 서버 처리                            | 프론트엔드 처리                        |
| ------------------- | ------------------------------------ | -------------------------------------- |
| INVALID\_INPUT      | 400과 error.code 반환                | 입력 필드 아래 검증 문구 표시          |
| UNAUTHORIZED        | 401과 error.code 반환, JWT 쿠키 정리 | 로그인 화면 이동 또는 재로그인 유도    |
| FORBIDDEN\_RELATION | 403과 error.code 반환                | 채팅, 추천 요청 차단 후 안내 문구 표시 |
| FRIEND\_NOT\_FOUND  | 404와 error.code 반환                | 친구 추가 입력창 아래 안내 문구 표시   |
| LOCATION\_REQUIRED  | 409와 error.code 반환                | 추천 버튼 근처에 위치 공유 안내 표시   |
| DEPARTURE\_REQUIRED | 409와 error.code 반환                | 출발 위치 입력 영역 근처에 안내 표시   |
| KAKAO\_API\_FAILED  | 502와 error.code 반환                | 재시도 버튼과 임시 오류 안내 표시      |
| INTERNAL\_ERROR     | 500과 error.code 반환                | 공통 에러 영역에 일반 안내 문구 표시   |

### 15.2 로그 및 추적 기준

*   모든 Route Handler 는 requestId, route path, currentUserId 존재 여부, error.code 를 함께 기록한다.
*   content 원문, 세션 토큰 원문, secret 값은 로그에 남기지 않는다.
*   외부 API 실패 시 응답 전문 전체를 남기기보다 status code 와 핵심 오류 메시지만 기록한다.

오류 응답 예시:

```
{ "ok": false, "error": { "code": "LOCATION_REQUIRED", "message": "두 사람 모두 위치를 공유해야 추천할 수 있습니다." } }
```

### 16.2 수동 확인 시나리오

2.  friends 허브에서 친구 검색 필터가 목록에 즉시 반영되는지 확인
3.  friends 허브에서 새 친구 추가 후 안내 문구와 미리보기 카드가 갱신되는지 확인

5.  메시지 전송 후 로컬 메시지와 피드백 문구가 갱신되는지 확인
6.  위치 공유 후 위치 상태 문구와 공유 시각이 갱신되는지 확인

8.  나중에 만나기 모드에서 주소 검색, 핀 지정, 저장 위치 선택 흐름이 각각 동작하는지 확인
9.  저장 위치 생성 후 목록과 선택 상태가 갱신되는지 확인
10. 추천 버튼 클릭 전후로 결과 카드와 지도 패널 상태가 바뀌는지 확인
11. SDK 또는 검색 결과 없음 상황에서 레이어 내부 오류 문구가 보이는지 확인
12. 후속 인증, 저장, 추천 API 연결 전에도 전체 UI 흐름이 끊기지 않는지 확인

### 16.3 운영 확인 항목

*   Kakao Maps JS SDK 와 Daum Postcode 키 로딩이 브라우저에서 정상 동작해야 한다.

*   후속 서버 통합 단계에서는 JWT\_SECRET, service role key, Kakao REST key 같은 비밀값이 로그에 출력되지 않아야 한다.

## 19\. 결론

MeetPoint의 현재 기술 설계는 구조 설계 문서에서 정의한 책임 분리를 실제 App Router 페이지, 화면 컴포넌트, 상태 훅, Kakao 기반 입력 레이어 단위로 구체화한 구현 기준이다.

본 문서는 현재 Team A UI 소스와 일치하는 기술 요소를 우선 고정하고, 이후 인증, DB 저장, 추천 계산, 외부 API 집계를 어떤 순서로 통합할지까지 함께 정리한 기준 문서이다. 이후 개발자는 이 문서를 기준으로 UI 유지, 후속 API 구현, 추천 로직 연결을 순차적으로 진행한다.
