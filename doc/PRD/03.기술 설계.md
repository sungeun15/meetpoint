# MeetPoint 기술 설계

## 1. 문서 목적

이 문서는 MeetPoint의 기획 문서와 구조 설계 문서를 실제 구현 단위로 연결하기 위한 기술 설계 문서이다.

현재 구현 기준으로 어떤 페이지, 클라이언트 컴포넌트, 상태 훅, Route Handler, repository, service 가 사용되고 있는지 정리하고, 화면과 서버 경계를 함께 고정하는 것을 목표로 한다.

---

## 2. 기술 설계 범위

포함 범위:

1. Next.js 16 App Router 기반 페이지 구성
2. 랜딩, 인증, friends 허브, chat 상세, 추천 결과 상태 화면 구조
3. JWT 쿠키 기반 인증과 보호 페이지 리다이렉트
4. 친구 요청, 메시지, 위치, 저장 위치, 추천 조회용 Route Handler
5. Supabase repository 계층과 추천/메시지 service 계층
6. Kakao Maps JS SDK, Kakao Local API, Kakao Mobility API, Daum Postcode 연동 구조
7. 모바일 전체화면 지도, 시트 상태, 추천 지도 인터랙션 구조

제외 범위:

1. WebSocket 기반 실시간 채팅
2. 실시간 GPS 추적
3. 비밀번호 재설정
4. 추천 이력 저장
5. 운영용 배치와 관리 화면

---

## 3. 구현 기준 요약

1. 페이지 라우팅은 Next.js 16 App Router 기준으로 구현한다.
2. 인증은 JWT httpOnly 쿠키를 기준으로 처리한다.
3. /friends 와 /chat 은 세션이 없으면 /login 으로 리다이렉트한다.
4. /login 과 /signup 은 세션이 있으면 /friends 로 리다이렉트한다.
5. friends 화면은 친구 목록, 검색, 요청 생성, 요청 수락/거절 상태를 함께 관리한다.
6. chat 화면은 선택 친구, 메시지, 위치 상태, 저장 위치, 추천 입력, 추천 결과, 지도 상호작용을 하나의 흐름으로 묶는다.
7. 데이터 접근은 Route Handler -> repository -> Supabase 구조를 사용한다.
8. 추천 계산은 service 계층에서 수행하고, 결과만 API 응답으로 반환한다.
9. 브라우저 SDK 기반 지도와 주소 검색 UI 는 클라이언트 컴포넌트 안에서 닫힌 흐름으로 유지한다.

## 5. 페이지 설계

### 5.1 페이지 라우팅

| 경로      | 역할               | 현재 동작                                                 |
| --------- | ------------------ | --------------------------------------------------------- |
| /         | 랜딩 페이지        | HomeHero 렌더링                                           |
| /login    | 로그인 페이지      | 세션 없으면 AuthScreen(login), 세션 있으면 /friends 이동  |
| /signup   | 회원가입 페이지    | 세션 없으면 AuthScreen(signup), 세션 있으면 /friends 이동 |
| /friends  | friends 허브       | 세션 없으면 /login 이동                                   |
| /chat     | chat 상세          | 세션 없으면 /login, friend 파라미터 없으면 /friends 이동  |
| /features | 기능 소개 페이지   | public 소개 콘텐츠 렌더링                                 |
| /about    | 서비스 소개 페이지 | public 소개 콘텐츠 렌더링                                 |

### 5.2 랜딩 및 인증 페이지 구현 기준

1. 랜딩 CTA 는 현재 /login 으로 이동한다.
2. 로그인과 회원가입은 모두 성공 시 JWT 쿠키를 발급하고 /friends 로 진입한다.
3. 인증 실패와 검증 오류는 카드 내부 메시지로 표시한다.

### 5.3 friends 허브 페이지 구현 기준

1. friends 화면은 좌측 친구 목록과 우측 허브 콘텐츠로 구성된다.
2. 좌측은 친구 필터와 친구 선택을 담당한다.
3. 우측은 친구 검색, 요청 생성, 받은 요청/보낸 요청, 선택 친구 미리보기, 안내 영역을 담당한다.
4. 화면 진입 시 GET /api/friends 로 목록과 요청 상태를 불러온다.
5. 친구 검색은 GET /api/friends?nickname=... 으로 처리한다.
6. 친구 추가는 POST /api/friends 로 pending 요청을 생성한다.
7. 받은 요청 수락/거절은 PATCH /api/friends 로 처리한다.

### 5.4 chat 상세 페이지 구현 기준

1. chat 화면은 친구 사이드바와 상세 상호작용 영역으로 구성된다.
2. 상세 영역은 친구 헤더, 채팅 패널, 위치 상태 패널, 추천 입력/결과 패널로 구성된다.
3. 친구 헤더에는 모바일 접기 상태와 채팅방 나가기 모달이 포함된다.
4. 채팅 패널은 커서 기반 메시지 조회와 입력 전송을 지원한다.
5. 위치 상태 패널은 현재 위치 공유, 친구 위치 확인, 저장 흐름을 지원한다.
6. 추천 패널은 now/later 모드, 카테고리, 저장 위치, 지도, 추천 결과를 통합한다.
7. 모바일에서는 추천 지도 전체화면 레이어와 시트 높이 조절 상태를 제공한다.

## 6. 프론트엔드 상태 설계

### 6.1 friends 화면 상태

주요 상태:

1. friends
2. incomingRequests
3. outgoingRequests
4. friendSearch
5. pendingNickname
6. searchedFriend
7. searchedFriendRelation
8. selectedFriendId
9. formMessage

구현 기준:

1. 친구 목록과 요청 목록은 서버 응답을 화면 상태로 보관한다.
2. 친구 검색 결과는 현재 관계 상태와 함께 관리한다.
3. 요청 처리 후 friends, incomingRequests, outgoingRequests 를 함께 갱신한다.

### 6.2 chat 화면 상태

주요 상태:

1. activeFriendId
2. selectedMessages
3. draftMessage
4. myLocationStatus
5. friendLocationStatus
6. meetingMode
7. selectedCategory
8. departureInputMethod
9. visibleSavedDepartures
10. recommendationSummary
11. recommendationCards
12. mapMarkers
13. overlay 레이어 상태

구현 기준:

1. 선택 친구가 바뀌면 메시지, 위치, 추천 상태가 함께 재해석된다.
2. 위치와 저장 위치 상태는 recommendation 흐름과 연결된다.
3. 추천 결과는 카드, 지도 마커, 전체화면 지도 상태까지 함께 갱신된다.
4. 모바일 UI 는 헤더 접기, 대화 접기, 지도 전체화면 시트 상태를 별도로 가진다.

## 7. 서버 구조 설계

### 7.1 인증 계층

1. signup/login 은 JWT 쿠키를 발급한다.
2. logout 은 인증 쿠키를 항상 제거한다.
3. getCurrentSession 과 createProtectedRoute 로 보호 페이지와 보호 API 접근을 통일한다.

### 7.2 Route Handler 계층

| 영역                    | 엔드포인트               | 책임                                                |
| ----------------------- | ------------------------ | --------------------------------------------------- |
| auth                    | signup, login, logout    | 사용자 생성, 인증, 쿠키 처리                        |
| friends                 | GET, POST, PATCH, DELETE | 친구 목록/검색, 요청 생성, 요청 처리, 채팅방 나가기 |
| messages                | GET, POST                | 메시지 조회/저장                                    |
| location                | GET, POST                | 마지막 위치 조회/저장                               |
| location/search         | GET                      | 출발 위치 검색                                      |
| location/departures     | GET, POST, PATCH, DELETE | 저장 위치 CRUD                                      |
| location/departures/use | POST                     | 최근 사용 시각 갱신                                 |
| recommendations         | POST                     | 추천 결과 계산                                      |
| recommendations/routes  | POST                     | 길찾기 보조 응답 생성                               |

### 7.3 Repository 계층

1. users.ts 는 사용자 조회, 생성, 위치 갱신을 담당한다.
2. friends.ts 는 친구 목록 조회, 요청 생성, 관계 확인, 요청 처리, 관계 삭제를 담당한다.
3. messages.ts 는 메시지 저장, 조회, 읽음 처리 기반 쿼리를 담당한다.
4. departures.ts 는 저장 위치 CRUD, 최근 사용 시각 갱신, 선택 상태 관련 쿼리를 담당한다.

### 7.4 Service 계층

1. recommendation-service.ts 는 중심점 계산, 후보 조회, 점수 계산, 정렬을 담당한다.
2. message-service.ts 는 커서 조회 응답과 읽음 포인터를 함께 조합한다.

## 8. 외부 연동 설계

### 8.1 Supabase

1. users, friends, messages, departure_locations 스키마를 사용한다.
2. 모든 DB 접근은 repository 계층을 통해 수행한다.
3. 브라우저에서 직접 Supabase 를 호출하지 않는다.

### 8.2 Kakao Local API

1. 출발 위치 검색과 추천 후보 검색에 사용한다.
2. 브라우저 직접 호출이 아니라 서버 Route Handler 를 통해 호출한다.

### 8.3 Kakao Maps JS SDK

1. 지도 미리보기, 마커 렌더링, 핀 지정, 전체화면 지도 UI 에 사용한다.
2. 모바일 전체화면 지도에서는 fill 레이아웃으로 가용 높이를 채운다.

### 8.4 Kakao Mobility API

1. 추천 장소 기준 길찾기 카드의 경로 정보 계산에 사용한다.
2. 차량 모드는 실제 provider 를 사용하고, 나머지는 fallback 경로 응답을 사용한다.

### 8.5 Daum Postcode

1. 나중에 만나기 모드 주소 검색 보조 UI 로 사용한다.
2. 검색 결과는 저장 위치 및 추천 입력 좌표로 연결된다.

## 9. 오류 처리 및 검증 기준

1. 입력 검증 실패는 InputValidationError 로 묶어 400 INVALID_INPUT 으로 반환한다.
2. 인증 실패는 401 UNAUTHORIZED 를 사용한다.
3. 친구 관계가 없는 경우 403 FORBIDDEN_RELATION 을 사용한다.
4. 닉네임 충돌은 409 CONFLICT_NICKNAME 을 사용한다.
5. 위치 부족과 출발지 부족은 각각 409 LOCATION_REQUIRED, 409 DEPARTURE_REQUIRED 를 사용한다.
6. 외부 API 실패는 KAKAO_API_FAILED 또는 KAKAO_MOBILITY_API_FAILED 로 구분한다.

---

## 10. 현재 설계 결론

1. MeetPoint 는 이미 UI-only 단계가 아니라 인증, API, DB, 외부 연동 구조를 포함한 풀스택 MVP 구조로 진입했다.
2. 화면과 서버 경계는 App Router 페이지, client component, Route Handler, repository, service 의 계층으로 분리되어 있다.
3. 현재 남은 작업은 구조 재설계가 아니라 문서와 구현의 차이를 줄이고, 남은 통합/QA 를 안정화하는 단계로 본다.
