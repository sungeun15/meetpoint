# MeetPoint 기술 설계

## 1\. 문서 목적

이 문서는 MeetPoint의 기획 문서와 구조 설계 문서를 실제 구현 단위로 연결하기 위한 기술 설계 문서이다.

03번 문서의 목적은 다음과 같다.

*   어떤 폴더와 파일을 만들지 정한다.
*   각 Route Handler와 UI 컴포넌트의 책임을 분리한다.
*   인증, DB 접근, 추천 계산, 외부 API 호출을 어떤 순서로 처리할지 고정한다.
*   구현 순서와 테스트 기준을 명확히 하여 개발 중 해석 차이를 줄인다.

---

## 2\. 기술 설계 범위

본 문서의 범위는 MVP 1차 구현 기준으로 한정한다.

포함 범위:

*   Next.js 16 App Router 기반 페이지 구성
*   Route Handler 기반 API 구현
*   Supabase users, friends, messages 테이블 사용
*   JWT + httpOnly 쿠키 기반 인증 구현
*   Kakao Map API 연동
*   Kakao Local API 기반 추천 계산
*   5초 폴링 기반 채팅 동기화

제외 범위:

*   WebSocket 기반 실시간 채팅
*   실시간 GPS 추적
*   닉네임 찾기 기능
*   비밀번호 재설정 기능
*   추천 이력 저장 기능
*   추천 결과 통계 및 분석 기능

---

## 3\. 구현 기준 요약

기술 설계의 기본 원칙은 다음과 같다.

*   페이지 라우팅은 App Router 기준으로 구현한다.
*   모든 보호 데이터 접근은 Route Handler를 통해 처리한다.
*   브라우저는 Supabase에 직접 쓰기 요청을 보내지 않는다.
*   인증 식별은 meetpoint\_auth JWT 쿠키 기준으로 통일한다.
*   추천 계산은 서버에서 수행하고 결과만 클라이언트에 반환한다.
*   카카오 지도는 클라이언트 컴포넌트에서 렌더링하고, 카카오 장소 검색은 서버에서 호출한다.

#### 생성 순서 원칙

*   1차 생성 필수 경로만으로 시작, 친구, 메시지, 위치, 추천의 핵심 사용자 흐름이 연결되어야 한다.
*   2차 생성 권장 경로는 중복 UI 제거, 공통화, 개발 보조 기능 강화 시점에 추가한다.
*   파일 수를 늘리는 것보다 책임 경계가 명확한지 여부를 우선 판단한다.

설계 기준:

*   app 디렉토리는 라우팅과 화면 진입점만 가진다.
*   components 디렉토리는 UI 렌더링 책임만 가진다.
*   lib/repositories는 DB 조회와 저장 책임만 가진다.
*   lib/services는 여러 repository와 외부 API를 조합하는 비즈니스 로직을 담당한다.
*   lib/utils는 순수 함수 중심으로 구성한다.
*   fixtures는 개발 및 테스트 환경에서만 사용한다.

| ----- | ----------- | --------------------------------------------------- |
| /     | 시작 페이지 | 서버 컴포넌트 + 닉네임 입력 클라이언트 컴포넌트     |
| /main | 메인 페이지 | 서버 컴포넌트에서 세션 확인 후 클라이언트 쉘 렌더링 |

### 5.2 시작 페이지 구현 기준

파일:

*   app/page.tsx
*   components/start/StartCard.tsx
*   components/start/AuthForm.tsx

동작 기준:

1.  서버 컴포넌트가 JWT 쿠키를 읽는다.
2.  유효한 JWT가 있으면 /main 으로 redirect 한다.
3.  JWT가 없으면 시작 카드와 인증 폼을 렌더링한다.
4.  폼 제출 시 POST /api/auth/signup 또는 POST /api/auth/login 호출 후 성공하면 /main 으로 이동한다.

### 5.3 메인 페이지 구현 기준

파일:

*   app/main/page.tsx
*   components/main/MainShell.tsx

동작 기준:

1.  서버 컴포넌트가 JWT 쿠키를 검증한다.
2.  JWT가 없거나 만료되면 / 로 redirect 한다.
3.  JWT가 유효하면 최소 currentUser 정보를 MainShell에 전달한다.
4.  MainShell은 친구 목록, 선택 상태, 채팅, 지도, 추천 결과 상태를 관리한다.

## 9\. JWT 인증 기술 설계

파일:

*   lib/auth/session.ts

필수 함수:

*   signAuthToken(payload)
*   verifyAuthToken(token)
*   setAuthCookie(response, payload)
*   clearAuthCookie(response)
*   getAuthFromCookies()
*   requireAuthOrThrow()

JWT payload 기준:

```
type AuthPayload = {
    userId: string;
    nickname: string;
    iat: number;
    exp: number;
};
```

구현 기준:

*   쿠키 이름은 meetpoint\_auth 로 고정한다.
*   JWT\_SECRET 기반 JWT 서명 또는 동등한 안전한 서명 방식을 사용한다.
*   쿠키 속성은 httpOnly, sameSite=lax, path=/ 를 기본으로 하고 운영 환경에서만 secure=true 로 설정한다.
*   쿠키 만료 시간은 7일 기준으로 고정하며, exp 와 쿠키 maxAge 를 동일하게 유지한다.
*   exp 만료 검증 실패 시 쿠키를 즉시 삭제한다.
*   브라우저에서는 auth payload를 직접 해석하지 않는다.
*   페이지 보호와 API 보호는 같은 검증 함수 하나를 공유한다.
*   currentUserId 는 검증된 JWT에서만 주입하며 요청 본문이나 query 에서 사용자 ID를 받지 않는다.

### 9.1 인증 함수별 계약

| 함수               | 입력                      | 출력                  | 실패 조건                               |
| ------------------ | ------------------------- | --------------------- | --------------------------------------- |
| signAuthToken      | AuthPayload               | string                | JWT\_SECRET 누락, payload 필수값 누락   |
| verifyAuthToken    | token string              | AuthPayload 또는 null | 서명 불일치, 만료, 형식 오류            |
| setAuthCookie      | NextResponse, AuthPayload | NextResponse          | response 객체 없음, payload 오류        |
| clearAuthCookie    | NextResponse              | NextResponse          | response 객체 없음                      |
| getAuthFromCookies | 없음                      | AuthPayload 또는 null | 쿠키 없음, 토큰 검증 실패               |
| requireAuthOrThrow | 없음                      | AuthPayload           | JWT 없음 또는 만료 시 UNAUTHORIZED 예외 |

### 9.2 인증 함수 예시

#### signAuthToken 예시

입력 예시:

```
{
    userId: "uuid",
    nickname: "민수",
    iat: 1770000000,
    exp: 1770604800
}
```

출력 예시:

```
"signed.jwt.token"
```

실패 조건 예시:

*   JWT\_SECRET 이 없으면 서버 시작 또는 호출 시점에 INTERNAL\_ERROR 로 처리한다.
*   userId 또는 exp 같은 필수 필드가 비어 있으면 토큰 발급을 중단한다.

#### verifyAuthToken 예시

입력 예시:

```
"signed.jwt.token"
```

성공 출력 예시:

```
{
    userId: "uuid",
    nickname: "민수",
    iat: 1770000000,
    exp: 1770604800
}
```

실패 조건 예시:

*   서명이 다르면 null 또는 UNAUTHORIZED 처리 기준으로 반환한다.
*   exp 가 현재 시각보다 이전이면 쿠키 삭제 대상이다.

## 10\. 입력값 검증 설계

파일:

*   lib/utils/nickname.ts
*   lib/utils/validation.ts

필수 함수:

*   normalizeNickname(value)
*   validateNickname(value)
*   validatePassword(value)
*   validateFriendNickname(value, currentNickname)
*   validateMessageContent(value)
*   validateCoordinates(lat, lng)
*   validateUuid(value)
*   validateMessageQuery(after, limit)

구현 기준:

*   normalizeNickname은 trim, 연속 공백 축소, 영문 소문자 정규화를 수행한다.
*   validatePassword는 8자 이상 20자 이하와 허용 문자 기준을 검증한다.
*   validateMessageQuery는 기본 limit 50, 최대 100을 강제한다.
*   invalid input은 400 INVALID\_INPUT으로 통일한다.

### 10.1 검증 함수별 계약

| 함수                   | 입력                            | 출력              | 실패 조건                      |
| ---------------------- | ------------------------------- | ----------------- | ------------------------------ |
| normalizeNickname      | raw string                      | normalized string | string 아님, 빈 값             |
| validateNickname       | nickname string                 | 검증 통과 문자열  | 길이 제한 위반, 허용 문자 위반 |
| validatePassword       | password string                 | 검증 통과 문자열  | 길이 제한 위반, 허용 문자 위반 |
| validateFriendNickname | friendNickname, currentNickname | 검증 통과 문자열  | 자기 자신과 동일, 형식 오류    |
| validateMessageContent | content string                  | trim 된 content   | 빈 문자열, 500자 초과          |
| validateCoordinates    | lat, lng                        | { lat, lng }      | 범위 초과, 숫자 아님           |
| validateUuid           | raw string                      | uuid string       | UUID 형식 불일치               |
| validateMessageQuery   | after, limit                    | { after, limit }  | ISO datetime 아님, limit 초과  |

### 10.2 검증 예시

#### normalizeNickname 예시

입력 예시:

```
"  Min   Su  "
```

출력 예시:

```
"min su"
```

#### validateMessageQuery 예시

입력 예시:

```
after = "2026-05-03T10:00:00.000Z"
limit = "50"
```

출력 예시:

```
{ after: "2026-05-03T10:00:00.000Z", limit: 50 }
```

실패 조건 예시:

*   limit 가 100을 넘으면 400 INVALID\_INPUT
*   after 가 ISO datetime 형식이 아니면 400 INVALID\_INPUT

구현 기준:

*   MVP는 Supabase Auth를 사용하지 않으므로 Route Handler 내부 서버 접근은 SUPABASE\_SERVICE\_ROLE\_KEY 기반으로 수행한다.
*   service role client 생성은 lib/supabase/server.ts 한 곳으로 제한한다.
*   repository 함수는 currentUserId 또는 명시적 대상 ID를 인자로 받아 조회 범위를 고정한다.
*   브라우저는 앱 데이터에 대해 Supabase 직접 read/write를 하지 않고, 모든 데이터 요청은 Route Handler를 경유한다.
*   DB 접근 로직은 Route Handler 안에 직접 쓰지 않고 repository 함수로 분리한다.
*   사용자 생성, 양방향 친구 관계 복구 같은 관리성 작업 외에는 범위가 넓은 update/delete 를 금지한다.

### 11.3 구현 제약, 관계, 인덱스 기준

실제 테이블 생성 시 반영해야 하는 최소 규칙은 다음과 같다.

| 테이블          | 필수 제약                                                                                                                            | 권장 인덱스                                                                                | 구현 메모                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| users           | unique(nickname\_normalized)                                                                                                         | index(location\_updated\_at), index(nickname\_normalized)                                  | nickname은 표시용, nickname\_normalized는 비교용으로 분리  |
| friends         | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id, unique(user\_id, friend\_id), check(user\_id \<> friend\_id) | index(user\_id), index(friend\_id)                                                         | 친구 추가 시 양방향 row 2건을 함께 upsert                  |
| messages        | foreign key(sender\_id) -> users.id, foreign key(receiver\_id) -> users.id                                                           | index(sender\_id, receiver\_id, created\_at), index(receiver\_id, sender\_id, created\_at) | 조회는 두 사용자 간 메시지를 created\_at 오름차순으로 반환 |
| recommendations | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id                                                               | index(user\_id, friend\_id, created\_at desc)                                              | MVP 1차에서는 생성하지 않고 후속 확장 시 추가              |

### 11.4 트랜잭션 및 동시성 기준

*   users 생성은 nickname\_normalized unique 제약을 전제로 구현하고, 동시 생성 충돌 시 기존 row 재조회로 수습한다.
*   친구 추가는 양방향 row 2건을 하나의 트랜잭션 또는 동등한 원자적 upsert 흐름으로 처리한다.
*   한쪽 관계만 남은 비정상 상태를 발견하면 누락된 반대 방향 row를 같은 요청 안에서 복구한다.
*   메시지 저장은 단건 insert 로 처리하되, 조회 정렬은 created\_at asc, id asc 로 고정한다.

### 12.5 메시지 조회

Route:

*   GET /api/messages

*   friendId: 필수
*   after: 선택
*   limit: 선택, 기본 50

처리 순서:

1.  세션 검증
2.  friendId, after, limit 검증
3.  친구 관계 확인
4.  기본 정렬 키는 createdAt asc, id asc 로 고정한다.
5.  after가 없으면 최신 limit 개를 desc 로 조회한 뒤 createdAt asc, id asc 순으로 다시 정렬한다.
6.  after가 있으면 after 이후 메시지만 조회한다.
7.  클라이언트 병합 기준으로 lastMessageCreatedAt 과 pollingIntervalSec = 5 를 함께 반환한다.

구현 메모:

*   MVP 1차에서는 query 를 단순화하기 위해 after 단일값을 유지한다.
*   같은 시각 메시지 경계에서 중복 표시가 생기지 않도록 클라이언트는 message.id 기준으로 병합한다.
*   대량 히스토리 페이지네이션은 MVP 범위에서 제외한다.

응답 예시:

```
{ "ok": true, "data": { "messages": [ { "id": "uuid-m", "senderId": "uuid-a", "receiverId": "uuid-f", "content": "언제 만날까?", "createdAt": "2026-05-03T10:01:00.000Z" } ], "lastMessageCreatedAt": "2026-05-03T10:01:00.000Z", "pollingIntervalSec": 5 } }
```

실패 예시:

*   friendId 가 UUID 형식이 아니면 400 INVALID\_INPUT
*   권한 없는 친구 대상이면 403 FORBIDDEN\_RELATION

| 항목           | 내용                                     |
| -------------- | ---------------------------------------- |
| 호출 위치      | 서버 전용 lib/kakao/local.ts             |
| 입력 값        | midpoint lat/lng, category, radius, size |
| 출력 값        | 정규화된 장소 후보 배열                  |
| 주요 실패 조건 | HTTP 실패, 응답 형식 오류, 인증 오류     |

요청 예시:

```
category = "cafe"
radius = 2000
size = 15
midpoint = { lat: 37.55025, lng: 127.0365 }
```

출력 예시:

```
[
    {
        name: "중간카페",
        category: "cafe",
        lat: 37.551,
        lng: 127.012
    }
]
```

실패 조건 예시:

*   REST API 키 누락 또는 인증 실패 시 외부 API 실패로 분류한다.
*   운영 환경에서는 실패 시 fixture 대신 502 KAKAO\_API\_FAILED 를 반환한다.

## 15\. 오류 처리 및 사용자 안내 설계

프론트엔드는 error.code 를 기준으로 UI 문구를 분기한다.

| error.code          | 프론트엔드 안내                                              |
| ------------------- | ------------------------------------------------------------ |
| INVALID\_INPUT      | 입력값을 다시 확인해 주세요.                                 |
| UNAUTHORIZED        | 세션이 만료되었습니다. 다시 시작해 주세요.                   |
| FORBIDDEN\_RELATION | 친구 관계를 확인한 뒤 다시 시도해 주세요.                    |
| FRIEND\_NOT\_FOUND  | 해당 닉네임의 사용자를 찾을 수 없습니다.                     |
| LOCATION\_REQUIRED  | 두 사람 모두 위치를 공유해야 추천할 수 있습니다.             |
| KAKAO\_API\_FAILED  | 장소 정보를 가져오지 못했습니다. 잠시 후 다시 시도해 주세요. |
| INTERNAL\_ERROR     | 요청을 처리하지 못했습니다. 잠시 후 다시 시도해 주세요.      |

구현 기준:

*   서버 로그에는 내부 오류 원인을 남긴다.
*   추천 후보가 0건인 경우는 오류가 아니라 ok: true 와 빈 places 배열로 응답한다.
*   Route Handler 는 requestId 또는 동등한 추적 값을 로그에 포함해 장애 분석 단위를 남긴다.
*   사용자에게는 시스템 내부 구현 세부 정보나 비밀값을 노출하지 않는다.

### 15.1 오류 처리 계약

| 구분                | 서버 처리                            | 프론트엔드 처리                        |
| ------------------- | ------------------------------------ | -------------------------------------- |
| INVALID\_INPUT      | 400과 error.code 반환                | 입력 필드 아래 검증 문구 표시          |
| UNAUTHORIZED        | 401과 error.code 반환, JWT 쿠키 정리 | 로그인 화면 이동 또는 재로그인 유도    |
| FORBIDDEN\_RELATION | 403과 error.code 반환                | 채팅, 추천 요청 차단 후 안내 문구 표시 |
| FRIEND\_NOT\_FOUND  | 404와 error.code 반환                | 친구 추가 입력창 아래 안내 문구 표시   |
| LOCATION\_REQUIRED  | 409와 error.code 반환                | 추천 버튼 근처에 위치 공유 안내 표시   |
| KAKAO\_API\_FAILED  | 502와 error.code 반환                | 재시도 버튼과 임시 오류 안내 표시      |
| INTERNAL\_ERROR     | 500과 error.code 반환                | 공통 에러 영역에 일반 안내 문구 표시   |

### 15.2 로그 및 추적 기준

*   모든 Route Handler 는 requestId, route path, currentUserId 존재 여부, error.code 를 함께 기록한다.
*   content 원문, 세션 토큰 원문, secret 값은 로그에 남기지 않는다.
*   외부 API 실패 시 응답 전문 전체를 남기기보다 status code 와 핵심 오류 메시지만 기록한다.

오류 응답 예시:

```
{ "ok": false, "error": { "code": "LOCATION_REQUIRED", "message": "두 사람 모두 위치를 공유해야 추천할 수 있습니다." } }
```

## 16\. 테스트 설계

### 16.1 우선 테스트 대상

*   nickname 정규화 함수
*   JWT 서명 및 만료 검증 함수
*   haversine 거리 계산 함수
*   추천 점수 계산과 정렬 함수
*   친구 추가 시 양방향 관계 생성 함수
*   메시지 조회의 limit, after 처리
*   닉네임 중복 생성 경쟁 상황에서 기존 user 재조회 처리
*   변조 또는 만료 쿠키 처리
*   추천 후보 0건 정상 응답 처리
*   Kakao API 실패 시 fallback 또는 502 분기 처리

### 16.2 수동 확인 시나리오

1.  닉네임 입력 후 시작 페이지에서 /main 이동 확인
2.  친구 추가 후 친구 목록 반영 확인
3.  친구 선택 후 최신 메시지 50개 로드 확인
4.  메시지 전송 직후 리스트 재조회 확인
5.  위치 저장 후 위치 시각 문구 갱신 확인
6.  추천 버튼 클릭 후 중심점과 상위 3개 결과 표시 확인
7.  위치 미공유 상태에서 추천 차단 확인
8.  동일 친구를 다시 추가해도 중복 관계가 생기지 않는지 확인
9.  만료 쿠키 또는 잘못된 쿠키로 보호 API 호출 시 시작 화면 복귀 확인
10.  추천 후보 0건일 때 오류 대신 빈 상태 UI 표시 확인

### 16.3 운영 확인 항목

*   서버 로그에 JWT\_SECRET, service role key, Kakao REST key 같은 비밀값이 출력되지 않아야 한다.
*   users, friends, messages 테이블의 핵심 제약과 인덱스가 실제 DB 에 반영되어 있어야 한다.
*   운영 환경에서는 secure 쿠키와 fallback 비활성화가 적용되어야 한다.

### 16.4 자동화 테스트 케이스 기준

| 대상                   | 케이스                                 | 기대 결과                             |
| ---------------------- | -------------------------------------- | ------------------------------------- |
| session.ts             | 만료 전 토큰 검증                      | AuthPayload 반환                      |
| session.ts             | 변조 토큰 검증                         | null 또는 UNAUTHORIZED 처리           |
| nickname.ts            | 대소문자와 공백이 섞인 nickname 정규화 | nickname\_normalized 기준 문자열 반환 |
| friends repository     | 동일 친구 재추가                       | 중복 row 없이 기존 관계 유지          |
| messages route         | limit 101 요청                         | 400 INVALID\_INPUT                    |
| messages route         | after polling 조회                     | after 이후 메시지만 반환              |
| recommendation-service | 후보 0건                               | ok: true 와 빈 places 배열            |
| recommendation-service | 후보 다수                              | score 기준 상위 3개 정렬 반환         |
| kakao/local.ts         | 운영 환경 API 실패                     | 502 KAKAO\_API\_FAILED                |

### 16.5 수동 검증 완료 기준

*   시작, 친구 추가, 채팅, 위치 저장, 추천 결과의 핵심 사용자 흐름이 최소 1회 이상 실제 화면에서 확인되어야 한다.
*   보호 API 에 대해 만료 쿠키, 잘못된 friendId, 빈 message content 같은 대표 실패 케이스가 확인되어야 한다.
*   추천 0건, 외부 API 실패, 위치 미공유 상태를 각각 구분해 UI 문구가 다르게 보이는지 확인해야 한다.

## 18\. 개발 완료 기준

다음 조건이 충족되면 MVP 1차 기술 구현이 완료된 것으로 본다.

*   / 와 /main 페이지가 정상 동작한다.
*   모든 보호 API가 JWT 쿠키로 현재 사용자를 식별한다.
*   친구 추가 시 양방향 관계가 보장된다.
*   메시지 조회가 최신 50개 초기 로드와 polling 추가 조회를 지원한다.
*   위치 저장과 위치 시각 표시가 동작한다.
*   추천 API가 중심점 계산, 후보 조회, 거리 계산, 점수 정렬을 모두 수행한다.
*   추천 후보 0건은 오류가 아니라 정상 빈 결과로 처리된다.
*   브라우저에서 Supabase 직접 쓰기 요청을 하지 않는다.
*   DB 제약과 인덱스가 문서 기준대로 반영된다.
*   운영 환경에서 비밀키가 브라우저에 노출되지 않는다.
*   운영 환경에서 secure 쿠키와 fallback 비활성화가 적용된다.

MeetPoint의 기술 설계는 구조 설계 문서에서 정의한 책임 분리를 실제 파일, 함수, Route Handler 단위로 구체화한 구현 기준이다.

본 문서는 MVP 1차 구현에서 필요한 최소 기술 결정을 고정하며, 이후 개발자는 이 문서를 기준으로 폴더 생성, API 구현, UI 통합, 추천 로직 구현을 순차적으로 진행한다.
