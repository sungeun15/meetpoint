# MeetPoint 기술 설계

## 1\. 문서 목적

이 문서는 MeetPoint의 기획 문서와 구조 설계 문서를 실제 구현 단위로 연결하기 위한 기술 설계 문서이다.

03번 문서의 목적은 다음과 같다.

*   어떤 폴더와 파일을 만들지 정한다.
*   각 Route Handler와 UI 컴포넌트의 책임을 분리한다.
*   인증, DB 접근, 추천 계산, 외부 API 호출을 어떤 순서로 처리할지 고정한다.
*   구현 순서와 테스트 기준을 명확히 하여 개발 중 해석 차이를 줄인다.

---

## 2\. 기술 설계 범위

본 문서의 범위는 MVP 1차 구현 기준으로 한정한다.

포함 범위:

*   Next.js 16 App Router 기반 페이지 구성
*   Route Handler 기반 API 구현
*   Supabase users, friends, messages 테이블 사용
*   JWT + httpOnly 쿠키 기반 인증 구현
*   Kakao Map API 연동
*   출발 위치 검색 및 입력 처리
*   Kakao Local API 기반 추천 계산
*   지금 만나기 / 나중에 만나기 모드 분기 처리
*   카테고리 선택, 반경 확장, 활성도 패널티를 포함한 추천 계산
*   5초 폴링 기반 채팅 동기화

제외 범위:

*   WebSocket 기반 실시간 채팅
*   실시간 GPS 추적
*   닉네임 찾기 기능
*   비밀번호 재설정 기능
*   추천 이력 저장 기능
*   추천 결과 통계 및 분석 기능

---

## 3\. 구현 기준 요약

기술 설계의 기본 원칙은 다음과 같다.

*   페이지 라우팅은 App Router 기준으로 구현한다.
*   모든 보호 데이터 접근은 Route Handler를 통해 처리한다.
*   브라우저는 Supabase에 직접 쓰기 요청을 보내지 않는다.
*   인증 식별은 meetpoint\_auth JWT 쿠키 기준으로 통일한다.
*   추천 계산은 서버에서 수행하고 결과만 클라이언트에 반환한다.
*   카카오 지도는 클라이언트 컴포넌트에서 렌더링하고, 카카오 주소 검색과 장소 검색은 서버에서 호출한다.
*   추천 요청은 friendId, mode, category, 필요한 경우 출발 위치 입력값을 함께 전달한다.

## 5\. 페이지 설계

### 5.1 페이지 라우팅

MVP 기준 페이지 라우팅은 다음과 같이 설계한다.

| 경로      | 역할                | 구현 방식                                                 |
| --------- | ------------------- | --------------------------------------------------------- |
| /         | 랜딩 페이지         | 서버 또는 정적 페이지 + 랜딩 히어로 컴포넌트              |
| /login    | 로그인 페이지       | 인증 화면 클라이언트 컴포넌트 렌더링                      |
| /signup   | 회원가입 페이지     | 인증 화면 클라이언트 컴포넌트 렌더링                      |
| /friends  | friends 허브 페이지 | 보호 페이지에서 friends 허브 화면 렌더링                  |
| /chat     | chat 상세 페이지    | 보호 페이지에서 friend searchParams 기반 chat 화면 렌더링 |
| /features | 기능 소개 페이지    | public 소개 콘텐츠 렌더링                                 |
| /about    | 서비스 소개 페이지  | public 소개 콘텐츠 렌더링                                 |

### 5.2 랜딩 및 인증 페이지 구현 기준

파일:

*   app/page.tsx
*   app/login/page.tsx
*   app/signup/page.tsx
*   app/components/home-hero.tsx
*   app/components/auth-screen.tsx

동작 기준:

1.  app/page.tsx 는 랜딩 히어로와 public CTA를 렌더링한다.
2.  랜딩 CTA는 로그인 상태에 따라 /login 또는 /friends 로 분기될 수 있다.
3.  app/login/page.tsx 와 app/signup/page.tsx 는 auth-screen 을 모드별로 재사용한다.
4.  회원가입 또는 로그인 성공 시 POST /api/auth/* 호출 후 /friends 로 이동한다.

### 5.3 friends 허브 페이지 구현 기준

파일:

*   app/friends/page.tsx
*   app/components/friends-screen.tsx
*   app/components/friends/friends-sidebar.tsx
*   app/components/friends/friends-content.tsx

동작 기준:

1.  보호 페이지 접근 전 JWT 쿠키를 검증한다.
2.  JWT가 없거나 만료되면 /login 또는 / 로 이동시킨다.
3.  friends-screen 은 친구 목록, 친구 검색, 친구 추가 입력 상태를 관리한다.
4.  친구 선택 액션은 /chat?friend={id} 이동으로 연결한다.

### 5.4 chat 상세 페이지 구현 기준

파일:

*   app/chat/page.tsx
*   app/components/chat-screen.tsx
*   app/components/chat/chat-content.tsx
*   app/components/chat/use-chat-screen-state.ts

동작 기준:

1.  app/chat/page.tsx 는 searchParams.friend 값을 읽어 requestedFriendId 로 전달한다.
2.  chat-screen 은 좌측 친구 사이드바와 우측 상세 콘텐츠를 함께 렌더링한다.
3.  use-chat-screen-state 는 선택 친구, 메시지, 위치 상태, 추천 상태를 묶어 관리한다.
4.  추천 결과는 chat 페이지 내부 상태로 확장한다.

## 6\. 프론트엔드 상태 설계

현재 퍼블 기준 상태는 friends 화면 상태와 chat 화면 상태로 분리해 관리한다.

### 6.1 friends 화면 상태

| 상태명          | 타입 예시        | 용도                            |
| --------------- | ---------------- | ------------------------------- |
| friendSearch    | string           | 친구 목록 필터 입력값           |
| filteredFriends | FriendSummary[]  | friends 허브에 표시할 친구 목록 |
| pendingNickname | string           | 친구 추가 입력값                |
| feedbackMessage | string 또는 null | 친구 추가 성공 또는 실패 안내   |

구현 기준:

*   friendSearch 는 서버 요청이 아니라 클라이언트 목록 필터에만 사용한다.
*   친구 선택은 상태 유지보다 /chat 이동을 우선 기준으로 삼는다.

### 6.2 chat 화면 상태

| 상태명                                        | 타입 예시                              | 용도                                 |
| --------------------------------------------- | -------------------------------------- | ------------------------------------ |
| activeFriendId                                | string 또는 null                       | 현재 선택한 친구 ID                  |
| selectedFriend                                | FriendSummary 또는 null                | 현재 선택한 친구                     |
| selectedMessages                              | MessageItem[]                          | 현재 대화 메시지                     |
| draftMessage                                  | string                                 | 입력 중인 메시지                     |
| myLocationStatus                              | string 또는 null                       | 현재 사용자 위치 상태 문구           |
| friendLocationStatus                          | string 또는 null                       | 친구 위치 상태 문구                  |
| lastSharedAt                                  | string 또는 null                       | 마지막 위치 공유 시각                |
| meetingMode                                   | RecommendationMode                     | 지금 만나기, 나중에 만나기 선택 상태 |
| category                                      | RecommendationCategory 또는 null       | 추천 카테고리 선택 상태              |
| departureInput                                | DepartureInputState                    | 현재 사용자 출발 위치 입력 상태      |
| friendDepartureInput                          | DepartureInputState                    | 친구 기준 출발 위치 입력 상태        |
| recommendationResult 또는 recommendationCards | RecommendationResult 또는 UI 카드 배열 | 추천 결과 상태                       |

구현 기준:

*   activeFriendId 가 없으면 상세 채팅과 추천 액션은 비활성 또는 안내 상태로 둔다.
*   selectedMessages 는 activeFriendId 변경 시 다시 불러온다.
*   recommendationResult 는 activeFriendId 나 meetingMode 변경 시 필요한 범위에서 초기화한다.
*   category 가 null 이면 추천 버튼을 비활성화한다.
*   나중에 만나기 모드에서는 departureInput 과 friendDepartureInput 이 모두 유효해야 추천 요청을 보낸다.

## 9\. JWT 인증 기술 설계

파일:

*   lib/auth/session.ts

필수 함수:

*   signAuthToken(payload)
*   verifyAuthToken(token)
*   setAuthCookie(response, payload)
*   clearAuthCookie(response)
*   getAuthFromCookies()
*   requireAuthOrThrow()

JWT payload 기준:

```
type AuthPayload = {
    userId: string;
    nickname: string;
    iat: number;
    exp: number;
};
```

구현 기준:

*   쿠키 이름은 meetpoint\_auth 로 고정한다.
*   JWT\_SECRET 기반 JWT 서명 또는 동등한 안전한 서명 방식을 사용한다.
*   쿠키 속성은 httpOnly, sameSite=lax, path=/ 를 기본으로 하고 운영 환경에서만 secure=true 로 설정한다.
*   쿠키 만료 시간은 7일 기준으로 고정하며, exp 와 쿠키 maxAge 를 동일하게 유지한다.
*   exp 만료 검증 실패 시 쿠키를 즉시 삭제한다.
*   브라우저에서는 auth payload를 직접 해석하지 않는다.
*   페이지 보호와 API 보호는 같은 검증 함수 하나를 공유한다.
*   currentUserId 는 검증된 JWT에서만 주입하며 요청 본문이나 query 에서 사용자 ID를 받지 않는다.

### 9.1 인증 함수별 계약

| 함수               | 입력                      | 출력                  | 실패 조건                               |
| ------------------ | ------------------------- | --------------------- | --------------------------------------- |
| signAuthToken      | AuthPayload               | string                | JWT\_SECRET 누락, payload 필수값 누락   |
| verifyAuthToken    | token string              | AuthPayload 또는 null | 서명 불일치, 만료, 형식 오류            |
| setAuthCookie      | NextResponse, AuthPayload | NextResponse          | response 객체 없음, payload 오류        |
| clearAuthCookie    | NextResponse              | NextResponse          | response 객체 없음                      |
| getAuthFromCookies | 없음                      | AuthPayload 또는 null | 쿠키 없음, 토큰 검증 실패               |
| requireAuthOrThrow | 없음                      | AuthPayload           | JWT 없음 또는 만료 시 UNAUTHORIZED 예외 |

### 9.2 인증 함수 예시

#### signAuthToken 예시

입력 예시:

```
{
    userId: "uuid",
    nickname: "민수",
    iat: 1770000000,
    exp: 1770604800
}
```

출력 예시:

```
"signed.jwt.token"
```

실패 조건 예시:

*   JWT\_SECRET 이 없으면 서버 시작 또는 호출 시점에 INTERNAL\_ERROR 로 처리한다.
*   userId 또는 exp 같은 필수 필드가 비어 있으면 토큰 발급을 중단한다.

#### verifyAuthToken 예시

```

```

*   서명이 다르면 null 또는 UNAUTHORIZED 처리 기준으로 반환한다.

*   invalid input은 400 INVALID\_INPUT으로 통일한다.

실제 테이블 생성 시 반영해야 하는 최소 규칙은 다음과 같다.

| 테이블               | 필수 제약                                                                                                                            | 권장 인덱스                                                                                | 구현 메모                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| users                | unique(nickname\_normalized)                                                                                                         | index(location\_updated\_at), index(nickname\_normalized)                                  | nickname은 표시용, nickname\_normalized는 비교용으로 분리  |
| friends              | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id, unique(user\_id, friend\_id), check(user\_id \<> friend\_id) | index(user\_id), index(friend\_id)                                                         | 친구 추가 시 양방향 row 2건을 함께 upsert                  |
| messages             | foreign key(sender\_id) -> users.id, foreign key(receiver\_id) -> users.id                                                           | index(sender\_id, receiver\_id, created\_at), index(receiver\_id, sender\_id, created\_at) | 조회는 두 사용자 간 메시지를 created\_at 오름차순으로 반환 |
| departure\_locations | foreign key(user\_id) -> users.id, check(location\_kind in ('recent', 'preset')), check(label not blank)                             | index(user\_id, last\_used\_at desc), index(user\_id, location\_kind)                      | users 현재 위치와 분리해 저장된 출발 위치를 관리           |
| recommendations      | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id                                                               | index(user\_id, friend\_id, created\_at desc)                                              | MVP 1차에서는 생성하지 않고 후속 확장 시 추가              |

### 11.4 트랜잭션 및 동시성 기준

*   users 생성은 nickname\_normalized unique 제약을 전제로 구현하고, 동시 생성 충돌 시 기존 row 재조회로 수습한다.
*   친구 추가는 양방향 row 2건을 하나의 트랜잭션 또는 동등한 원자적 upsert 흐름으로 처리한다.
*   한쪽 관계만 남은 비정상 상태를 발견하면 누락된 반대 방향 row를 같은 요청 안에서 복구한다.
*   메시지 저장은 단건 insert 로 처리하되, 조회 정렬은 created\_at asc, id asc 로 고정한다.
*   나중에 만나기 모드의 출발 위치는 추천 요청 payload와 저장된 출발 위치 선택값을 함께 고려한다.
*   저장된 출발 위치 재사용은 departure\_locations 테이블을 기준으로 처리하고, users 의 현재 위치 공유값과 혼용하지 않는다.

*   MVP 1차에서는 query 를 단순화하기 위해 after 단일값을 유지한다.
*   같은 시각 메시지 경계에서 중복 표시가 생기지 않도록 클라이언트는 message.id 기준으로 병합한다.

3.  Kakao Local API 후보 조회
4.  반경 확장 필요 여부 판단
5.  반경별 후보 병합 또는 최종 후보 선택
6.  각 후보에 대해 distanceA, distanceB 계산
7.  averageDistance 계산
8.  distanceGap 계산
9.  categoryPenalty 계산
10.  vitalityPenalty 계산
11.  score = averageDistance + distanceGap + categoryPenalty + vitalityPenalty
12.  score, distanceGap, averageDistance, name 순으로 정렬
13.  후보가 0건이면 빈 배열을 정상 응답으로 반환한다.
14.  상위 3개만 반환

distance.ts 는 순수 함수만 포함하도록 유지한다.

## 15\. 오류 처리 및 사용자 안내 설계

프론트엔드는 error.code 를 기준으로 UI 문구를 분기한다.

| error.code          | 프론트엔드 안내                                                    |
| ------------------- | ------------------------------------------------------------------ |
| INVALID\_INPUT      | 입력값을 다시 확인해 주세요.                                       |
| UNAUTHORIZED        | 세션이 만료되었습니다. 다시 시작해 주세요.                         |
| FORBIDDEN\_RELATION | 친구 관계를 확인한 뒤 다시 시도해 주세요.                          |
| FRIEND\_NOT\_FOUND  | 해당 닉네임의 사용자를 찾을 수 없습니다.                           |
| LOCATION\_REQUIRED  | 지금 만나기에서는 두 사람 모두 위치를 공유해야 추천할 수 있습니다. |
| DEPARTURE\_REQUIRED | 나중에 만나기에서는 두 사람의 출발 위치가 모두 필요합니다.         |
| KAKAO\_API\_FAILED  | 장소 정보를 가져오지 못했습니다. 잠시 후 다시 시도해 주세요.       |
| INTERNAL\_ERROR     | 요청을 처리하지 못했습니다. 잠시 후 다시 시도해 주세요.            |

구현 기준:

*   서버 로그에는 내부 오류 원인을 남긴다.
*   추천 후보가 0건인 경우는 오류가 아니라 ok: true 와 빈 places 배열로 응답한다.
*   Route Handler 는 requestId 또는 동등한 추적 값을 로그에 포함해 장애 분석 단위를 남긴다.
*   사용자에게는 시스템 내부 구현 세부 정보나 비밀값을 노출하지 않는다.

### 15.1 오류 처리 계약

| 구분                | 서버 처리                            | 프론트엔드 처리                        |
| ------------------- | ------------------------------------ | -------------------------------------- |
| INVALID\_INPUT      | 400과 error.code 반환                | 입력 필드 아래 검증 문구 표시          |
| UNAUTHORIZED        | 401과 error.code 반환, JWT 쿠키 정리 | 로그인 화면 이동 또는 재로그인 유도    |
| FORBIDDEN\_RELATION | 403과 error.code 반환                | 채팅, 추천 요청 차단 후 안내 문구 표시 |
| FRIEND\_NOT\_FOUND  | 404와 error.code 반환                | 친구 추가 입력창 아래 안내 문구 표시   |
| LOCATION\_REQUIRED  | 409와 error.code 반환                | 추천 버튼 근처에 위치 공유 안내 표시   |
| DEPARTURE\_REQUIRED | 409와 error.code 반환                | 출발 위치 입력 영역 근처에 안내 표시   |
| KAKAO\_API\_FAILED  | 502와 error.code 반환                | 재시도 버튼과 임시 오류 안내 표시      |
| INTERNAL\_ERROR     | 500과 error.code 반환                | 공통 에러 영역에 일반 안내 문구 표시   |

### 15.2 로그 및 추적 기준

*   모든 Route Handler 는 requestId, route path, currentUserId 존재 여부, error.code 를 함께 기록한다.
*   content 원문, 세션 토큰 원문, secret 값은 로그에 남기지 않는다.
*   외부 API 실패 시 응답 전문 전체를 남기기보다 status code 와 핵심 오류 메시지만 기록한다.

오류 응답 예시:

```
{ "ok": false, "error": { "code": "LOCATION_REQUIRED", "message": "두 사람 모두 위치를 공유해야 추천할 수 있습니다." } }
```

## 18\. 개발 완료 기준

다음 조건이 충족되면 MVP 1차 기술 구현이 완료된 것으로 본다.

*   /, /login, /signup, /friends, /chat 페이지가 정상 동작한다.
*   모든 보호 API가 JWT 쿠키로 현재 사용자를 식별한다.
*   친구 추가 시 양방향 관계가 보장된다.
*   메시지 조회가 최신 50개 초기 로드와 polling 추가 조회를 지원한다.
*   위치 저장과 위치 시각 표시가 동작한다.
*   나중에 만나기 모드에서 출발 위치 검색과 입력 검증이 동작한다.
*   추천 API가 중심점 계산, 반경 확장 후보 조회, 거리 계산, 카테고리 패널티, 활성도 패널티, 점수 정렬을 모두 수행한다.
*   추천 후보 0건은 오류가 아니라 정상 빈 결과로 처리된다.
*   브라우저에서 Supabase 직접 쓰기 요청을 하지 않는다.
*   DB 제약과 인덱스가 문서 기준대로 반영된다.
*   운영 환경에서 비밀키가 브라우저에 노출되지 않는다.
*   운영 환경에서 secure 쿠키와 fallback 비활성화가 적용된다.

## 19\. 결론

MeetPoint의 기술 설계는 구조 설계 문서에서 정의한 책임 분리를 실제 파일, 함수, Route Handler 단위로 구체화한 구현 기준이다.

본 문서는 MVP 1차 구현에서 필요한 최소 기술 결정을 고정하며, 이후 개발자는 이 문서를 기준으로 폴더 생성, API 구현, UI 통합, 추천 로직 구현을 순차적으로 진행한다.
