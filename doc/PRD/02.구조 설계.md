# MeetPoint 구조 설계

## 1\. 문서 목적

이 문서는 MeetPoint 기획안을 실제 구현 구조로 연결하기 위한 구조 설계 문서이다.

기획 문서에서 정의한 기능을 화면 구조, 시스템 구조, 데이터 흐름, 역할 분리 기준으로 구체화하여 개발 기준을 명확히 하는 것을 목표로 한다.

---

## 2\. 구조 설계 개요

MeetPoint는 Next.js 16 기반 풀스택 웹 서비스로 구성한다.

구조 설계의 핵심 방향은 다음과 같다.

*   프론트엔드와 백엔드를 하나의 Next.js 프로젝트 안에서 운영한다.
*   지도 렌더링과 사용자 입력은 클라이언트에서 처리한다.
*   데이터 저장, 추천 계산, 외부 API 호출은 서버에서 처리한다.
*   사용자 흐름은 로그인 화면, 메인 화면, 추천 결과 흐름으로 단순하게 유지한다.

### 2.1 핵심 기술 스택

| 영역          | 기술                  | 선택 이유                                                                                                  |
| ------------- | --------------------- | ---------------------------------------------------------------------------------------------------------- |
| Frontend      | Next.js               | React 기반 UI 구현과 배포가 쉬움                                                                           |
| Styling       | Tailwind CSS          | 짧은 기간 안에 일관된 UI 구성 가능                                                                         |
| Backend       | Next.js Route Handler | 별도 서버 없이 API 구현 가능                                                                               |
| Database      | Supabase              | PostgreSQL 기반 DB를 팀원과 함께 사용 가능                                                                 |
| Map           | Kakao Map API         | 국내 지도와 장소 검색에 적합하며, 내 위치, 친구 위치, 중심점, 추천 장소를 지도에 표시할 수 있음            |
| Deployment    | Vercel                | Next.js 배포에 간단함                                                                                      |
| Collaboration | GitHub + Jira         | GitHub로 코드와 브랜치 이력을 관리하고, Jira로 작업을 Epic, Story, Task, Bug 단위로 관리할 수 있음         |
| Branch        | main / feature / docs | 작업지침서 기준과 동일하게 기능 개발과 문서 작업 흐름을 분리하고, main을 최종 통합 기준으로 유지할 수 있음 |

## 3\. 전체 시스템 구조

### 3.1 상위 구성 요소

MeetPoint는 다음 요소로 구성된다.

*   사용자 브라우저
*   Next.js 16 프론트엔드
*   Next.js 16 서버 Route Handler
*   Supabase 데이터베이스
*   Kakao Map API
*   Kakao Local API

### 3.2 역할 분리

*   브라우저: 화면 렌더링, 입력 처리, 위치 권한 요청, 지도 표시
*   Next.js 서버: 사용자 식별, 데이터 저장/조회, 추천 계산, 외부 API 호출
*   Supabase: 사용자, 친구, 메시지, 위치 데이터 저장
*   Kakao Map API: 지도와 마커 시각화
*   Kakao Local API: 추천 후보 장소 검색

### 3.3 구성 요소 및 역할 요약

| 구성 요소             | 역할                                                             |
| --------------------- | ---------------------------------------------------------------- |
| Frontend              | 사용자가 보는 화면 구성, 지도 표시, 마커 표시, 버튼 클릭 처리    |
| Next.js Route Handler | 사용자 식별, 추천 요청 처리, DB 조회, 카카오 API 호출, 점수 계산 |
| Supabase DB           | 사용자, 친구, 메시지, 위치 정보 저장                             |
| Kakao Map API         | 지도 화면 표시, 마커 시각화                                      |
| Kakao Local API       | 중심점 주변 장소 후보 제공                                       |
| 자체 추천 로직        | 중심점 계산, 거리 계산, 추천 점수 계산, 순위 정렬                |

## 4\. 화면 구조 설계

### 4.1 시작 화면 구조

시작 화면은 서비스 진입과 인증을 담당한다.

전체 화면은 상단 글로벌 헤더와 중앙 인증 카드 영역으로 구성한다.

#### 상단 글로벌 헤더

*   로고 영역
*   우측 안내 문구 또는 현재 사용자 표시 영역

MVP에서는 별도 상단 내비게이션 메뉴와 추가 액션 버튼은 두지 않는다.

#### 중앙 인증 카드

*   서비스 환영 문구
*   닉네임 입력 필드
*   비밀번호 입력 필드
*   회원가입 버튼
*   로그인 버튼

회원가입 또는 로그인 성공 시 서버는 JWT를 발급하고, 사용자 식별 정보를 httpOnly 쿠키에 저장한다.

### 4.2 메인 화면 구조

메인 화면은 상단 글로벌 헤더와 본문 대시보드 영역으로 구성한다.

#### 상단 글로벌 헤더

*   로고 영역
*   현재 사용자 닉네임 표시 영역

헤더는 시작 화면과 메인 화면에서 공통으로 사용하는 최소 구조로 설계하며, MVP에서는 로고와 현재 사용자 표시 외 별도 메뉴는 두지 않는다.

#### 본문 대시보드 영역

본문은 좌측 사이드 패널과 우측 카드형 콘텐츠 영역으로 구성한다.

#### 좌측 패널

*   친구 목록 제목
*   친구 목록 필터 입력창
*   친구 목록

좌측 패널은 친구 선택의 진입점 역할을 하며, 각 친구 항목은 카드형 리스트로 표시한다. 여기의 입력창은 이미 추가된 친구 목록을 필터링하는 용도이며, 신규 친구 추가는 우측의 친구 추가 카드에서만 처리한다.

#### 우측 콘텐츠 영역

*   친구 추가 카드
*   지도 확인 카드
*   선택 상태에 따른 채팅 또는 추천 상세 영역

상세 영역에는 선택한 친구 정보와 함께 위치 상태 문구를 포함한다.

예시 문구:

*   마지막 위치 공유: 5분 전

초기 메인 화면은 카드형 대시보드 중심으로 구성하고, 친구 선택 이후 상세 기능 영역으로 자연스럽게 확장되도록 설계한다.

상태별 렌더링 기준:

*   초기 상태: 우측 영역에 친구 추가 카드와 지도 확인 카드만 표시한다.
*   친구 선택 상태: 선택한 친구 정보, 위치 상태 문구, 채팅 리스트, 채팅 입력, 위치 공유 버튼, 추천 버튼을 표시한다.
*   추천 완료 상태: 친구 선택 상태 UI를 유지한 채 추천 결과 카드와 지도 마커를 함께 표시한다.

#### 친구 추가 카드

*   친구 추가 제목
*   설명 문구
*   닉네임 입력 필드
*   검색 또는 추가 버튼

#### 지도 확인 카드

*   지도 기반 기능 소개 문구
*   지도 보기 버튼
*   지도 미리보기 이미지 또는 썸네일 영역

### 4.3 추천 결과 구조

추천 결과는 메인 화면 내부에서 함께 표시한다.

구성 요소는 다음과 같다.

*   중심점 안내 문구
*   추천 장소 3개 카드
*   장소별 거리 또는 간단한 설명
*   지도 위 추천 장소 마커

## 5\. 사용자 흐름 구조

### 5.1 전체 사용자 흐름

1.  사용자가 닉네임과 비밀번호로 회원가입 또는 로그인한다.
2.  서버는 JWT를 발급하고 httpOnly 쿠키를 설정한다.
3.  메인 화면에서 친구를 추가하거나 선택한다.
4.  친구 선택 시 채팅 데이터와 친구 정보가 표시된다.
5.  위치 공유 버튼 클릭 시 사용자 위치가 저장된다.
6.  지도는 사용자와 친구 위치를 표시한다.
7.  추천 버튼 클릭 시 서버가 추천 결과를 계산한다.
8.  지도와 추천 카드 영역에 결과를 표시한다.

### 5.2 채팅 흐름

1.  친구 선택
2.  해당 친구와의 최신 메시지 50개 조회
3.  메시지 입력 및 저장
4.  저장 직후 메시지 재조회
5.  5초 주기 폴링으로 마지막으로 받은 메시지 이후 데이터만 추가 조회

메시지 조회 범위 기준:

*   초기 진입 시 최신 메시지 50개를 created\_at 오름차순으로 반환한다.
*   polling 요청은 마지막으로 받은 메시지의 created\_at 이후 데이터만 조회한다.
*   MVP에서는 이전 메시지 더보기 기능은 제외하고, 최신 대화 유지에만 집중한다.

### 5.3 위치 및 추천 흐름

1.  위치 공유 버튼 클릭
2.  Geolocation API로 좌표 획득
3.  서버에 위치 저장 요청
4.  사용자와 친구의 마지막 공유 위치를 기준으로 지도 정보를 갱신
5.  마지막 위치 공유 시각 문구 갱신
6.  추천 버튼 클릭
7.  서버에서 친구 위치 포함 조회
8.  중심점 계산 및 장소 후보 검색
9.  점수 계산 후 상위 3개 반환

새로고침이나 친구 선택은 친구의 현재 GPS를 새로 가져오는 동작이 아니라, 친구가 마지막으로 공유한 위치를 DB 에서 다시 불러오는 흐름으로 이해한다.

### 5.4 예외 흐름 및 사용자 안내 기준

MVP에서 우선 처리해야 하는 예외 상황은 다음과 같다.

| 상황                          | 프론트엔드 처리                                             | 비고                                              |
| ----------------------------- | ----------------------------------------------------------- | ------------------------------------------------- |
| 위치 권한 거부                | 위치 공유 버튼 아래에 권한 필요 문구 표시, 재시도 버튼 노출 | 기존에 저장된 마지막 위치가 있으면 지도 표시 유지 |
| 사용자 또는 친구 위치 미공유  | 추천 버튼 비활성화 또는 클릭 시 안내 문구 표시              | 문구 예시: 위치 공유 후 추천할 수 있습니다.       |
| 추천 결과 0건                 | 빈 결과 카드와 재시도 버튼 표시                             | 오류가 아니라 정상 응답으로 처리                  |
| 친구 목록 또는 채팅 조회 실패 | 기존 화면 상태를 유지하고 재시도 버튼 표시                  | 선택 중인 친구 정보는 유지                        |
| 세션 만료 또는 쿠키 유실      | 로그인 화면으로 유도하고 재로그인 요청                      | 보호 API는 401 응답                               |

## 7\. 서버 구조 설계

### 7.1 서버 책임

서버는 다음 역할을 담당한다.

*   회원가입 및 로그인 처리
*   JWT 기반 사용자 식별
*   친구 추가 처리
*   친구 목록 조회
*   메시지 저장 및 조회
*   위치 저장 및 조회
*   추천 요청 처리
*   Kakao Local API 호출
*   거리 계산 및 추천 점수 계산

### 7.2 서버 인터페이스 방향

MVP 기준에서 필요한 주요 서버 기능은 다음과 같다.

*   회원가입 처리
*   로그인 처리
*   로그아웃 처리
*   친구 추가 처리
*   친구 목록 조회
*   메시지 저장
*   메시지 조회
*   위치 저장
*   추천 결과 조회

MVP 구현은 아래 7.3 API 계약 초안을 기준으로 진행하고, 경로 이름 변경이 필요한 경우 프론트엔드와 서버 구현을 함께 수정하는 것을 원칙으로 한다.

### 7.3 MVP API 계약 초안

모든 API 응답은 JSON 기준으로 통일한다. 보호 API는 사용자 ID를 요청 본문에서 받지 않고, 검증된 JWT 쿠키에서 현재 사용자를 식별한다.

| 기능           | Method | Path                                                        | 요청 값                       | 성공 응답 예시                                                                            |
| -------------- | ------ | ----------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------- |
| 회원가입 처리  | POST   | /api/auth/signup                                            | { nickname, password }        | { ok: true, data: { user: { id, nickname } } }                                            |
| 로그인 처리    | POST   | /api/auth/login                                             | { nickname, password }        | { ok: true, data: { user: { id, nickname, lat, lng, locationUpdatedAt } } }               |
| 로그아웃 처리  | POST   | /api/auth/logout                                            | 없음                          | { ok: true, data: { cleared: true } }                                                     |
| 친구 추가      | POST   | /api/friends                                                | { friendNickname }            | { ok: true, data: { relationId, friend: { id, nickname, lat, lng, locationUpdatedAt } } } |
| 친구 목록 조회 | GET    | /api/friends                                                | 없음                          | { ok: true, data: { friends: \[...\] } }                                                  |
| 메시지 저장    | POST   | /api/messages                                               | { friendId, content }         | { ok: true, data: { message: { id, senderId, receiverId, content, createdAt } } }         |
| 메시지 조회    | GET    | /api/messages?friendId={id}&after={isoDatetime?}&limit={n?} | query: friendId, after, limit | { ok: true, data: { messages: \[...\], pollingIntervalSec: 5, limit: 50 } }               |
| 위치 저장      | POST   | /api/location                                               | { lat, lng }                  | { ok: true, data: { location: { lat, lng, locationUpdatedAt } } }                         |
| 추천 결과 조회 | GET    | /api/recommendations?friendId={id}                          | query: friendId               | { ok: true, data: { midpoint: { lat, lng }, places: \[...\] } }                           |

요청 검증 기준:

*   nickname은 trim 후 앞뒤 공백을 제거하고, 내부 연속 공백은 한 칸으로 정규화한다.
*   nickname은 정규화 후 2자 이상 12자 이하 문자열로 제한한다.
*   nickname은 한글, 영문, 숫자, 공백만 허용하고 특수문자는 허용하지 않는다.
*   nickname 비교와 중복 검사는 nickname\_normalized 기준으로 수행하며, 영문은 소문자로 정규화한다.
*   password는 8자 이상 20자 이하 문자열로 제한한다.
*   friendNickname은 정규화 후 자기 자신의 nickname\_normalized와 같을 수 없다.
*   content는 공백 제거 후 1자 이상 500자 이하로 제한한다.
*   lat는 -90 이상 90 이하, lng는 -180 이상 180 이하 범위만 허용한다.
*   friendId는 UUID 형식 문자열만 허용한다.
*   limit는 생략 시 50을 사용하고 최대 100까지만 허용한다.
*   after는 ISO datetime 문자열만 허용하며, polling 요청에서만 선택적으로 사용한다.

친구 관계 생성 규칙:

*   친구 추가 성공 시 서버는 user\_id -> friend\_id, friend\_id -> user\_id 관계 row 2건을 하나의 트랜잭션으로 upsert 한다.
*   이미 양방향 관계가 모두 존재하면 중복 생성하지 않고 기존 관계를 그대로 사용한다.
*   한쪽 관계만 남아 있는 비정상 상태가 발견되면 누락된 반대 방향 row를 함께 복구한다.

### 7.4 인증 및 쿠키 규칙

MVP에서는 닉네임 + 비밀번호 기반 회원가입/로그인을 사용하고, 인증 토큰은 JWT를 httpOnly 쿠키로 관리한다.

*   쿠키 이름은 meetpoint\_auth로 통일한다.
*   JWT payload는 userId, nickname, iat, exp 값을 포함한다.
*   JWT는 서버 전용 비밀키로 서명한다.
*   쿠키는 httpOnly, sameSite=lax, path=/ 기준으로 설정하고, 운영 환경에서는 secure=true로 설정한다.
*   쿠키 만료 시간은 7일로 설정한다.
*   POST /api/auth/login 성공 시 서버가 JWT 쿠키를 발급한다.
*   POST /api/auth/logout 성공 시 서버가 JWT 쿠키를 삭제한다.
*   보호 API는 JWT 쿠키를 검증한 뒤 currentUserId를 서버 내부 컨텍스트에 주입한다.
*   서명이 유효하지 않거나 만료된 쿠키는 즉시 삭제하고 401을 반환한다.
*   JWT 비밀키는 JWT\_SECRET 환경 변수로 관리하며 브라우저에 노출하지 않는다.
*   닉네임 찾기와 비밀번호 재설정은 MVP 범위에서 제외한다.

### 7.4.1 필수 환경 변수 계약

실제 구현 시 사용하는 주요 환경 변수는 다음과 같이 고정한다.

| 변수명                             | 사용 위치        | 용도                      | 공개 여부 |
| ---------------------------------- | ---------------- | ------------------------- | --------- |
| NEXT\_PUBLIC\_SUPABASE\_URL        | 클라이언트, 서버 | Supabase 프로젝트 URL     | 공개 가능 |

| SUPABASE\_SERVICE\_ROLE\_KEY       | 서버 전용        | 관리자 권한 DB 작업       | 서버 전용 |

*   환경 변수 이름은 팀 공통으로 고정하며 임의 별칭을 만들지 않는다.

### 7.5 공통 응답 및 오류 처리 규칙

## 8\. 데이터 구조 설계

### 8.0 데이터베이스 요약

| 테이블          | 주요 컬럼                                                                                                                 | 저장 내용                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| users           | id, nickname, nickname\_normalized, password\_hash, lat, lng, location\_updated\_at, created\_at                          | 사용자 정보, 인증 정보와 마지막 공유 위치        |
| friends         | id, user\_id, friend\_id, created\_at                                                                                     | 사용자 간 친구 관계                              |
| messages        | id, sender\_id, receiver\_id, content, created\_at                                                                        | 댓글형 채팅 메시지                               |
| recommendations | id, user\_id, friend\_id, midpoint\_lat, midpoint\_lng, place\_name, place\_lat, place\_lng, category, score, created\_at | 추천 결과 기록용 확장 데이터, MVP 필수 생성 아님 |

MVP 기본 흐름에서는 추천 결과를 요청 시 계산 후 바로 반환하고, recommendations 테이블은 후속 단계에서 추천 이력 기능이 필요할 때만 추가한다.

### 8.1 users

역할:

*   사용자 기본 정보 저장
*   비밀번호 해시 저장
*   현재 위치 및 위치 갱신 시각 저장
*   회원가입과 로그인 처리의 기준 테이블 역할 수행
*   위치 상태 문구 표시를 위한 기준 데이터 제공

핵심 필드:

*   id
*   nickname
*   nickname\_normalized
*   password\_hash
*   lat
*   lng
*   location\_updated\_at
*   created\_at

컬럼 의미:

*   id - 사용자 고유 ID
*   nickname - 사용자가 화면에서 보는 표시용 닉네임
*   nickname\_normalized - 중복 비교와 검색에 사용하는 정규화 닉네임
*   password\_hash - 비밀번호 해시 저장 값
*   lat - 사용자가 마지막으로 공유한 위치의 위도
*   lng - 사용자가 마지막으로 공유한 위치의 경도
*   location\_updated\_at - 사용자가 위치 공유 버튼을 마지막으로 누른 시간
*   created\_at - 사용자가 처음 생성된 시간

설계 기준:

*   nickname은 표시용 값으로 저장하되, 중복 검사는 nickname\_normalized 기준으로 수행한다.
*   사용자 조회, 친구 검색, 자기 자신 비교는 모두 nickname\_normalized 기준으로 처리한다.
*   초기 진입 사용자를 위해 위치 필드는 null 허용 구조로 둔다.

### 8.2 friends

역할:

*   사용자와 친구의 관계 저장

핵심 필드:

*   id
*   user\_id
*   friend\_id
*   created\_at

컬럼 의미:

*   id - 친구 관계 고유 ID
*   user\_id - 친구를 추가한 사용자 ID
*   friend\_id - 추가된 친구의 사용자 ID
*   created\_at - 친구 관계가 생성된 시간

설계 기준:

*   단순 닉네임 문자열 저장이 아니라 사용자 관계 기반 구조로 설계한다.
*   동일 관계 중복 저장을 방지한다.
*   친구 추가 성공 시 양방향 관계 row 2건을 함께 유지하여 메시지 조회와 추천 조회 권한 기준을 단순하게 맞춘다.

### 8.3 messages

역할:

*   댓글형 채팅 메시지 저장

핵심 필드:

*   id
*   sender\_id
*   receiver\_id
*   content
*   created\_at

컬럼 의미:

*   id - 메시지 고유 ID
*   sender\_id - 메시지를 보낸 사용자 ID
*   receiver\_id - 메시지를 받은 사용자 ID
*   content - 메시지 내용
*   created\_at - 메시지가 작성된 시간

설계 기준:

*   생성 시간 기준으로 정렬 조회한다.
*   실시간 동기화 대신 저장 및 재조회 방식에 맞춘다.

### 8.4 recommendations

역할:

*   향후 추천 결과 저장 확장용 테이블

핵심 필드 예시:

*   id
*   user\_id
*   friend\_id
*   midpoint\_lat
*   midpoint\_lng
*   place\_name
*   place\_lat
*   place\_lng
*   category
*   score
*   created\_at

컬럼 의미:

*   id - 추천 결과 고유 ID
*   user\_id - 장소 추천을 요청한 사용자 ID
*   friend\_id - 함께 만날 친구의 사용자 ID
*   midpoint\_lat - 사용자와 친구 위치를 기준으로 계산한 중심점 위도
*   midpoint\_lng - 사용자와 친구 위치를 기준으로 계산한 중심점 경도
*   place\_name - 추천된 장소 이름
*   place\_lat - 추천된 장소의 위도
*   place\_lng - 추천된 장소의 경도
*   category - 추천 장소의 종류, 예: 카페, 식당, 편의점
*   score - 평균 이동거리와 거리 편차를 반영한 추천 점수
*   created\_at - 추천 결과가 생성된 시간

MVP 기준:

*   기본 흐름은 추천 결과를 요청 시 계산 후 바로 반환하는 방식이다.
*   MVP 1차 구현에서는 recommendations 테이블을 생성하지 않는다.
*   추천 이력 확인 기능이 확정될 때만 후속 마이그레이션으로 추가한다.

### 8.5 MVP DB 구성 방식

MVP 기준 최소 DB는 users, friends, messages 중심으로 구성한다.

| 방식                 | 설명                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------- |
| 기본 MVP DB          | users, friends, messages 테이블만 필수 생성한다.                                             |
| Kakao Local API 사용 | 장소 후보를 실시간으로 가져오므로 places 테이블은 만들지 않는다.                             |
| 임시 데이터 기반 MVP | 개발 및 테스트 환경에서만 서버 내부 fixture 배열 또는 JSON 파일을 보조적으로 사용할 수 있다. |
| 추천 결과 기록       | recommendations 테이블은 MVP 범위에서 제외하고 후속 확장 시 추가한다.                        |

### 8.6 구현 제약, 관계, 인덱스 규칙

실제 테이블 생성 시 반영해야 하는 최소 규칙은 다음과 같다.

| 테이블          | 필수 제약                                                                                                                            | 권장 인덱스                                                                                | 구현 메모                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| users           | unique(nickname\_normalized)                                                                                                         | index(location\_updated\_at), index(nickname\_normalized)                                  | nickname은 표시용, nickname\_normalized는 비교용으로 분리  |
| friends         | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id, unique(user\_id, friend\_id), check(user\_id \<> friend\_id) | index(user\_id), index(friend\_id)                                                         | MVP에서는 친구 추가 시 양방향 row 2건을 함께 upsert        |
| messages        | foreign key(sender\_id) -> users.id, foreign key(receiver\_id) -> users.id                                                           | index(sender\_id, receiver\_id, created\_at), index(receiver\_id, sender\_id, created\_at) | 조회는 두 사용자 간 메시지를 created\_at 오름차순으로 반환 |
| recommendations | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id                                                               | index(user\_id, friend\_id, created\_at desc)                                              | 저장은 선택 기능이며 기본 응답은 즉시 계산 결과 반환       |

추가 구현 원칙:

*   브라우저는 Supabase에 직접 쓰기 요청을 보내지 않고, 모든 DB 접근은 Next.js Route Handler를 통해 수행한다.
*   service role key 또는 DB 비밀값은 서버 환경 변수로만 보관한다.
*   사용자 삭제 기능은 MVP 범위에서 제외하며, 삭제 정책은 후속 단계에서 별도 확정한다.

## 9\. 추천 구조 설계

### 9.1 장소 추천 흐름

사용자가 장소 추천 버튼을 누르면 다음 순서로 동작한다.

1.  프론트엔드에서 추천 버튼 클릭
2.  Next.js Route Handler에 추천 요청
3.  백엔드가 Supabase에서 사용자와 친구의 마지막 공유 위치 조회
4.  두 위치의 중심점 계산
5.  중심점 주변의 카페 또는 식당 후보를 Kakao Local API로 검색
6.  카카오 API가 장소 후보 목록 반환
7.  각 후보 장소와 사용자 A, 사용자 B 사이의 거리 계산
8.  추천 점수 계산
9.  점수가 낮은 순서대로 정렬
10.  상위 3개 장소를 프론트엔드에 전달
11.  프론트엔드가 지도 마커와 추천 장소 카드 표시

### 9.2 중심점 계산

MVP에서는 두 사람의 위도와 경도 평균값으로 중심점을 구한다.

*   중심 위도 = (A 위도 + B 위도) / 2
*   중심 경도 = (A 경도 + B 경도) / 2

예시:

| 사람     | 위도   | 경도    |
| -------- | ------ | ------- |
| 사용자 A | 37.500 | 127.030 |
| 사용자 B | 37.560 | 127.010 |

중심점:

*   중심 위도 = (37.500 + 37.560) / 2 = 37.530
*   중심 경도 = (127.030 + 127.010) / 2 = 127.020

이 중심점 주변에서 카페나 식당 후보를 검색한다.

### 9.3 거리 계산과 Haversine 공식

Haversine 공식은 두 좌표 사이의 거리를 계산하는 공식이다.

MeetPoint에서는 다음 거리 계산에 사용한다.

*   사용자 A와 후보 장소 사이 거리
*   사용자 B와 후보 장소 사이 거리

각 장소마다 다음 값을 계산한다.

*   distanceA = 사용자 A와 장소 사이 거리
*   distanceB = 사용자 B와 장소 사이 거리

이 값을 기반으로 평균 이동거리와 거리 편차를 계산한다.

### 9.4 추천 점수식

좋은 장소는 다음 두 조건을 만족해야 한다.

1.  전체적으로 너무 멀지 않아야 한다.
2.  한 사람에게만 불리하지 않아야 한다.

점수식:

```
score = 평균 이동거리 + 거리 편차 × 가중치
```

MVP 기준 가중치는 1로 설정하여 평균 이동거리와 공평성을 동일한 비중으로 반영한다.

| 항목          | 의미                               |
| ------------- | ---------------------------------- |
| 평균 이동거리 | 전체적으로 가까운 장소인지 판단    |
| 거리 편차     | 두 사람에게 공평한 장소인지 판단   |
| 가중치        | 공평성을 얼마나 중요하게 볼지 조절 |
| score         | 낮을수록 좋은 장소                 |

계산식은 다음과 같다.

```
평균 이동거리 = (A 거리 + B 거리) / 2
거리 편차 = |A 거리 - B 거리|
```

### 9.5 가중치 설명

가중치는 거리 편차의 중요도를 조절하는 값이다.

가중치가 작을 때:

```
score = 평균 이동거리 + 거리 편차 × 0.3
```

전체적으로 가까운 장소가 더 유리하다.

| 장소   | A 거리 | B 거리 | 평균거리 | 거리차 | 점수 |
| ------ | ------ | ------ | -------- | ------ | ---- |
| 카페 A | 1km    | 4km    | 2.5km    | 3km    | 3.4  |
| 카페 B | 4km    | 4km    | 4km      | 0km    | 4    |

이 경우 카페 A가 선택된다.

가중치가 클 때:

```
score = 평균 이동거리 + 거리 편차 × 1.5
```

두 사람에게 더 공평한 장소가 유리하다.

| 장소   | A 거리 | B 거리 | 평균거리 | 거리차 | 점수 |
| ------ | ------ | ------ | -------- | ------ | ---- |
| 카페 A | 1km    | 4km    | 2.5km    | 3km    | 7    |
| 카페 B | 4km    | 4km    | 4km      | 0km    | 4    |

이 경우 카페 B가 선택된다.

### 9.6 MeetPoint MVP의 선택

카페 B가 선택되는 이유는 한 사람에게만 유리한 장소보다 두 사람 모두에게 더 공평한 장소를 우선하기 때문이다.

MeetPoint는 공정한 중간 장소 추천이 목표이므로 가중치를 너무 작게 두지 않는다.

MVP에서는 다음과 같이 설정한다.

*   가중치 = 1

즉, 점수식은 다음과 같다.

```
score = 평균 이동거리 + 거리 편차 × 1
```

### 9.7 예시 계산

| 장소   | A 거리 | B 거리 | 평균거리 | 거리차 | score |
| ------ | ------ | ------ | -------- | ------ | ----- |
| 카페 A | 1km    | 5km    | 3km      | 4km    | 7     |
| 카페 B | 3km    | 3km    | 3km      | 0km    | 3     |
| 식당 C | 2km    | 4km    | 3km      | 2km    | 5     |

추천 순위:

1.  카페 B: 평균거리 3km, 거리차 0km, score 3
2.  식당 C: 평균거리 3km, 거리차 2km, score 5
3.  카페 A: 평균거리 3km, 거리차 4km, score 7

세 장소의 평균거리는 모두 3km로 같지만, 카페 B가 가장 공평하기 때문에 1순위가 된다.

### 9.8 후보 장소 확보 전략

*   1차 기준은 Kakao Local API를 통한 실시간 후보 조회이다.
*   외부 API 호출이 제한되거나 테스트 환경이 불안정한 경우를 대비해 개발 및 테스트 환경에서만 임시 후보 장소 데이터 구조를 보조 전략으로 둔다.
*   보조 전략은 서버 내부 fixture 데이터 fallback 용도로만 사용한다.
*   운영 환경에서는 Kakao Local API 응답만 사용하고, 임시 데이터 fallback은 활성화하지 않는다.

### 9.9 추천 파라미터 및 동점 처리 기준

MVP 구현 시 추천 결과를 일관되게 만들기 위한 계산 기준은 다음과 같다.

| 항목           | 값                | 적용 방식                                             |
| -------------- | ----------------- | ----------------------------------------------------- |
| 추천 카테고리  | 카페, 식당        | Kakao Local API 검색 시 1차 대상 카테고리로 사용      |
| 검색 반경      | 중심점 기준 2km   | 2km 안에서 후보를 우선 조회                           |
| 최대 후보 수   | 15개              | 응답 후보가 많으면 중심점과 가까운 순으로 15개만 사용 |
| 최종 노출 개수 | 3개               | score 오름차순 기준 상위 3개 반환                     |
| 거리 계산 단위 | 내부 계산은 meter | 화면 표시는 1000m 이상이면 km 한 자리 소수로 변환     |
| 가중치         | 1                 | 평균 이동거리와 거리 편차를 동일 비중으로 반영        |

동점 처리 규칙:

1.  score가 낮은 순서
2.  거리 편차가 낮은 순서
3.  평균 이동거리가 낮은 순서
4.  place\_name 가나다순

추가 기준:

*   사용자와 친구 둘 중 하나라도 위치가 없으면 계산하지 않고 409 LOCATION\_REQUIRED를 반환한다.
*   위치 갱신 시각이 오래되었더라도 MVP에서는 마지막 공유 위치를 그대로 사용한다.
*   추천 결과가 0건이면 오류가 아니라 빈 결과로 처리한다.

## 10\. 외부 서비스 연동 구조

### 10.1 카카오 API 역할 구분

카카오 API 는 다음과 같이 역할을 나누어 이해한다.

| 구분            | 사용 위치  | 역할                                             |
| --------------- | ---------- | ------------------------------------------------ |
| Kakao Map API   | 프론트엔드 | 지도 화면 표시, 마커 표시                        |
| Kakao Local API | 백엔드     | 중심점 주변 카페, 식당, 편의점 등 장소 후보 검색 |

카카오 API 가 최종 추천을 직접 결정하는 것은 아니다.

MeetPoint 는 카카오 API 로 장소 후보를 확보한 뒤, 사용자와 후보 장소 간 거리를 계산하고 평균 이동거리와 거리 편차를 반영한 자체 점수식으로 다시 정렬한다.

### 10.2 Kakao Map API

역할:

*   지도 렌더링
*   사용자 위치 마커 표시
*   친구 위치 마커 표시
*   중심점 마커 표시
*   추천 장소 마커 표시

처리 위치:

*   클라이언트

### 10.3 Kakao Local API

역할:

*   중심점 주변 장소 후보 검색

처리 위치:

*   서버 Route Handler

설계 기준:

*   브라우저에서 직접 호출하지 않는다.
*   추천 로직과 함께 서버에서 처리한다.

### 10.4 임시 장소 데이터

역할:

*   외부 API 사용이 어려운 상황에서 추천 후보를 제공하는 보조 데이터 소스

처리 위치:

*   서버 중심

설계 기준:

*   MVP 기본 경로는 아니며, 개발 및 테스트 환경에서만 보조 경로로 허용한다.
*   DB 테이블이 아니라 서버 내부 배열 또는 JSON fixture 파일 구조로 관리한다.
*   데이터 형식은 장소명, 카테고리, 위도, 경도를 포함하는 단순 배열 구조를 사용한다.
*   운영 배포에서는 임시 장소 데이터를 사용하지 않는다.

### 10.5 Supabase

역할:

*   사용자 데이터 저장
*   친구 관계 저장
*   메시지 저장
*   위치 데이터 저장

처리 위치:

*   서버 중심

## 12\. 통합 구조 전략

통합 전략은 다음과 같다.

*   팀원별로 자기 역할에 맞는 기능 구조를 먼저 정리한다.
*   A 팀원이 최종 화면 흐름 기준을 맞추고 통합 화면 구조를 정리한다.
*   팀원 B와 C의 기능은 메인 화면 구조에 연결 가능한 방식으로 설계한다.
*   공통 데이터 구조와 사용자 흐름은 구조 설계 문서를 기준으로 통일한다.

### 12.1 협업 및 지도/브랜치 전략

협업 도구와 기본 기술 선택은 2.1 핵심 기술 스택을 기준으로 통일한다.

운영 원칙은 다음과 같다.

*   지도 기능은 Kakao Map API를 기준으로 통일하여 사용자 위치, 친구 위치, 중심점, 추천 장소 마커 표시 방식을 일관되게 맞춘다.
*   협업 관리는 GitHub와 Jira를 함께 사용하여 코드 변경 이력과 작업 단위를 분리해서 관리한다.
*   브랜치 전략은 `main`, `feature/*`, `docs/*` 기준으로 고정하여 작업지침서와 동일하게 운영한다.
*   기능 병합은 PR 리뷰를 전제로 진행하여 팀원 간 충돌을 줄이고 최종 통합 품질을 관리한다.

## 13\. 개발 착수 기준

다음 조건이 만족되면 구조 설계 기준으로 개발 착수가 가능하다.

*   시작 화면과 메인 화면 구성 요소가 정의되어 있다.
*   사용자 흐름이 단계별로 정리되어 있다.
*   서버와 클라이언트의 책임이 분리되어 있다.
*   핵심 데이터 구조와 추천 처리 흐름이 정리되어 있다.
*   API 계약, 세션 규칙, 공통 오류 응답 기준이 정의되어 있다.
*   닉네임 정규화 규칙과 친구 관계 생성 규칙이 확정되어 있다.
*   환경 변수 이름과 공개 범위가 정의되어 있다.
*   DB 제약 조건과 추천 파라미터가 구현 가능한 수준으로 명시되어 있다.
*   팀원별 구조 책임이 구분되어 있다.

## 14\. 결론

MeetPoint의 구조 설계는 단순한 화면 구성에 그치지 않고, 사용자 흐름, 데이터 흐름, 서버 처리, 추천 계산 구조까지 포함한 일관된 풀스택 구조를 목표로 한다. 본 문서는 기획안에서 정의한 서비스를 실제 구현 가능한 구조로 구체화한 기준 문서이며, 이후 기술 설계 및 구현 단계의 직접적인 기반으로 사용한다.
