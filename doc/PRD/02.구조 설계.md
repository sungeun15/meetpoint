# MeetPoint 구조 설계

## 1\. 문서 목적

이 문서는 MeetPoint 기획안을 실제 구현 구조로 연결하기 위한 구조 설계 문서이다.

기획 문서에서 정의한 기능을 화면 구조, 시스템 구조, 데이터 흐름, 역할 분리 기준으로 구체화하여 개발 기준을 명확히 하는 것을 목표로 한다.

---

## 2\. 구조 설계 개요

MeetPoint는 Next.js 16 기반 UI 우선 웹 서비스로 구성한다.

구조 설계의 핵심 방향은 다음과 같다.

*   App Router 페이지와 화면 단위 컴포넌트로 랜딩, 인증, friends 허브, chat 상세 흐름을 분리한다.
*   현재 구현은 친구 목록, 채팅, 위치 상태, 추천 입력과 결과 표시를 클라이언트 컴포넌트와 로컬 상태 훅 중심으로 연결한다.
*   지도 미리보기, 주소 검색, 핀 지정 같은 위치 입력 보조 기능은 브라우저 SDK와 레이어 UI로 처리한다.
*   인증, 데이터 저장, 서버 추천 계산, 외부 API 집계는 후속 통합 구조로 별도 설계하되 현재 UI 구조를 깨지 않도록 준비한다.

### 2.1 핵심 기술 스택

| 영역              | 기술                                    | 선택 이유                                                                                                  |
| ----------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Frontend          | Next.js 16 + React 19                   | App Router 기반 화면 분리와 클라이언트 컴포넌트 구성에 적합함                                              |
| Styling           | Tailwind CSS                            | 짧은 기간 안에 일관된 UI 구성 가능                                                                         |
| UI State          | React useState/useMemo 기반 custom hook | friends/chat/recommendation UI 상태를 얇게 분리해 관리할 수 있음                                           |
| Map / Location UI | Kakao Maps JS SDK + Daum Postcode       | 지도 미리보기, 주소 검색, 핀 지정 레이어를 현재 UI에 바로 연결할 수 있음                                   |
| Planned Backend   | Next.js Route Handler                   | 후속 인증, 저장, 추천 계산 API를 같은 프로젝트 안에서 확장하기 쉬움                                        |
| Planned Database  | Supabase                                | 후속 사용자, 친구, 메시지, 저장 위치 데이터 저장 구조로 적합함                                             |
| Deployment        | Vercel                                  | Next.js 배포에 간단함                                                                                      |
| Collaboration     | GitHub + Jira                           | GitHub로 코드와 브랜치 이력을 관리하고, Jira로 작업을 Epic, Story, Task, Bug 단위로 관리할 수 있음         |
| Branch            | main / feature / docs                   | 작업지침서 기준과 동일하게 기능 개발과 문서 작업 흐름을 분리하고, main을 최종 통합 기준으로 유지할 수 있음 |

## 3\. 전체 시스템 구조

### 3.1 상위 구성 요소

MeetPoint는 다음 요소로 구성된다.

*   사용자 브라우저
*   Next.js 16 App Router 페이지와 공통 레이아웃
*   화면 단위 클라이언트 컴포넌트와 상태 훅
*   Kakao Maps JS SDK
*   Daum Postcode 및 Kakao geocoder 기반 위치 입력 레이어
*   후속 통합 대상: Next.js 서버 Route Handler
*   후속 통합 대상: Supabase 데이터베이스
*   후속 통합 대상: Kakao Local API

### 3.2 역할 분리

*   브라우저: 화면 렌더링, 입력 처리, 위치 권한 요청, 지도 표시, 주소 검색, 핀 지정, 저장 위치 레이어 표시
*   클라이언트 상태 훅: 친구 선택, 채팅 입력, 위치 상태, 저장 위치 목록, 추천 결과 패널 상태 관리
*   Kakao Maps JS SDK: 지도와 마커 시각화, 좌표 기반 핀 선택 보조
*   Daum Postcode 및 Kakao geocoder: 주소 검색과 주소 확인 보조
*   후속 Next.js 서버: 사용자 식별, 데이터 저장/조회, 추천 계산, 외부 API 호출
*   후속 Supabase: 사용자, 친구, 메시지, 저장 위치 데이터 저장
*   후속 Kakao Local API: 추천 후보 장소 검색

### 3.3 구성 요소 및 역할 요약

| 구성 요소                      | 역할                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------- |
| App Router 페이지              | 랜딩, 인증, friends, chat, 소개 페이지 진입 구조 제공                                         |
| Screen / Panel 컴포넌트        | 화면 레이아웃, 채팅, 위치 상태, 추천 입력, 결과 패널을 사용자에게 표시                        |
| Client State Hook              | friend 선택, message draft, meeting mode, category, saved departure, recommendation 상태 관리 |
| Kakao Maps JS SDK              | 지도 화면 표시, 마커 시각화, 핀 지정 인터랙션                                                 |
| Daum Postcode / Kakao geocoder | 주소 검색과 주소 확인 보조                                                                    |
| 후속 Next.js Route Handler     | 사용자 식별, 추천 요청 처리, DB 조회, 외부 API 호출, 점수 계산                                |
| 후속 Supabase DB               | 사용자, 친구, 메시지, 위치 정보 저장                                                          |
| 후속 Kakao Local API           | 중심점 주변 장소 후보 제공                                                                    |
| 후속 추천 로직                 | 중심점 계산, 거리 계산, 카테고리 패널티, 활성도 패널티, 순위 정렬                             |

## 4\. 화면 구조 설계

### 4.1 랜딩 및 인증 화면 구조

현재 퍼블 기준 public 영역은 랜딩 화면과 인증 화면으로 나뉜다.

#### 랜딩 화면

랜딩 화면은 서비스 첫 인상과 CTA 분기를 담당한다.

구성 요소는 아래와 같다.

*   상단 글로벌 헤더
*   서비스 소개 헤드라인
*   대표 CTA 버튼
*   Features, About 진입 링크
*   인증 전/후 CTA 미리보기 토글
*   대표 일러스트 이미지

글로벌 헤더는 최소 로고만 두는 구조가 아니라, public 내비게이션과 인증 이동 버튼까지 포함할 수 있는 구조로 본다.

#### 인증 화면

인증은 /login 과 /signup 으로 분리한다.

구성 요소는 아래와 같다.

*   중앙 인증 카드
*   닉네임 입력 필드
*   비밀번호 입력 필드
*   회원가입 또는 로그인 액션 버튼
*   오류 문구와 화면 전환 링크

현재 구현 기준으로 인증 화면은 입력 UI와 모드 전환 링크를 제공한다. 성공 후 세션 발급, 보호 라우트 이동, 쿠키 저장 규칙은 후속 인증 연동 단계에서 확정한다.

### 4.2 friends 허브 화면과 chat 상세 화면 구조

현재 보호 화면은 friends 허브 화면과 chat 상세 화면으로 나뉜다.

#### 공통 헤더

*   로고 영역
*   Home, Features, About us 진입 링크
*   Friends, Chat 진입 링크
*   인증 상태 기반 액션 영역

#### friends 허브 화면

friends 화면은 좌측 친구 패널과 우측 허브 콘텐츠 영역으로 구성한다.

좌측 패널:

*   친구 목록 제목
*   친구 목록 필터 입력창
*   친구 목록

우측 허브 콘텐츠 영역:

*   친구 추가 카드
*   기본 안내 또는 소개 카드
*   상세 화면 진입 전 허브 상태 영역

friends 화면은 친구 선택의 진입점 역할을 하며, 각 친구 항목은 chat 상세 화면으로 이동하는 카드형 리스트로 표시한다. 여기의 입력창은 이미 추가된 친구 목록을 필터링하는 용도이며, 신규 친구 추가는 우측의 친구 추가 카드에서 처리한다.

#### chat 상세 화면

chat 화면은 선택한 친구 기준 상세 상호작용을 담당한다.

상세 영역에는 아래를 포함한다.

*   선택한 친구 정보
*   위치 상태 패널
*   채팅 리스트
*   채팅 입력
*   만남 모드 선택 UI
*   위치 공유 버튼
*   출발 위치 입력 방식 선택 UI
*   카테고리 선택 UI
*   추천 버튼
*   추천 결과 패널과 지도 패널
*   저장 위치 제목 입력 레이어
*   주소 검색 레이어 및 핀 지정 레이어

예시 문구:

*   마지막 위치 공유: 5분 전

상태별 렌더링 기준:

*   friends 기본 상태: 친구 목록과 친구 추가 카드 중심으로 표시한다.
*   chat 기본 상태: 선택한 친구 정보, 채팅, 위치 상태, 추천 입력 UI를 표시한다.
*   chat 추천 완료 상태: chat 기본 상태를 유지한 채 추천 결과 카드, 추천 기준 요약, 지도 마커를 함께 표시한다.

### 4.3 추천 결과 구조

추천 결과는 chat 화면 내부에서 함께 표시한다.

구성 요소는 다음과 같다.

*   추천 조건 요약 카드
*   추천 장소 3개 카드
*   장소별 거리, 카테고리, 추천 사유 요약
*   추천 전 안내 상태와 추천 후 결과 상태 구분
*   지도 위 추천 장소 마커와 출발 위치 마커
*   사용 중인 만남 모드와 카테고리 요약

## 5\. 사용자 흐름 구조

### 5.1 전체 사용자 흐름

1.  사용자가 랜딩 화면에서 서비스 소개와 CTA를 확인한다.
2.  사용자가 로그인 또는 회원가입 화면으로 이동해 인증 UI를 확인한다.
3.  사용자는 friends 허브 화면에서 친구를 추가하거나 검색한다.
4.  친구 선택 시 chat 화면으로 이동하며 선택한 친구 정보, 채팅 패널, 위치 상태가 표시된다.
5.  사용자는 지금 만나기 또는 나중에 만나기 모드를 선택한다.
6.  지금 만나기 모드이면 위치 공유 버튼으로 현재 위치 상태를 갱신하고, 나중에 만나기 모드이면 주소 검색, 핀 지정, 저장 위치 선택 중 하나로 내 출발 위치와 친구 출발 위치를 정한다.
7.  필요하면 위치 상태 또는 출발 위치를 저장 위치 제목 입력 레이어를 통해 저장 목록에 추가한다.
8.  사용자는 카페, 식사, 놀거리 중 만남 목적 카테고리를 선택한다.
9.  추천 버튼 클릭 시 추천 요약, 장소 카드, 지도 패널 UI가 갱신된다.

### 5.2 채팅 흐름

1.  친구 선택
2.  선택한 친구 기준으로 채팅 패널과 상단 상태 패널 전환
3.  메시지 입력
4.  전송 시 로컬 메시지 목록 갱신
5.  전송 피드백 문구 표시

메시지 조회 범위 기준:

*   현재 UI 기준에서는 친구별 목업 메시지 배열을 선택해 보여준다.
*   메시지 전송은 로컬 상태에 새 메시지를 추가하는 방식으로 표현한다.
*   실제 저장, 재조회, 폴링 기준은 후속 서버 연동 단계에서 확정한다.

### 5.3 위치 및 추천 흐름

1.  사용자가 만남 모드를 선택한다.
2.  지금 만나기 모드이면 위치 공유 버튼으로 현재 위치 상태와 공유 시각 UI를 갱신한다.
3.  나중에 만나기 모드이면 주소 검색 레이어, 핀 지정 레이어, 저장 위치 목록 중 하나로 내 출발 위치와 친구 출발 위치를 정한다.
4.  주소 검색 또는 핀 지정 결과는 저장 위치 제목 입력 레이어를 통해 목록에 추가할 수 있다.
5.  사용자는 카테고리를 선택한다.
6.  추천 버튼 클릭 시 추천 요약, 추천 카드 3개, 지도 패널 상태를 함께 갱신한다.
7.  추천 후에는 지도 패널에 중심점과 추천 장소 마커 흐름을 보여준다.

현재 구현은 UI와 로컬 상태 중심으로 흐름을 보여주며, 실제 좌표 저장, 서버 계산, 후보 조회 규칙은 후속 통합 단계에서 이 문서의 서버/추천 설계를 따른다.

### 5.4 예외 흐름 및 사용자 안내 기준

MVP에서 우선 처리해야 하는 예외 상황은 다음과 같다.

| 상황                            | 프론트엔드 처리                                    | 비고                                                    |
| ------------------------------- | -------------------------------------------------- | ------------------------------------------------------- |
| 위치 권한 또는 SDK 준비 실패    | 위치 공유 피드백 또는 레이어 내 오류 문구 표시     | 기존 UI 상태는 유지                                     |
| 현재 위치 또는 출발 위치 미입력 | 추천 버튼 비활성화 또는 안내 문구 표시             | 모드와 입력 방식에 따라 필요한 항목을 구분해 안내       |
| 저장 위치 제목 미입력           | 저장 버튼 비활성화                                 | 제목 입력 후 저장 가능                                  |
| 주소 검색 결과 없음             | 검색 결과 없음 문구와 입력 재시도 안내             | 주소 검색 레이어와 핀 지정 레이어 모두 동일한 원칙 적용 |
| 추천 전 상태                    | 결과 패널 대신 안내 문구와 기본 지도 이미지를 표시 | 오류가 아니라 기본 대기 상태                            |
| 후속 인증 연동 전 세션 처리     | 랜딩 CTA preview 와 인증 입력 UI만 제공            | 실제 세션 만료 처리 규칙은 후속 인증 연동 단계에서 확정 |

## 6\. 페이지 및 컴포넌트 구조

### 6.1 페이지 구조

MVP 기준 기본 페이지 구조는 다음과 같이 설계한다.

*   랜딩 페이지
*   로그인 페이지
*   회원가입 페이지
*   friends 허브 페이지
*   chat 상세 페이지

### 7.3 후속 MVP API 계약 초안

모든 API 응답은 JSON 기준으로 통일한다. 보호 API는 사용자 ID를 요청 본문에서 받지 않고, 검증된 JWT 쿠키에서 현재 사용자를 식별한다.

| 기능                            | Method | Path                                                        | 요청 값                                                                                              | 성공 응답 예시                                                                                             |
| ------------------------------- | ------ | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 회원가입 처리                   | POST   | /api/auth/signup                                            | { nickname, password }                                                                               | { ok: true, data: { user: { id, nickname, lat, lng, locationUpdatedAt } } }                                |
| 로그인 처리                     | POST   | /api/auth/login                                             | { nickname, password }                                                                               | { ok: true, data: { user: { id, nickname, lat, lng, locationUpdatedAt } } }                                |
| 로그아웃 처리                   | POST   | /api/auth/logout                                            | 없음                                                                                                 | { ok: true, data: { cleared: true } }                                                                      |
| 친구 추가                       | POST   | /api/friends                                                | { friendNickname }                                                                                   | { ok: true, data: { relationId, friend: { id, nickname, lat, lng, locationUpdatedAt } } }                  |
| 친구 목록 조회                  | GET    | /api/friends                                                | 없음                                                                                                 | { ok: true, data: { friends: \[...\] } }                                                                   |
| 메시지 저장                     | POST   | /api/messages                                               | { friendId, content }                                                                                | { ok: true, data: { message: { id, senderId, receiverId, content, createdAt } } }                          |
| 메시지 조회                     | GET    | /api/messages?friendId={id}&after={isoDatetime?}&limit={n?} | query: friendId, after, limit                                                                        | { ok: true, data: { messages: \[...\], pollingIntervalSec: 5 } }                                           |
| 위치 저장                       | POST   | /api/location                                               | { lat, lng }                                                                                         | { ok: true, data: { location: { lat, lng, locationUpdatedAt } } }                                          |
| 출발 위치 검색                  | GET    | /api/location/search?query={text}                           | query: query                                                                                         | { ok: true, data: { places: \[{ label, source, lat, lng }\] } }                                            |
| 저장된 출발 위치 목록 조회      | GET    | /api/location/departures?limit={n?}                         | query: limit                                                                                         | { ok: true, data: { departures: \[...\] } }                                                                |
| 저장된 출발 위치 저장           | POST   | /api/location/departures                                    | { label, lat, lng, locationKind }                                                                    | { ok: true, data: { departure: { id, label, lat, lng, locationKind, lastUsedAt, createdAt, updatedAt } } } |
| 저장된 출발 위치 사용 시각 갱신 | POST   | /api/location/departures/use                                | { departureLocationId }                                                                              | { ok: true, data: { departure: { id, label, lat, lng, locationKind, lastUsedAt, updatedAt } } }            |
| 추천 결과 조회                  | POST   | /api/recommendations                                        | { friendId, mode, category, departure?: { lat, lng, label }, friendDeparture?: { lat, lng, label } } | { ok: true, data: { midpoint: { lat, lng }, summary: { mode, category, radiusUsed }, places: \[...\] } }   |

요청 검증 기준:

*   nickname은 trim 후 앞뒤 공백을 제거하고, 내부 연속 공백은 한 칸으로 정규화한다.
*   nickname은 정규화 후 2자 이상 12자 이하 문자열로 제한한다.
*   nickname은 한글, 영문, 숫자, 공백만 허용하고 특수문자는 허용하지 않는다.
*   nickname 비교와 중복 검사는 nickname\_normalized 기준으로 수행하며, 영문은 소문자로 정규화한다.
*   password는 8자 이상 20자 이하 문자열로 제한한다.
*   friendNickname은 정규화 후 자기 자신의 nickname\_normalized와 같을 수 없다.
*   content는 공백 제거 후 1자 이상 500자 이하로 제한한다.
*   lat는 -90 이상 90 이하, lng는 -180 이상 180 이하 범위만 허용한다.
*   friendId는 UUID 형식 문자열만 허용한다.
*   departureLocationId는 UUID 형식 문자열만 허용한다.
*   limit는 생략 시 50을 사용하고 최대 100까지만 허용한다.
*   after는 ISO datetime 문자열만 허용하며, polling 요청에서만 선택적으로 사용한다.
*   mode는 now 또는 later 중 하나만 허용한다.
*   category는 cafe, meal, fun 중 하나만 허용한다.
*   locationKind는 recent 또는 preset 중 하나만 허용한다.
*   출발 위치 검색 query는 2자 이상 문자열만 허용한다.

친구 관계 생성 규칙:

*   친구 추가 성공 시 서버는 user\_id -> friend\_id, friend\_id -> user\_id 관계 row 2건을 하나의 트랜잭션으로 upsert 한다.
*   이미 양방향 관계가 모두 존재하면 중복 생성하지 않고 기존 관계를 그대로 사용한다.
*   한쪽 관계만 남아 있는 비정상 상태가 발견되면 누락된 반대 방향 row를 함께 복구한다.

### 7.4 후속 인증 및 쿠키 규칙

후속 인증 연동 단계에서는 닉네임 + 비밀번호 기반 회원가입/로그인을 사용하고, 인증 토큰은 JWT를 httpOnly 쿠키로 관리한다.

*   쿠키 이름은 meetpoint\_auth로 통일한다.
*   JWT payload는 userId, nickname, iat, exp 값을 포함한다.
*   JWT는 서버 전용 비밀키로 서명한다.
*   쿠키는 httpOnly, sameSite=lax, path=/ 기준으로 설정하고, 운영 환경에서는 secure=true로 설정한다.
*   쿠키 만료 시간은 7일로 설정한다.
*   POST /api/auth/signup 성공 시 서버가 JWT 쿠키를 발급한다.
*   POST /api/auth/login 성공 시 서버가 JWT 쿠키를 발급한다.
*   POST /api/auth/logout 는 JWT 유무와 관계없이 쿠키를 삭제하고 200 응답을 반환한다.
*   보호 API는 JWT 쿠키를 검증한 뒤 currentUserId를 서버 내부 컨텍스트에 주입한다.
*   서명이 유효하지 않거나 만료된 쿠키는 즉시 삭제하고 401을 반환한다.
*   JWT 비밀키는 JWT\_SECRET 환경 변수로 관리하며 브라우저에 노출하지 않는다.
*   닉네임 찾기와 비밀번호 재설정은 MVP 범위에서 제외한다.

### 7.4.1 후속 필수 환경 변수 계약

실제 구현 시 사용하는 주요 환경 변수는 다음과 같이 고정한다.

| 변수명                                   | 사용 위치        | 용도                      | 공개 여부 |
| ---------------------------------------- | ---------------- | ------------------------- | --------- |
| NEXT\_PUBLIC\_SUPABASE\_URL              | 클라이언트, 서버 | Supabase 프로젝트 URL     | 공개 가능 |
| NEXT\_PUBLIC\_SUPABASE\_PUBLISHABLE\_KEY | 클라이언트, 서버 | 제한된 공개용 Supabase 키 | 공개 가능 |
| SUPABASE\_SERVICE\_ROLE\_KEY             | 서버 전용        | 관리자 권한 DB 작업       | 서버 전용 |
| JWT\_SECRET                              | 서버 전용        | JWT 서명 및 검증          | 서버 전용 |
| NEXT\_PUBLIC\_KAKAO\_MAP\_APP\_KEY       | 클라이언트       | Kakao Map SDK 로딩        | 공개 가능 |
| KAKAO\_LOCAL\_REST\_API\_KEY             | 서버 전용        | Kakao Local API 호출      | 서버 전용 |

추가 원칙:

*   NEXT\_PUBLIC\_ 접두사가 없는 값은 브라우저 번들에 포함하지 않는다.
*   Kakao Local API 키와 Supabase service role key는 Route Handler 내부에서만 사용한다.
*   환경 변수 이름은 팀 공통으로 고정하며 임의 별칭을 만들지 않는다.

### 7.5 공통 응답 및 오류 처리 규칙

성공 응답 형식:

```
{ "ok": true, "data": {} }
```

오류 응답 형식:

```
{ "ok": false, "error": { "code": "ERROR_CODE", "message": "사용자 안내 문구" } }
```

주요 오류 기준은 다음과 같다.

| 상황                         | 상태 코드 | error.code          | 처리 기준                                                     |
| ---------------------------- | --------- | ------------------- | ------------------------------------------------------------- |
| 입력값 형식 오류             | 400       | INVALID\_INPUT      | 닉네임, 좌표, 메시지 길이, UUID 형식 검증 실패                |
| JWT 없음 또는 쿠키 검증 실패 | 401       | UNAUTHORIZED        | 로그인 화면으로 유도                                          |
| 친구 관계가 없는 대상 접근   | 403       | FORBIDDEN\_RELATION | 메시지 조회, 추천 조회 차단                                   |
| 대상 친구 없음               | 404       | FRIEND\_NOT\_FOUND  | 닉네임 검색 실패 또는 삭제된 사용자                           |
| 위치 정보 부족               | 409       | LOCATION\_REQUIRED  | 지금 만나기 모드에서 사용자 또는 친구 위치가 없으면 추천 차단 |
| 출발 위치 정보 부족          | 409       | DEPARTURE\_REQUIRED | 나중에 만나기 모드에서 출발 위치 입력이 없으면 추천 차단      |
| 추천 후보 없음               | 200       | 없음                | 빈 배열과 안내 문구를 정상 응답으로 반환                      |
| 외부 API 실패                | 502       | KAKAO\_API\_FAILED  | fallback 데이터가 있으면 대체, 없으면 재시도 안내             |

## 8\. 후속 데이터 구조 설계

현재 UI는 초기 친구 목록, 채팅 메시지, 저장 위치, 추천 결과를 클라이언트 상태와 fixture 데이터로 유지한다. 아래 데이터 구조는 실제 저장 연동이 시작될 때 적용할 후속 DB 설계 기준이다.

### 8.0 후속 데이터베이스 요약

| 테이블               | 주요 컬럼                                                                                                                       | 저장 내용                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| users                | id, nickname, nickname\_normalized, password\_hash, lat, lng, location\_updated\_at, created\_at                                | 사용자 정보, 인증 정보와 마지막 공유 위치        |
| friends              | id, user\_id, friend\_id, created\_at                                                                                           | 사용자 간 친구 관계                              |
| messages             | id, sender\_id, receiver\_id, content, created\_at                                                                              | 댓글형 채팅 메시지                               |
| departure\_locations | id, user\_id, label, lat, lng, location\_kind, last\_used\_at, created\_at, updated\_at                                         | 나중에 만나기 모드의 저장된 출발 위치            |
| recommendations      | id, user\_id, friend\_id, midpoint\_lat, midpoint\_lng, place\_name, place\_lat, place\_lng, category, score, mode, created\_at | 추천 결과 기록용 확장 데이터, MVP 필수 생성 아님 |

MVP 기본 흐름에서는 추천 결과를 요청 시 계산 후 바로 반환하고, recommendations 테이블은 후속 단계에서 추천 이력 기능이 필요할 때만 추가한다.

### 8.1 users

역할:

*   사용자 기본 정보 저장
*   비밀번호 해시 저장
*   현재 위치 및 위치 갱신 시각 저장
*   회원가입과 로그인 처리의 기준 테이블 역할 수행
*   위치 상태 문구 표시를 위한 기준 데이터 제공
*   지금 만나기 모드의 추천 입력 기준 위치 제공

핵심 필드:

*   id
*   nickname
*   nickname\_normalized
*   password\_hash
*   lat
*   lng
*   location\_updated\_at
*   created\_at

컬럼 의미:

*   id - 사용자 고유 ID
*   nickname - 사용자가 화면에서 보는 표시용 닉네임
*   nickname\_normalized - 중복 비교와 검색에 사용하는 정규화 닉네임
*   password\_hash - 비밀번호 해시 저장 값
*   lat - 사용자가 마지막으로 공유한 위치의 위도
*   lng - 사용자가 마지막으로 공유한 위치의 경도
*   location\_updated\_at - 사용자가 위치 공유 버튼을 마지막으로 누른 시간
*   created\_at - 사용자가 처음 생성된 시간

설계 기준:

*   nickname은 표시용 값으로 저장하되, 중복 검사는 nickname\_normalized 기준으로 수행한다.
*   사용자 조회, 친구 검색, 자기 자신 비교는 모두 nickname\_normalized 기준으로 처리한다.
*   초기 진입 사용자를 위해 위치 필드는 null 허용 구조로 둔다.
*   나중에 만나기 모드의 출발 위치는 추천 요청 입력값과 저장된 출발 위치 선택값을 함께 고려한다.
*   users 의 현재 위치 공유값과 저장된 출발 위치는 분리해 관리한다.

### 8.2 friends

역할:

*   사용자와 친구의 관계 저장

핵심 필드:

*   id
*   user\_id
*   friend\_id
*   created\_at

컬럼 의미:

*   id - 친구 관계 고유 ID
*   user\_id - 친구를 추가한 사용자 ID
*   friend\_id - 추가된 친구의 사용자 ID
*   created\_at - 친구 관계가 생성된 시간

설계 기준:

*   단순 닉네임 문자열 저장이 아니라 사용자 관계 기반 구조로 설계한다.
*   동일 관계 중복 저장을 방지한다.
*   친구 추가 성공 시 양방향 관계 row 2건을 함께 유지하여 메시지 조회와 추천 조회 권한 기준을 단순하게 맞춘다.

### 8.3 messages

역할:

*   댓글형 채팅 메시지 저장

핵심 필드:

*   id
*   sender\_id
*   receiver\_id
*   content
*   created\_at

컬럼 의미:

*   id - 메시지 고유 ID
*   sender\_id - 메시지를 보낸 사용자 ID
*   receiver\_id - 메시지를 받은 사용자 ID
*   content - 메시지 내용
*   created\_at - 메시지가 작성된 시간

설계 기준:

*   생성 시간 기준으로 정렬 조회한다.
*   실시간 동기화 대신 저장 및 재조회 방식에 맞춘다.

### 8.4 departure\_locations

역할:

*   나중에 만나기 모드에서 재사용할 저장된 출발 위치 저장
*   최근 저장 위치와 사전 등록 위치를 같은 구조 안에서 관리
*   사용자별 저장된 출발 위치 목록 조회와 최근 사용 위치 재사용 기준 제공

핵심 필드:

*   id
*   user\_id
*   label
*   lat
*   lng
*   location\_kind
*   last\_used\_at
*   created\_at
*   updated\_at

컬럼 의미:

*   id - 저장된 출발 위치 고유 ID
*   user\_id - 해당 출발 위치를 저장한 사용자 ID
*   label - 사용자가 식별할 수 있는 출발 위치 이름
*   lat - 추천 입력 기준으로 사용할 출발 위치 위도
*   lng - 추천 입력 기준으로 사용할 출발 위치 경도
*   location\_kind - recent 또는 preset 구분 값
*   last\_used\_at - 마지막으로 해당 출발 위치를 사용한 시간
*   created\_at - 해당 출발 위치가 생성된 시간
*   updated\_at - 해당 출발 위치가 수정된 시간

설계 기준:

*   user\_id 는 users.id 를 참조한다.
*   저장된 출발 위치는 users 의 현재 위치 컬럼과 분리해 관리한다.
*   label 은 빈 문자열을 허용하지 않는다.
*   location\_kind 는 recent 또는 preset 값만 허용한다.
*   저장된 출발 위치 선택 시 last\_used\_at 을 갱신해 최근 재사용 기준으로 활용한다.

### 8.5 recommendations

역할:

*   향후 추천 결과 저장 확장용 테이블

핵심 필드 예시:

*   id
*   user\_id
*   friend\_id
*   midpoint\_lat
*   midpoint\_lng
*   place\_name
*   place\_lat
*   place\_lng
*   category
*   score
*   created\_at

컬럼 의미:

*   id - 추천 결과 고유 ID
*   user\_id - 장소 추천을 요청한 사용자 ID
*   friend\_id - 함께 만날 친구의 사용자 ID
*   midpoint\_lat - 사용자와 친구의 추천 입력 기준 위치를 바탕으로 계산한 중심점 위도
*   midpoint\_lng - 사용자와 친구의 추천 입력 기준 위치를 바탕으로 계산한 중심점 경도
*   place\_name - 추천된 장소 이름
*   place\_lat - 추천된 장소의 위도
*   place\_lng - 추천된 장소의 경도
*   category - 추천 장소의 종류, 예: 카페, 식당, 놀거리 계열
*   score - 평균 이동거리, 거리 편차, 카테고리 패널티, 활성도 패널티를 반영한 추천 점수
*   mode - 추천 요청 시 사용한 만남 모드
*   created\_at - 추천 결과가 생성된 시간

MVP 기준:

*   기본 흐름은 추천 결과를 요청 시 계산 후 바로 반환하는 방식이다.
*   MVP 1차 구현에서는 recommendations 테이블을 생성하지 않는다.
*   추천 이력 확인 기능이 확정될 때만 후속 마이그레이션으로 추가한다.

### 8.6 후속 MVP DB 구성 방식

MVP 기준 최소 DB는 users, friends, messages, departure\_locations 중심으로 구성한다.

| 방식                 | 설명                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------- |
| 기본 MVP DB          | users, friends, messages, departure\_locations 테이블을 필수 생성한다.                       |
| Kakao Local API 사용 | 장소 후보를 실시간으로 가져오므로 places 테이블은 만들지 않는다.                             |
| 임시 데이터 기반 MVP | 개발 및 테스트 환경에서만 서버 내부 fixture 배열 또는 JSON 파일을 보조적으로 사용할 수 있다. |
| 추천 결과 기록       | recommendations 테이블은 MVP 범위에서 제외하고 후속 확장 시 추가한다.                        |

### 8.7 구현 제약, 관계, 인덱스 규칙

실제 테이블 생성 시 반영해야 하는 최소 규칙은 다음과 같다.

| 테이블               | 필수 제약                                                                                                                            | 권장 인덱스                                                                                | 구현 메모                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| users                | unique(nickname\_normalized)                                                                                                         | index(location\_updated\_at), index(nickname\_normalized)                                  | nickname은 표시용, nickname\_normalized는 비교용으로 분리  |
| friends              | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id, unique(user\_id, friend\_id), check(user\_id \<> friend\_id) | index(user\_id), index(friend\_id)                                                         | MVP에서는 친구 추가 시 양방향 row 2건을 함께 upsert        |
| messages             | foreign key(sender\_id) -> users.id, foreign key(receiver\_id) -> users.id                                                           | index(sender\_id, receiver\_id, created\_at), index(receiver\_id, sender\_id, created\_at) | 조회는 두 사용자 간 메시지를 created\_at 오름차순으로 반환 |
| departure\_locations | foreign key(user\_id) -> users.id, check(location\_kind in ('recent', 'preset')), check(label not blank)                             | index(user\_id, last\_used\_at desc), index(user\_id, location\_kind)                      | users 현재 위치와 분리해 저장된 출발 위치를 관리           |
| recommendations      | foreign key(user\_id) -> users.id, foreign key(friend\_id) -> users.id                                                               | index(user\_id, friend\_id, created\_at desc)                                              | 저장은 선택 기능이며 기본 응답은 즉시 계산 결과 반환       |

추가 구현 원칙:

*   브라우저는 Supabase에 직접 쓰기 요청을 보내지 않고, 모든 DB 접근은 Next.js Route Handler를 통해 수행한다.
*   service role key 또는 DB 비밀값은 서버 환경 변수로만 보관한다.
*   사용자 삭제 기능은 MVP 범위에서 제외하며, 삭제 정책은 후속 단계에서 별도 확정한다.
*   현재 UI-only 단계에서는 위 구조를 실제 테이블 대신 로컬 상태와 목업 데이터로 대응한다.

## 9\. 추천 구조 설계

현재 구현에서는 추천 버튼이 요약 카드, 장소 카드, 지도 패널 상태를 갱신하는 UI 흐름을 먼저 제공한다. 아래 구조는 이 UI 흐름을 유지한 채 후속 서버 계산으로 확장하기 위한 기준이다.

### 9.1 장소 추천 흐름

사용자가 장소 추천 버튼을 누르면 다음 순서로 동작한다.

1.  프론트엔드에서 만남 모드, 카테고리, 출발 위치 입력 상태를 확인한다.
2.  현재 UI 단계에서는 추천 요약, 추천 카드 3개, 지도 패널 표시 상태를 로컬 상태로 갱신한다.
3.  후속 서버 연동 단계에서는 프론트엔드가 friendId, mode, category, 필요한 경우 출발 위치 정보를 포함해 추천 요청을 보낸다.
4.  Next.js Route Handler가 인증 상태를 검증한다.
5.  서버가 추천 요청 기준에 따라 사용자와 친구의 출발 기준 위치를 확정한다.
6.  두 위치의 중심점을 계산한다.
7.  중심점 주변 장소 후보를 1km, 2km, 3km 순서로 확장 조회한다.
8.  외부 장소 API가 후보 목록을 반환한다.
9.  각 후보 장소와 사용자 A, 사용자 B 사이의 거리 계산을 수행한다.
10. 카테고리 패널티와 지역 활성도 패널티를 계산한다.
11. 추천 점수를 계산하고 동점 처리 기준에 따라 정렬한다.
12. 상위 3개 장소와 추천 기준 요약을 프론트엔드에 전달한다.
13. 프론트엔드가 지도 마커와 추천 장소 카드 표시를 갱신한다.

### 9.2 중심점 계산

MVP에서는 두 사람의 위도와 경도 평균값으로 중심점을 구한다.

*   중심 위도 = (A 위도 + B 위도) / 2
*   중심 경도 = (A 경도 + B 경도) / 2

예시:

| 사람     | 위도   | 경도    |
| -------- | ------ | ------- |
| 사용자 A | 37.500 | 127.030 |
| 사용자 B | 37.560 | 127.010 |

중심점:

*   중심 위도 = (37.500 + 37.560) / 2 = 37.530
*   중심 경도 = (127.030 + 127.010) / 2 = 127.020

이 중심점 주변에서 사용자가 선택한 카테고리에 맞는 후보를 검색한다.

### 9.3 거리 계산과 Haversine 공식

Haversine 공식은 두 좌표 사이의 거리를 계산하는 공식이다.

MeetPoint에서는 다음 거리 계산에 사용한다.

*   사용자 A와 후보 장소 사이 거리
*   사용자 B와 후보 장소 사이 거리

각 장소마다 다음 값을 계산한다.

*   distanceA = 사용자 A와 장소 사이 거리
*   distanceB = 사용자 B와 장소 사이 거리

이 값을 기반으로 평균 이동거리와 거리 편차를 계산한다.

### 9.4 추천 점수식

좋은 장소는 다음 네 조건을 함께 만족해야 한다.

1.  전체적으로 너무 멀지 않아야 한다.
2.  한 사람에게만 불리하지 않아야 한다.
3.  사용자가 원하는 만남 목적과 맞아야 한다.
4.  주변에 실제로 갈 만한 후보가 충분해야 한다.

점수식:

```
score = 평균 이동거리 + 거리 편차 + 카테고리 패널티 + 지역 활성도 패널티
```

| 항목               | 의미                                       |
| ------------------ | ------------------------------------------ |
| 평균 이동거리      | 전체적으로 가까운 장소인지 판단            |
| 거리 편차          | 두 사람에게 공평한 장소인지 판단           |
| 카테고리 패널티    | 선택한 목적과 후보 카테고리 일치도 반영    |
| 지역 활성도 패널티 | 후보 주변의 장소 밀집도와 지역 매력도 반영 |
| score              | 낮을수록 좋은 장소                         |

계산식은 다음과 같다.

```
평균 이동거리 = (A 거리 + B 거리) / 2
거리 편차 = |A 거리 - B 거리|
카테고리 패널티 = 선택한 목적과 장소 카테고리가 안 맞을수록 증가
지역 활성도 패널티 = 주변에 갈 만한 장소가 적을수록 증가
```

### 9.5 카테고리 패널티 기준

MVP에서는 카테고리 패널티를 거리 점수처럼 합산 가능한 수치로 단순화한다.

| 사용자 선택 | 후보 장소 카테고리             | 패널티 |
| ----------- | ------------------------------ | ------ |
| 카페        | 카페                           | 0점    |
| 카페        | 베이커리, 디저트               | 200점  |
| 카페        | 식당                           | 800점  |
| 식사        | 한식, 중식, 일식, 양식         | 0점    |
| 식사        | 카페                           | 600점  |
| 놀거리      | 영화관, 노래방, 게임, 문화시설 | 0점    |
| 놀거리      | 카페                           | 400점  |
| 공통        | 전혀 관련 없는 후보            | 1000점 |

### 9.6 지역 활성도 패널티 기준

지역 활성도는 각 후보 장소 주변 500m 안에 관련 후보가 몇 개인지를 기준으로 본다.

| 주변 500m 내 후보 수 | 지역 활성도 | 패널티 |
| -------------------- | ----------- | ------ |
| 10개 이상            | 매우 좋음   | 0점    |
| 6~9개                | 좋음        | 200점  |
| 3~5개                | 보통        | 500점  |
| 1~2개                | 낮음        | 800점  |
| 0개                  | 매우 낮음   | 1200점 |

MVP에서는 Kakao Local API 검색 결과 안에서 각 후보의 주변 후보 수를 비교하는 방식으로 단순 계산한다.

### 9.7 예시 계산

| 장소   | A 거리 | B 거리 | 거리 편차 | 카테고리 패널티 | 활성도 패널티 | score |
| ------ | ------ | ------ | --------- | --------------- | ------------- | ----- |
| 카페 A | 1.5km  | 3.5km  | 2km       | 0               | 200           | 2700  |
| 카페 B | 2km    | 2km    | 0km       | 0               | 0             | 2000  |
| 식당 C | 1.8km  | 2.2km  | 0.4km     | 800             | 0             | 3200  |

추천 순위:

1.  카페 B: 거리와 공정성, 지역 활성도가 모두 안정적이어서 1순위
2.  카페 A: 공정성은 다소 떨어지지만 카테고리가 적합해 2순위
3.  식당 C: 거리는 나쁘지 않지만 카페 목적과 맞지 않아 3순위

### 9.8 후보 장소 확보 전략

*   1차 기준은 Kakao Local API를 통한 실시간 후보 조회이다.
*   외부 API 호출이 제한되거나 테스트 환경이 불안정한 경우를 대비해 개발 및 테스트 환경에서만 임시 후보 장소 데이터 구조를 보조 전략으로 둔다.
*   보조 전략은 서버 내부 fixture 데이터 fallback 용도로만 사용한다.
*   운영 환경에서는 Kakao Local API 응답만 사용하고, 임시 데이터 fallback은 활성화하지 않는다.

### 9.9 추천 파라미터 및 동점 처리 기준

MVP 구현 시 추천 결과를 일관되게 만들기 위한 계산 기준은 다음과 같다.

| 항목           | 값                     | 적용 방식                                                 |
| -------------- | ---------------------- | --------------------------------------------------------- |
| 추천 카테고리  | 카페, 식사, 놀거리     | Kakao Local API 검색과 자체 카테고리 매핑의 기준으로 사용 |
| 검색 반경      | 1km → 2km → 3km        | 후보 부족 시 단계적으로 확장                              |
| 최대 후보 수   | 15개                   | 응답 후보가 많으면 중심점과 가까운 순으로 15개만 사용     |
| 최종 노출 개수 | 3개                    | score 오름차순 기준 상위 3개 반환                         |
| 거리 계산 단위 | 내부 계산은 meter      | 화면 표시는 1000m 이상이면 km 한 자리 소수로 변환         |
| 활성도 기준    | 후보 주변 500m 내 개수 | Kakao Local API 결과 안에서 주변 후보 수 기준으로 계산    |

동점 처리 규칙:

1.  score가 낮은 순서
2.  거리 편차가 낮은 순서
3.  평균 이동거리가 낮은 순서
4.  place\_name 가나다순

추가 기준:

*   지금 만나기 모드에서 사용자와 친구 둘 중 하나라도 위치가 없으면 계산하지 않고 409 LOCATION\_REQUIRED를 반환한다.
*   나중에 만나기 모드에서 출발 위치가 비어 있으면 409 DEPARTURE\_REQUIRED를 반환한다.
*   위치 갱신 시각이 오래되었더라도 MVP에서는 마지막 공유 위치를 그대로 사용한다.
*   추천 결과가 0건이면 오류가 아니라 빈 결과로 처리한다.

## 10\. 외부 서비스 연동 구조

### 10.1 외부 서비스 역할 구분

현재 UI와 후속 통합에서 사용하는 외부 서비스는 다음과 같이 역할을 나누어 이해한다.

| 구분                       | 사용 위치            | 역할                                                |
| -------------------------- | -------------------- | --------------------------------------------------- |
| Kakao Maps JS SDK          | 프론트엔드           | 지도 화면 표시, 마커 표시, 핀 지정 인터랙션 보조    |
| Daum Postcode              | 프론트엔드           | 주소 검색 레이어 제공                               |
| Kakao geocoder             | 프론트엔드           | 핀 지정 결과의 주소 확인과 주소 검색 보조           |
| Kakao Local API            | 후속 백엔드          | 중심점 주변 카테고리별 장소 후보 검색               |
| 로컬 fixture / 상태 데이터 | 현재 프론트엔드 구현 | 친구, 메시지, 저장 위치, 추천 결과 UI의 임시 데이터 |

카카오 API 가 최종 추천을 직접 결정하는 것은 아니다.

MeetPoint 는 카카오 API 로 장소 후보를 확보한 뒤, 사용자와 후보 장소 간 거리를 계산하고 평균 이동거리, 거리 편차, 카테고리 패널티, 지역 활성도 패널티를 반영한 자체 점수식으로 다시 정렬한다.

### 10.2 Kakao Maps JS SDK

역할:

*   지도 렌더링
*   사용자 위치 마커 표시
*   친구 위치 마커 표시
*   중심점 마커 표시
*   추천 장소 마커 표시

처리 위치:

*   클라이언트

### 10.3 Daum Postcode 및 Kakao geocoder

역할:

*   주소 검색
*   핀 지정 결과 주소 확인
*   출발 위치 입력 보조

처리 위치:

*   클라이언트 레이어 UI

설계 기준:

*   chat 상세 화면의 주소 검색 레이어와 핀 지정 레이어에서 사용한다.
*   추천 후보 계산용 장소 검색과는 구분해 사용한다.

### 10.4 임시 UI 데이터

역할:

*   friends, chat, recommendation UI를 현재 화면에서 안정적으로 보여주기 위한 목업 데이터 소스

처리 위치:

*   클라이언트 중심

설계 기준:

*   현재 단계에서는 friend 목록, chat 메시지, 저장 위치, 추천 카드 상태를 로컬 배열과 상태 훅으로 관리한다.
*   후속 서버 및 DB 연동 시 실제 응답 구조와 자연스럽게 교체할 수 있도록 화면 컴포넌트와 분리한다.
*   운영 기준 데이터 저장 구조는 7장과 8장의 후속 통합 설계를 따른다.

### 10.5 후속 백엔드 연동 대상

역할:

*   Kakao Local API를 통한 장소 후보 조회
*   Supabase를 통한 사용자, 친구, 메시지, 저장 위치 데이터 저장
*   인증과 추천 계산을 서버 중심으로 통합

처리 위치:

*   서버 중심

## 12\. 통합 구조 전략

통합 전략은 다음과 같다.

*   팀원별로 자기 역할에 맞는 기능 구조를 먼저 정리한다.
*   A 팀원이 최종 화면 흐름 기준을 맞추고 통합 화면 구조를 정리한다.
*   팀원 B와 C의 기능은 friends 허브 화면과 chat 상세 화면 구조에 연결 가능한 방식으로 설계한다.
*   공통 데이터 구조와 사용자 흐름은 구조 설계 문서를 기준으로 통일한다.

### 12.1 협업 및 지도/브랜치 전략

협업 도구와 기본 기술 선택은 2.1 핵심 기술 스택을 기준으로 통일한다.

운영 원칙은 다음과 같다.

*   지도 기능은 Kakao Map API를 기준으로 통일하여 사용자 위치, 친구 위치, 중심점, 추천 장소 마커 표시 방식을 일관되게 맞춘다.
*   협업 관리는 GitHub와 Jira를 함께 사용하여 코드 변경 이력과 작업 단위를 분리해서 관리한다.
*   브랜치 전략은 `main`, `feature/*`, `docs/*` 기준으로 고정하여 작업지침서와 동일하게 운영한다.
*   기능 병합은 PR 리뷰를 전제로 진행하여 팀원 간 충돌을 줄이고 최종 통합 품질을 관리한다.

## 13\. 개발 착수 기준

다음 조건이 만족되면 구조 설계 기준으로 개발 착수가 가능하다.

*   랜딩, 인증, friends, chat 화면 구성 요소가 정의되어 있다.
*   사용자 흐름이 단계별로 정리되어 있다.
*   현재 UI-only 구현 범위와 후속 서버/DB 통합 범위가 구분되어 있다.
*   서버와 클라이언트의 책임이 분리되어 있다.
*   핵심 데이터 구조와 추천 처리 흐름이 정리되어 있다.
*   후속 API 계약, 세션 규칙, 공통 오류 응답 기준이 정의되어 있다.
*   닉네임 정규화 규칙과 친구 관계 생성 규칙이 확정되어 있다.
*   후속 환경 변수 이름과 공개 범위가 정의되어 있다.
*   DB 제약 조건과 추천 파라미터가 구현 가능한 수준으로 명시되어 있다.
*   팀원별 구조 책임이 구분되어 있다.

---

## 14\. 결론

MeetPoint의 현재 구조 설계는 랜딩, 인증, friends, chat, 추천 흐름을 우선 안정적으로 보여주는 프론트엔드 UI 구조를 기준으로 한다. 동시에 후속 인증, 저장, 추천 계산, 외부 API 연동이 들어와도 화면 구조를 크게 바꾸지 않도록 서버와 데이터 설계 초안을 함께 유지한다. 본 문서는 현재 구현 상태와 후속 통합 방향을 한 문서 안에서 구분해 정리한 기준 문서이며, 이후 기술 설계와 역할별 구현 단계의 직접적인 기반으로 사용한다.
