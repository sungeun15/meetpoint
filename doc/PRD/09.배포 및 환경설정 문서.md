# MeetPoint 배포 및 환경설정 문서

## 1\. 문서 목적

이 문서는 MeetPoint MVP 1차 구현을 실제 배포 환경에 올릴 때 필요한 기준을 정리한 문서이다.

기획 문서와 기술 설계 문서가 무엇을 만들지 설명하는 문서라면, 본 문서는 어디에 배포하고 어떤 환경 변수를 넣고 배포 후 무엇을 확인해야 하는지를 정리하는 운영 기준 문서로 사용한다.

---

## 2\. 문서 범위

본 문서는 아래 범위를 포함한다.

1.  배포 대상과 배포 환경 정의
2.  Vercel 배포 기준
3.  환경 변수 구성 기준
4.  local, preview, production 운영 원칙
5.  배포 절차와 배포 후 확인 항목
6.  자주 발생하는 배포 문제와 확인 순서

본 문서의 기본 범위에서 제외하는 항목은 아래와 같다.

1.  서버 인프라를 직접 구축하는 방식
2.  Docker 기반 별도 배포 방식
3.  실시간 서버 운영 구조
4.  모바일 앱 배포 방식

## 3\. 배포 대상 요약

### 3.1 배포 대상 서비스

MeetPoint MVP 1차는 Next.js 16 App Router 기반 웹앱으로 배포한다.

현재 구조 기준 핵심 배포 대상은 아래와 같다.

1.  app/
2.  public/
3.  package.json
4.  next.config.ts
5.  pnpm-lock.yaml
6.  tsconfig.json

즉, 배포 기준은 문서 폴더나 협업용 작업 폴더가 아니라 실제 앱 실행에 필요한 저장소 루트 구조이다.

### 3.2 배포 대상 환경

MeetPoint는 아래 3개 환경을 기준으로 운영한다.

1.  local
2.  preview
3.  production

각 환경의 목적은 아래와 같다.

| 환경       | 목적                   | 사용 시점                        |
| ---------- | ---------------------- | -------------------------------- |
| local      | 개발자 개인 기능 확인  | 기능 구현 중                     |
| preview    | 배포 전 통합 확인      | 브랜치 또는 Pull Request 검토 시 |
| production | 최종 시연 및 제출 기준 | 최종 배포 시                     |

## 4\. 배포 플랫폼 기준

### 4.1 기본 배포 플랫폼

MeetPoint MVP 1차 기본 배포 플랫폼은 Vercel로 한다.

이유는 아래와 같다.

1.  Next.js 프로젝트와 가장 자연스럽게 연결된다.
2.  GitHub 저장소 연동이 쉽다.
3.  Preview 배포와 Production 배포를 나누기 쉽다.
4.  MVP 시연 기준으로 설정 부담이 적다.

### 4.2 기본 배포 방식

배포 방식은 GitHub 연동 자동 배포를 기본으로 한다.

즉, 아래 흐름으로 이해하면 된다.

1.  GitHub 저장소를 Vercel에 연결한다.
2.  지정된 브랜치에 push 한다.
3.  Vercel이 자동으로 새 배포를 생성한다.
4.  Preview 또는 Production URL에서 결과를 확인한다.

CLI 배포도 가능하지만, 현재 MVP 기준 운영 방식으로는 Git 기반 자동 배포가 가장 단순하다.

## 5\. 환경 변수 기준

### 5.1 필수 환경 변수 목록

배포 전 아래 변수 6개는 반드시 준비되어 있어야 한다.

1.  NEXT\_PUBLIC\_SUPABASE\_URL
2.  NEXT\_PUBLIC\_SUPABASE\_PUBLISHABLE\_KEY
3.  SUPABASE\_SERVICE\_ROLE\_KEY
4.  JWT\_SECRET
5.  NEXT\_PUBLIC\_KAKAO\_MAP\_APP\_KEY
6.  KAKAO\_LOCAL\_REST\_API\_KEY

이 중 하나라도 누락되면 인증, 데이터 조회, 지도 표시, 추천 기능 중 일부가 실패할 수 있다.

### 5.2 공개 가능 변수와 비공개 변수

공개 가능 변수는 아래와 같다.

1.  NEXT\_PUBLIC\_SUPABASE\_URL
2.  NEXT\_PUBLIC\_SUPABASE\_PUBLISHABLE\_KEY
3.  NEXT\_PUBLIC\_KAKAO\_MAP\_APP\_KEY

서버 전용 변수는 아래와 같다.

1.  SUPABASE\_SERVICE\_ROLE\_KEY
2.  JWT\_SECRET
3.  KAKAO\_LOCAL\_REST\_API\_KEY

가장 중요한 원칙은 아래 한 줄이다.

1.  NEXT\_PUBLIC\_ 로 시작하면 브라우저에 노출 가능한 값
2.  NEXT\_PUBLIC\_ 가 없으면 서버에서만 사용해야 하는 값

### 5.3 환경 변수 사용 목적

| 변수명                                   | 용도                    | 사용 위치      |
| ---------------------------------------- | ----------------------- | -------------- |
| NEXT\_PUBLIC\_SUPABASE\_URL              | Supabase 프로젝트 주소  | 브라우저, 서버 |
| NEXT\_PUBLIC\_SUPABASE\_PUBLISHABLE\_KEY | 공개용 Supabase 연결 키 | 브라우저, 서버 |
| SUPABASE\_SERVICE\_ROLE\_KEY             | 관리자 권한 DB 처리     | 서버 전용      |
| JWT\_SECRET                              | JWT 서명 및 검증        | 서버 전용      |
| NEXT\_PUBLIC\_KAKAO\_MAP\_APP\_KEY       | Kakao 지도 SDK 로드     | 브라우저       |
| KAKAO\_LOCAL\_REST\_API\_KEY             | Kakao Local 장소 검색   | 서버 전용      |

### 5.4 예시 환경 변수 형식

아래 예시는 구조 확인용 샘플이다.

```
NEXT_PUBLIC_SUPABASE_URL=https://sample-project.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_sample-key-value
SUPABASE_SERVICE_ROLE_KEY=sample-service-role-key-value
JWT_SECRET=meetpoint-sample-jwt-secret-2026
NEXT_PUBLIC_KAKAO_MAP_APP_KEY=sample-kakao-map-app-key
KAKAO_LOCAL_REST_API_KEY=sample-kakao-local-rest-api-key
```

주의 사항은 아래와 같다.

1.  실제 비밀 값은 문서에 적지 않는다.
2.  실제 운영 값은 저장소에 커밋하지 않는다.
3.  Preview 와 Production 값을 섞지 않는다.

### 5.5 앱 실행 변수와 스키마 변경용 접속 정보는 분리한다

위 6개 환경 변수는 MeetPoint 앱을 실행하고, 이미 준비된 테이블에 접근하고, 배포 환경에서 인증과 추천 기능을 확인하기 위한 기본 변수이다.

하지만 새 테이블 생성, ALTER TABLE, 인덱스 생성, 직접 SQL 실행 같은 작업은 앱 실행과 다른 관리자 작업이다.

따라서 배포 문서에서는 앱 실행용 기본 변수와 DB 관리자용 직접 접속 정보를 분리해서 관리한다.

이렇게 구분하는 이유는 아래와 같다.

1.  배포에 필요한 최소 변수와 관리자용 강한 권한 정보를 섞지 않기 위해서이다.
2.  connection string이나 DB password 같은 값을 모든 환경에 기본 배포하지 않기 위해서이다.
3.  local, preview, production에서 관리자용 접속 정보를 더 엄격하게 통제하기 위해서이다.

### 5.6 직접 DB 작업이 필요할 때 추가로 준비할 것

새 테이블 생성이나 직접 SQL 실행이 필요하면 아래 중 하나가 더 있어야 한다.

1.  Supabase SQL Editor
2.  PostgreSQL 직접 접속 정보
3.  Supabase CLI migration 환경
4.  관리자용 내부 스크립트

예를 들어 PostgreSQL 직접 접속 방식으로 진행할 때는 아래 같은 정보가 추가로 필요할 수 있다.

```env
SUPABASE_DATABASE_URL=postgresql://postgres:[YOUR_PASSWORD]@db.your-project-ref.supabase.co:5432/postgres?sslmode=require
```

또는 아래처럼 나눠서 관리할 수도 있다.

```env
SUPABASE_DB_HOST=db.your-project-ref.supabase.co
SUPABASE_DB_PORT=5432
SUPABASE_DB_NAME=postgres
SUPABASE_DB_USER=postgres
SUPABASE_DATABASE_PASSWORD=your-postgres-password
```

주의:

1.  위 값들은 기본 배포 환경 변수 6개에 포함되지 않는다.
2.  앱 실행만으로 충분한 환경에서는 굳이 넣지 않는다.
3.  DB password, connection string, 관리자 접속 정보는 공개 저장소에 커밋하면 안 된다.

## 6\. 환경별 운영 기준

### 6.1 local

local은 개발자 개인 PC에서 실행하는 개발 환경이다.

가장 대표적인 실행 방식은 아래와 같다.

```
pnpm dev
```

즉, local은 개발 서버를 띄워 빠르게 수정하고 바로 화면을 확인하는 환경이라고 이해하면 된다.

주요 확인 항목은 아래와 같다.

1.  회원가입과 로그인 동작 여부
2.  Supabase 연결 여부
3.  Kakao 지도 렌더링 여부
4.  추천 API 응답 여부

로컬에서는 .env.local 또는 이에 준하는 로컬 환경 변수 파일을 사용한다.

추가로 필요하면 아래 명령으로 production 모드와 비슷하게 로컬 점검을 할 수 있다.

```
pnpm build
pnpm start
```

하지만 이 경우도 여전히 내 PC에서 실행하는 로컬 확인이라는 점은 변하지 않는다.

### 6.2 preview

preview는 배포 전 검토용 환경이다.

preview는 `pnpm preview` 같은 로컬 명령을 의미하는 것이 아니라, 보통 Vercel 같은 배포 플랫폼에서 브랜치나 Pull Request 기준으로 자동 생성되는 원격 배포 환경을 뜻한다.

보통 아래 목적에 사용한다.

1.  기능 브랜치 결과 확인
2.  통합 배포 전 시나리오 점검
3.  Pull Request 검토

Preview에는 처음에는 Production과 같은 구조의 값을 넣는 편이 안전하다. 그래야 코드 문제인지 환경 변수 문제인지 빠르게 구분할 수 있다.

즉, preview는 아래처럼 이해하면 된다.

1.  개발 서버가 아니라 실제 배포와 거의 같은 방식으로 올라간 확인용 URL
2.  팀원이 같은 주소로 함께 볼 수 있는 검토 환경
3.  main 반영 전에 인증, 지도, 추천 흐름을 점검하는 중간 단계

### 6.3 production

production은 최종 시연 및 제출 기준 환경이다.

로컬에서 아래 명령으로 production 모드처럼 확인할 수는 있다.

```
pnpm build
pnpm start
```

하지만 이것은 production 자체가 아니라 production과 비슷한 모드로 로컬에서 확인하는 과정이다.

이 환경에서는 아래 항목을 특히 엄격하게 관리한다.

1.  JWT\_SECRET
2.  SUPABASE\_SERVICE\_ROLE\_KEY
3.  KAKAO\_LOCAL\_REST\_API\_KEY

즉, 브라우저 노출 금지 값은 Production에서 더 엄격하게 통제해야 한다.

### 6.4 local, preview, production 차이 정리

아래 표처럼 이해하면 가장 헷갈리지 않는다.

| 구분                  | 실행 방식                                  | 실행 위치      | 용도                               |
| --------------------- | ------------------------------------------ | -------------- | ---------------------------------- |
| local                 | pnpm dev                                   | 내 PC          | 개발 중 빠른 수정 확인             |
| local production 점검 | pnpm build 후 pnpm start                   | 내 PC          | production 모드와 비슷한 로컬 점검 |
| preview               | 브랜치 또는 Pull Request push 후 자동 배포 | 원격 배포 서버 | 배포 전 검토, 팀 공유 확인         |
| production            | main 반영 후 최종 배포                     | 원격 배포 서버 | 최종 시연 및 제출 기준             |

핵심은 아래 한 줄이다.

1.  `pnpm dev` 와 `pnpm build && pnpm start` 는 둘 다 로컬 실행이다.
2.  preview는 로컬 명령이 아니라 배포 플랫폼이 만들어 주는 원격 배포 환경이다.

## 7\. Vercel 프로젝트 설정 기준

### 7.1 Framework Preset

Framework Preset은 Next.js로 설정한다.

자동 감지가 되면 그대로 사용하고, 수동 설정이 필요하면 Next.js를 직접 선택한다.

### 7.2 Root Directory

Root Directory는 저장소 루트를 기준으로 잡는다.

즉, app, public, package.json 이 바로 보이는 위치가 기준이다.

아래처럼 이해하면 된다.

1.  로컬 workspace 전체 경로를 Root Directory로 잡지 않는다.
2.  .my\_work 같은 문서 작업 폴더를 Root Directory로 잡지 않는다.
3.  실제 앱 소스가 있는 저장소 루트를 Root Directory로 사용한다.

### 7.3 Install Command

pnpm-lock.yaml 이 있으므로 Install Command는 아래 기준으로 본다.

```
pnpm install
```

### 7.4 Build Command

Build Command는 아래 기준으로 본다.

```
pnpm build
```

### 7.5 런타임 주의 사항

아래 동작은 서버 측에서 이뤄진다고 이해해야 한다.

1.  JWT 검증
2.  Supabase service role key 사용
3.  Kakao Local API 호출
4.  추천 계산

즉, 브라우저 전용 키와 서버 전용 키를 섞으면 안 된다.

## 8\. 배포 절차

### 8.1 최초 배포 절차

최초 배포는 아래 순서를 기준으로 진행한다.

1.  Vercel Dashboard에서 New Project를 선택한다.
2.  GitHub 저장소를 연결한다.
3.  Framework Preset이 Next.js인지 확인한다.
4.  Root Directory가 저장소 루트인지 확인한다.
5.  Install Command가 pnpm install 인지 확인한다.
6.  Build Command가 pnpm build 인지 확인한다.
7.  환경 변수 6개를 모두 입력한다.
8.  Deploy를 실행한다.

### 8.2 변경 배포 절차

최초 연결 후에는 보통 아래 순서로 배포가 진행된다.

1.  GitHub에 코드 push
2.  Vercel이 자동 배포 시작
3.  빌드 로그 확인
4.  배포 완료 후 URL 접속
5.  핵심 사용자 시나리오 확인

실무 흐름을 더 쉽게 쓰면 아래와 같다.

1.  local에서 `pnpm dev` 로 기능 개발
2.  필요하면 `pnpm build` 와 `pnpm start` 로 production 모드와 비슷하게 로컬 점검
3.  브랜치를 push 해서 preview URL 생성
4.  preview에서 로그인, 지도, 추천 흐름 확인
5.  문제 없으면 main 반영 후 production 배포 확인

### 8.3 권장 확인 순서

배포 후 기능 확인은 아래 순서를 권장한다.

1.  시작 화면 렌더링 확인
2.  회원가입 또는 로그인 확인
3.  메인 화면 진입 확인
4.  친구 추가와 친구 선택 확인
5.  채팅 저장과 조회 확인
6.  위치 공유 확인
7.  지도 렌더링 확인
8.  추천 결과 확인

---

## 9\. 배포 전 체크리스트

배포 전 아래 항목을 반드시 확인한다.

1.  package.json 기준 빌드 스크립트 확인
2.  환경 변수 6개 준비 여부 확인
3.  JWT\_SECRET 누락 여부 확인
4.  Kakao Map 키와 Kakao Local 키 구분 확인
5.  service role key 가 공개 변수로 들어가지 않았는지 확인
6.  보호 페이지와 보호 API 동작 확인
7.  Preview에서 핵심 시나리오 1회 이상 확인

## 10\. 배포 후 점검 항목

### 10.1 인증 점검

1.  회원가입 후 메인 화면 이동 여부
2.  로그인 후 보호 페이지 접근 여부
3.  로그아웃 후 보호 페이지 차단 여부
4.  새로고침 후 로그인 상태 유지 여부

### 10.2 데이터 및 API 점검

1.  친구 추가 API 동작 여부
2.  메시지 저장 및 조회 동작 여부
3.  위치 저장 API 동작 여부
4.  추천 API가 midpoint 와 places 를 반환하는지 여부

### 10.3 외부 연동 점검

1.  Kakao 지도 SDK 정상 로드 여부
2.  추천 장소 조회 동작 여부
3.  브라우저 콘솔과 서버 로그 오류 여부

## 11\. 자주 발생하는 문제

### 11.1 환경 변수 누락

증상은 아래와 같다.

1.  로그인은 되는데 API가 500으로 실패한다.
2.  Kakao 지도나 추천 기능이 동작하지 않는다.
3.  서버 로그에 환경 변수 undefined가 보인다.

확인 순서는 아래와 같다.

1.  Vercel 환경 변수 등록 여부 확인
2.  Preview 와 Production 모두 값이 있는지 확인
3.  NEXT\_PUBLIC\_ 와 서버 전용 변수 이름을 섞지 않았는지 확인

### 11.2 빌드 실패

주요 원인은 아래와 같다.

1.  Root Directory 오설정
2.  Install Command 또는 Build Command 오설정
3.  package manager 불일치
4.  타입 오류 또는 코드 오류

확인 순서는 아래와 같다.

1.  저장소 루트 기준인지 확인
2.  pnpm install, pnpm build 기준인지 확인
3.  로컬에서 먼저 빌드 가능한지 확인

### 11.3 지도는 보이는데 추천이 안 되는 경우

이 경우는 보통 아래 원인을 먼저 본다.

1.  KAKAO\_LOCAL\_REST\_API\_KEY 누락
2.  서버 측 API 호출 실패
3.  위치 데이터 누락

즉, 지도 SDK 문제와 장소 검색 API 문제를 분리해서 확인해야 한다.

## 12\. 팀 운영 기준 메모

1.  환경 변수 실제 값은 채팅이나 문서에 직접 남기지 않는다.
2.  로컬 확인 없이 바로 Production으로 반영하지 않는다.
3.  Preview 배포 확인 후 main 반영을 진행한다.
4.  배포 오류가 나면 코드 문제와 환경 변수 문제를 먼저 분리해서 본다.

## 13\. 최종 정리

MeetPoint MVP 1차 배포 기준은 아래 한 줄로 정리할 수 있다.

1.  Vercel에 Next.js 앱을 GitHub 연동 방식으로 배포한다.
2.  환경 변수 6개를 정확히 분리해서 넣는다.
3.  Preview에서 핵심 사용자 시나리오를 확인한 뒤 Production으로 반영한다.

즉, 본 문서는 단순 배포 설명 문서가 아니라 시연 가능한 배포 상태를 만들기 위한 실행 기준 문서이다.
