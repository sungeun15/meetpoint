# MeetPoint API 명세서

## 1\. 문서 목적

이 문서는 MeetPoint의 현재 서버 API 계약과 UI 연동 기준을 고정하기 위한 문서이다.

현재 UI 소스는 friends, chat, 저장 위치, 추천 결과를 로컬 상태와 브라우저 SDK 중심으로 우선 구현하고 있고, 서버 구현에는 Route Handler 와 DB 연동 기반이 들어가 있으므로, 본 문서는 양쪽을 연결할 때 적용할 요청, 응답, 오류 코드, 인증 규칙을 정리하는 것을 목표로 한다.

역할 분담과 완료 상태는 WBS 문서에서 관리하며, 본 문서는 API 계약과 연동 기준만 다룬다.

---

## 2\. 범위

현재 UI 소스는 아직 이 API를 직접 호출하지 않지만, 서버 Route Handler 구현은 존재한다. 본 문서는 현재 구현된 backend contract 와 이후 UI 연동 기준으로 한정한다.

API 범위는 다음과 같다.

1.  인증 API
2.  친구 API
3.  메시지 API
4.  위치 저장 API
5.  출발 위치 검색 API
6.  저장된 출발 위치 API
7.  추천 결과 조회 API

본 문서의 기본 범위에서 제외하는 항목은 다음과 같다.

1.  닉네임 찾기
2.  비밀번호 재설정
3.  추천 결과 이력 저장 API
4.  WebSocket 기반 실시간 채팅 API
5.  실시간 위치 추적 API

### 2.1 현재 구현 대응 관계

현재 UI 소스와 본 API 문서의 대응 관계는 다음과 같이 이해한다.

1.  인증 화면은 현재 입력 UI를 제공하고, signup/login/logout API 계약은 구현되어 있다.
2.  friends 허브의 친구 추가와 친구 목록은 현재 UI에서 로컬 상태로 동작하지만, friends API 계약은 구현되어 있다.
3.  chat 메시지 전송과 위치 공유는 현재 UI에서 로컬 상태와 피드백 문구로 동작하지만, messages/location API 계약은 구현되어 있다.
4.  나중에 만나기의 주소 검색과 핀 지정은 현재 브라우저 SDK로 동작하고, location/search 와 recommendations API 계약도 구현되어 있다.
5.  저장 위치 목록은 현재 UI에서 로컬 상태로 유지되지만, location/departures API 계약은 구현되어 있다.

## 3\. 공통 규칙

아래 규칙은 현재 backend 구현과 이후 UI 연동에 공통으로 적용하는 API 계약이다. 현재 UI 단계에서는 이 명세를 직접 호출하지 않고 로컬 상태와 브라우저 SDK 흐름으로 대응한다.

### 3.1 기본 규칙

1.  모든 API 응답은 JSON 형식으로 반환한다.
2.  보호 API는 요청 본문에 userId를 받지 않고, JWT 쿠키 검증 결과의 currentUserId를 기준으로 현재 사용자를 식별한다.
3.  클라이언트는 인증 토큰을 직접 저장하지 않고, 서버가 발급한 httpOnly 쿠키를 사용한다.
4.  Kakao Local API는 브라우저에서 직접 호출하지 않고 서버 Route Handler에서만 호출한다.

### 3.2 인증 및 쿠키 규칙

1.  쿠키 이름은 meetpoint\_auth로 고정한다.
2.  JWT payload는 userId, nickname, iat, exp 값을 포함한다.
3.  JWT는 JWT\_SECRET 환경 변수로 서명하고 검증한다.
4.  쿠키 속성은 httpOnly, sameSite=lax, path=/ 를 기본으로 한다.
5.  운영 환경에서는 secure=true 로 설정한다.
6.  쿠키 만료 시간은 7일로 설정한다.
7.  보호 API는 JWT 검증 실패 시 401 UNAUTHORIZED 를 반환한다.
8.  서명이 유효하지 않거나 만료된 쿠키는 즉시 삭제한다.

### 3.3 회원가입 후 인증 처리 기준

현재 인증 계약에서는 회원가입 성공 후에도 바로 /friends 흐름으로 진입할 수 있어야 하므로, 본 명세서에서는 회원가입 성공 시 로그인 성공과 동일하게 JWT 쿠키를 발급하는 흐름으로 고정한다.

즉, 아래 두 API는 모두 성공 시 meetpoint\_auth 쿠키를 설정한다.

1.  POST /api/auth/signup
2.  POST /api/auth/login

### 3.4 공통 응답 형식

성공 응답 형식:

```
{ "ok": true, "data": {} }
```

오류 응답 형식:

```
{
    "ok": false,
    "error": {
        "code": "ERROR_CODE",
        "message": "사용자 안내 문구"
    }
}
```

### 3.5 공통 검증 규칙

1.  nickname 은 trim 후 앞뒤 공백을 제거하고 내부 연속 공백은 한 칸으로 정규화한다.
2.  nickname 은 정규화 후 2자 이상 12자 이하 문자열만 허용한다.
3.  nickname 은 한글, 영문, 숫자, 공백만 허용하고 특수문자는 허용하지 않는다.
4.  nickname 비교와 중복 검사는 nickname\_normalized 기준으로 수행하며 영문은 소문자로 정규화한다.
5.  password 는 4자 이상 20자 이하 문자열만 허용한다.
6.  friendNickname 은 정규화 후 자기 자신의 nickname\_normalized 와 같을 수 없다.
7.  content 는 trim 후 1자 이상 500자 이하 문자열만 허용한다.
8.  lat 는 -90 이상 90 이하 범위만 허용한다.
9.  lng 는 -180 이상 180 이하 범위만 허용한다.
10.  friendId 는 UUID 형식 문자열만 허용한다.
11.  limit 는 생략 시 50을 사용하고 최대 100까지만 허용한다.
12.  after 는 ISO datetime 문자열만 허용한다.
13.  mode 는 now 또는 later 중 하나만 허용한다.
14.  category 는 cafe, meal, fun 중 하나만 허용한다.
15.  query 는 출발 위치 검색 시 2자 이상 문자열만 허용한다.
16.  departureLocationId 는 UUID 형식 문자열만 허용한다.
17.  locationKind 는 recent 또는 preset 중 하나만 허용한다.
18.  departure 와 friendDeparture 는 label, lat, lng, source 를 모두 포함해야 하며 source 는 search, pin, saved 중 하나만 허용한다.

## 4\. 공통 타입 계약

아래 타입은 현재 API 응답과 요청 계약의 기준이다. 현재 UI 구현에서 실제 사용 중인 타입은 app/components/friends/types.ts 와 app/components/chat/types.ts 를 우선 기준으로 삼고, 서버 연동 시 아래 형태로 수렴시킨다.

### 4.1 UserSummary

```
type UserSummary = {
    id: string;
    nickname: string;
    lat: number | null;
    lng: number | null;
    locationUpdatedAt: string | null;
};
```

### 4.2 FriendSummary

```
type FriendSummary = UserSummary & {
    relationId?: string;
};
```

### 4.3 MessageItem

```
type MessageItem = {
    id: string;
    senderId: string;
    receiverId: string;
    content: string;
    createdAt: string;
};
```

### 4.4 RecommendationMode

```
type RecommendationMode = "now" | "later";
```

### 4.5 RecommendationCategory

```
type RecommendationCategory = "cafe" | "meal" | "fun";
```

### 4.6 Coordinate

```
type Coordinate = {
    lat: number;
    lng: number;
};
```

### 4.7 DeparturePoint

```
type DeparturePoint = Coordinate & {
    label: string;
    source: "search" | "pin" | "saved";
};
```

### 4.8 DepartureSearchItem

```
type DepartureSearchItem = DeparturePoint;
```

### 4.9 SavedDepartureLocation

```
type SavedDepartureLocation = {
    id: string;
    label: string;
    lat: number;
    lng: number;
    locationKind: "recent" | "preset";
    lastUsedAt: string;
    createdAt: string;
    updatedAt: string;
};
```

### 4.10 RecommendationPlace

```
type RecommendationPlace = {
    name: string;
    category: string;
    lat: number;
    lng: number;
    distanceA: number;
    distanceB: number;
    averageDistance: number;
    distanceGap: number;
    categoryPenalty: number;
    vitalityPenalty: number;
    score: number;
};
```

### 4.11 RecommendationResult

```
type RecommendationResult = {
    midpoint: { lat: number; lng: number };
    summary: { mode: RecommendationMode; category: RecommendationCategory; radiusUsed: number };
    places: RecommendationPlace[];
};
```

### 4.12 공통 API 응답 타입

```
type ApiSuccess<T> = { ok: true; data: T };
type ApiError = { ok: false; error: { code: string; message: string } };
type ApiResponse<T> = ApiSuccess<T> | ApiError;
```

## 6\. 상세 API 명세

아래 명세는 현재 backend 구현 기준 Route Handler 계약이며, 현재 UI 소스는 아직 이 API를 직접 호출하지 않는다.

### 6.1 POST /api/auth/signup

목적:

*   닉네임 중복 검사 후 사용자를 생성한다.
*   비밀번호는 해시로 저장한다.
*   성공 시 JWT 쿠키를 발급해 즉시 로그인 상태를 만든다.

요청 본문:

```
{
    "nickname": "민수",
    "password": "pass1234"
}
```

처리 규칙:

1.  nickname 정규화를 먼저 수행한다.
2.  nickname\_normalized 기준 중복 사용자를 검사한다.
3.  password\_hash 를 생성해 users 테이블에 저장한다.
4.  생성 성공 후 JWT 쿠키를 발급한다.

성공 응답:

```
{
    "ok": true,
    "data": {
        "user": {
            "id": "uuid",
            "nickname": "민수",
            "lat": null,
            "lng": null,
            "locationUpdatedAt": null
        }
    }
}
```

주요 실패 조건:

| 상태 코드 | error.code         | 설명                                   |
| --------- | ------------------ | -------------------------------------- |
| 400       | INVALID\_INPUT     | 닉네임 또는 비밀번호 형식이 맞지 않음  |
| 409       | CONFLICT\_NICKNAME | 이미 사용 중인 닉네임                  |
| 500       | INTERNAL\_ERROR    | 사용자 생성 중 복구 불가능한 내부 오류 |

### 6.2 POST /api/auth/login

목적:

*   닉네임과 비밀번호를 검증한다.
*   성공 시 JWT 쿠키를 발급한다.

요청 본문:

```
{
    "nickname": "민수",
    "password": "pass1234"
}
```

처리 규칙:

1.  nickname 정규화 후 사용자 조회를 수행한다.
2.  password\_hash 와 입력 비밀번호를 비교한다.
3.  인증 성공 시 JWT 쿠키를 발급한다.

성공 응답:

```
{
    "ok": true,
    "data": {
        "user": {
            "id": "uuid",
            "nickname": "민수",
            "lat": 37.5665,
            "lng": 126.978,
            "locationUpdatedAt": "2026-05-04T10:30:00.000Z"
        }
    }
}
```

주요 실패 조건:

| 상태 코드 | error.code      | 설명                                     |
| --------- | --------------- | ---------------------------------------- |
| 400       | INVALID\_INPUT  | 닉네임 또는 비밀번호 형식이 맞지 않음    |
| 401       | UNAUTHORIZED    | 닉네임이 없거나 비밀번호가 일치하지 않음 |
| 500       | INTERNAL\_ERROR | 내부 인증 처리 오류                      |

### 6.3 POST /api/auth/logout

목적:

*   현재 인증 쿠키를 제거한다.

요청 본문:

*   없음

처리 규칙:

1.  meetpoint\_auth 쿠키를 만료 처리한다.
2.  이미 쿠키가 없더라도 동일한 성공 응답을 반환할 수 있다.
3.  만료되었거나 잘못된 JWT가 포함되어 있더라도 로그아웃 요청 자체는 200 성공으로 처리한다.

성공 응답:

```
{
    "ok": true,
    "data": {
        "cleared": true
    }
}
```

주요 실패 조건:

*   없음. 로그아웃은 idempotent 동작으로 처리하며 정상 응답을 우선한다.

### 6.4 GET /api/friends

목적:

*   현재 사용자 기준 친구 목록을 조회한다.

요청 값:

*   없음

처리 규칙:

1.  JWT 쿠키에서 currentUserId 를 식별한다.
2.  friends 와 users 를 조인해 친구 요약 목록을 반환한다.
3.  locationUpdatedAt, lat, lng 를 함께 반환해 지도와 추천 기능에서 재사용한다.

성공 응답:

```
{
    "ok": true,
    "data": {
        "friends": [
            {
                "id": "friend-uuid",
                "relationId": "relation-uuid",
                "nickname": "지은",
                "lat": 37.5701,
                "lng": 126.9823,
                "locationUpdatedAt": "2026-05-04T11:00:00.000Z"
            }
        ]
    }
}
```

주요 실패 조건:

| 상태 코드 | error.code      | 설명                         |
| --------- | --------------- | ---------------------------- |
| 401       | UNAUTHORIZED    | JWT 없음 또는 쿠키 검증 실패 |
| 500       | INTERNAL\_ERROR | 친구 목록 조회 중 내부 오류  |

### 6.5 POST /api/friends

목적:

*   친구 닉네임 기준으로 친구 관계를 생성한다.

요청 본문:

```
{
    "friendNickname": "지은"
}
```

처리 규칙:

1.  friendNickname 을 정규화한다.
2.  자기 자신을 친구로 추가하는 요청은 차단한다.
3.  users 테이블에서 대상 사용자를 조회한다.
4.  친구 추가 성공 시 user\_id -> friend\_id, friend\_id -> user\_id 양방향 row 2건을 하나의 트랜잭션으로 upsert 한다.
5.  이미 양방향 관계가 모두 존재하면 기존 관계를 그대로 사용한다.
6.  한쪽 관계만 남은 비정상 상태면 누락된 반대 row 를 함께 복구한다.

성공 응답:

```
{
    "ok": true,
    "data": {
        "relationId": "relation-uuid",
        "friend": {
            "id": "friend-uuid",
            "nickname": "지은",
            "lat": null,
            "lng": null,
            "locationUpdatedAt": null
        }
    }
}
```

주요 실패 조건:

| 상태 코드 | error.code         | 설명                                 |
| --------- | ------------------ | ------------------------------------ |
| 400       | INVALID\_INPUT     | 닉네임 형식 오류 또는 자기 자신 추가 |
| 401       | UNAUTHORIZED       | JWT 없음 또는 쿠키 검증 실패         |
| 404       | FRIEND\_NOT\_FOUND | 대상 닉네임 사용자를 찾지 못함       |
| 500       | INTERNAL\_ERROR    | 친구 관계 저장 중 내부 오류          |

### 6.6 GET /api/messages

목적:

*   현재 사용자와 선택 친구의 입력 기준 위치를 바탕으로 추천 장소를 반환한다.

    }

처리 규칙:

1.  JWT 검증 후 currentUserId 를 식별한다.
2.  friendId, mode, category 를 검증한다.
3.  currentUserId 와 friendId 간 친구 관계를 검증한다.

9.  score 기준으로 정렬 후 상위 10개 장소를 반환한다.
10.  추천 결과는 MVP 범위에서 DB에 저장하지 않고 즉시 응답만 반환한다.

성공 응답:

## 8\. 구현 메모

1.  현재 UI 소스에서는 users, friends, messages, departure\_locations 를 실제 DB 대신 로컬 상태와 fixture 데이터로 우선 표현한다.
2.  app/api/auth/login, logout, signup route.ts 구현은 존재하지만, UI 소스는 아직 이를 직접 호출하지 않는다.
3.  friends, messages, location, recommendations API 경로는 구현되어 있고, UI 연동이 남아 있다.
4.  users, friends, messages, departure\_locations 는 MVP 1차 필수 테이블이며 Supabase schema 와 테스트 스크립트까지 반영되어 있다.
5.  recommendations 는 ERD 상 확장 구조만 정의하고 실제 생성은 MVP 범위에서 제외한다.
6.  저장된 출발 위치 재사용은 departure\_locations 기준으로 처리한다.
7.  친구 관계는 양방향 2개 row 유지 규칙을 따른다.
8.  메시지 조회는 기본 5초 polling 기준을 사용한다.
9.  추천 결과는 요청 시 계산 후 반환하며 저장하지 않는다.
10. 보호 API는 모두 JWT 쿠키 검증을 통과해야 한다.
