# MeetPoint WBS 및 팀원별 작업 분담

## 1\. 문서 목적

이 문서는 MeetPoint MVP 1차 구현을 실제 작업 단위로 나누고, 각 팀원이 무엇을 어떤 순서로 진행해야 하는지 정리하기 위한 실행 기준 문서이다.

기획 문서, 기술 설계 문서, 화면 명세서가 무엇을 만들어야 하는지 설명하는 문서라면, 본 문서는 누가 어떤 브랜치에서 어떤 산출물을 만들어야 하는지까지 연결하는 문서로 사용한다.

---

## 2\. 문서 범위

본 문서는 아래 범위를 포함한다.

1.  MVP 1차 구현 기준 작업 분리
2.  팀원 A, B, C 역할과 책임 정리
3.  기능별 작업 순서와 선행 조건 정리
4.  브랜치 전략과 작업 연결 기준
5.  완료 기준과 통합 확인 기준

본 문서의 기본 범위에서 제외하는 항목은 아래와 같다.

1.  WebSocket 기반 실시간 채팅 확장 작업
2.  실시간 위치 추적 확장 작업
3.  추천 이력 저장 기능
4.  비밀번호 재설정 기능
5.  닉네임 찾기 기능

---

## 3\. 운영 원칙

### 3.1 기본 원칙

1.  MVP 1차 범위 안에서만 작업을 분리한다.
2.  각 작업은 주담당자 1명을 기준으로 한다.
3.  연동이 필요한 기능은 협업 담당자를 함께 표시한다.
4.  최종 통합 확인 기준은 팀원 A 작업 디렉토리 기준으로 본다.
5.  문서, API, 화면 기준이 충돌하면 PRD 문서와 API 명세를 우선 참고한다.

### 3.2 작업 완료 판단 원칙

아래 조건을 모두 만족하면 작업 완료로 본다.

1.  담당 기능이 지정된 화면 또는 API에서 직접 확인된다.
2.  선행 기능과 연결 시 흐름이 끊기지 않는다.
3.  테스트 체크리스트에서 관련 항목을 점검할 수 있다.
4.  다른 팀원이 의존하는 입력값과 출력값이 고정되어 있다.

## 5\. 브랜치 전략 기준

기본 브랜치 전략은 아래와 같이 사용한다.

```
main
feature/login
feature/friend-list
feature/chat
feature/location-map
feature/place-recommend
feature/ui-alert
docs/readme
```

실제 작업 연결 기준은 아래처럼 이해하면 된다.

| 브랜치 | 주요 담당 | 목적 |
| --- | --- | --- |
| main | 전체 | 최종 통합 기준 브랜치 |
| feature/login | 팀원 A, C | 회원가입/로그인 UI와 인증 API 연결 |
| feature/friend-list | 팀원 A, C | 친구 추가, 친구 목록, 친구 선택 흐름 |
| feature/chat | 팀원 A, C | 채팅 UI와 메시지 저장/조회 연결 |
| feature/location-map | 팀원 B, A, C | 지도 렌더링, 위치 공유, 위치 데이터 반영 |
| feature/place-recommend | 팀원 B, C, A | 중심점 계산, 추천 API, 추천 결과 UI |
| feature/ui-alert | 팀원 A | 빈 상태, 오류 상태, 로딩 상태 정리 |
| docs/readme | 팀원 C | README 및 제출용 문서 정리 |

문서 작업은 필요 시 `docs/*` 계열 브랜치를 추가로 사용할 수 있다.

팀원 A는 사용자가 직접 보는 화면을 만들고, 팀원 B와 C가 만든 기능을 최종 화면 흐름으로 묶는 역할을 담당한다.

### 7.2 상세 작업 목록

| 작업 ID | 작업명 | 연결 브랜치 | 선행 조건 | 주요 산출물 | 완료 기준 |
| --- | --- | --- | --- | --- | --- |

### 7.3 협업 주의 사항

1.  지도 배치는 팀원 B 로직을 존중하되 최종 UI 배치는 팀원 A가 정리한다.
2.  친구, 메시지, 인증 입력 형식은 팀원 C의 API 규약에 맞춘다.
3.  최종 통합 기준은 팀원 A 화면에서 확인한다.

### 9.2 상세 작업 목록

| 작업 ID | 작업명 | 연결 브랜치 | 선행 조건 | 주요 산출물 | 완료 기준 |

### 9.3 협업 주의 사항

1.  API 입력값과 응답값이 바뀌면 팀원 A와 B에 먼저 공유한다.
2.  인증과 데이터 구조는 UI보다 먼저 고정하는 것이 좋다.
3.  제출용 문서와 협업 기록은 기능 구현과 병행해서 최신 상태로 유지한다.

## 10\. 추천 작업 순서

실제 진행 순서는 아래 흐름을 권장한다.

1.  기준 문서 확정
2.  인증 API와 시작 화면 구현
3.  메인 레이아웃과 친구 목록 흐름 구현
4.  메시지 저장/조회와 채팅 UI 구현
5.  지도 렌더링과 위치 공유 구현
6.  중심점 계산과 추천 로직 구현
7.  추천 결과 UI와 상태 UI 정리
8.  통합 검증 및 문서 마감

이 순서를 지키면 화면만 먼저 만들고 데이터가 비거나, API만 먼저 만들고 화면이 없는 상태를 줄일 수 있다.
