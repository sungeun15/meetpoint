# MeetPoint WBS 및 팀원별 작업 분담

## 1\. 문서 목적

이 문서는 MeetPoint MVP 1차 구현을 실제 작업 단위로 나누고, 각 팀원이 무엇을 어떤 순서로 진행해야 하는지 정리하기 위한 실행 기준 문서이다.

기획 문서, 기술 설계 문서, 화면 명세서가 무엇을 만들어야 하는지 설명하는 문서라면, 본 문서는 누가 어떤 브랜치에서 어떤 산출물을 만들어야 하는지까지 연결하는 문서로 사용한다.

팀 역할, 담당 범위, 현재 상태, 완료 판단은 본 문서에서 관리하며, 기술 설계 문서는 시스템 구조와 구현 규칙만 다룬다.

---

## 2\. 문서 범위

본 문서는 아래 범위를 포함한다.

1.  MVP 1차 구현 기준 작업 분리
2.  팀원 A, B, C 역할과 책임 정리
3.  기능별 작업 순서와 선행 조건 정리
4.  브랜치 전략과 작업 연결 기준
5.  완료 기준과 통합 확인 기준

본 문서의 기본 범위에서 제외하는 항목은 아래와 같다.

1.  WebSocket 기반 실시간 채팅 확장 작업
2.  실시간 위치 추적 확장 작업
3.  추천 이력 저장 기능
4.  비밀번호 재설정 기능
5.  닉네임 찾기 기능

---

## 3\. 운영 원칙

### 3.1 기본 원칙

1.  MVP 1차 범위 안에서만 작업을 분리한다.
2.  각 작업은 주담당자 1명을 기준으로 한다.
3.  연동이 필요한 기능은 협업 담당자를 함께 표시한다.
4.  현재 01\_sungeun15 기준 구현물은 Team A UI-only 결과물로 본다.
5.  Team B, C 책임 범위는 문서상 후속 연동 항목으로 유지하되, Team A 소스에 선반영된 것으로 간주하지 않는다.
6.  최종 통합 확인 기준은 팀원 A 작업 디렉토리 기준으로 본다.
7.  문서, API, 화면 기준이 충돌하면 PRD 문서와 API 명세를 우선 참고한다.

### 3.2 작업 완료 판단 원칙

아래 조건을 모두 만족하면 작업 완료로 본다.

1.  Team A 작업은 지정된 화면과 상호작용에서 직접 확인된다.
2.  Team B, C 작업은 지정된 API, 데이터 구조, 외부 연동 규약에서 직접 확인된다.
3.  선행 기능과 연결 시 흐름이 끊기지 않는다.
4.  테스트 체크리스트에서 관련 항목을 점검할 수 있다.
5.  다른 팀원이 의존하는 입력값과 출력값이 고정되어 있다.
6.  역할 구분과 완료 상태 표시는 본 WBS 문서를 기준으로 관리한다.

## 5\. 브랜치 전략 기준

기본 브랜치 전략은 아래와 같이 사용한다.

```
main
feature/login
feature/friend-list
feature/chat
feature/location-map
feature/departure-location
feature/place-recommend
feature/ui-alert
docs/readme
```

실제 작업 연결 기준은 아래처럼 이해하면 된다.

| 브랜치                     | 주요 담당    | 목적                                     |
| -------------------------- | ------------ | ---------------------------------------- |
| main                       | 전체         | 최종 통합 기준 브랜치                    |
| feature/login              | 팀원 A, C    | 회원가입/로그인 UI와 인증 API 연결       |
| feature/friend-list        | 팀원 A, C    | 친구 추가, 친구 목록, 친구 선택 흐름     |
| feature/chat               | 팀원 A, C    | 채팅 UI와 메시지 저장/조회 연결          |
| feature/location-map       | 팀원 B, A, C | 지도 렌더링, 위치 공유, 위치 데이터 반영 |
| feature/departure-location | 팀원 C, A, B | 저장된 출발 위치 조회/저장/선택 흐름     |
| feature/place-recommend    | 팀원 B, C, A | 중심점 계산, 추천 API, 추천 결과 UI      |
| feature/ui-alert           | 팀원 A       | 빈 상태, 오류 상태, 로딩 상태 정리       |
| docs/readme                | 팀원 C       | README 및 제출용 문서 정리               |

문서 작업은 필요 시 `docs/*` 계열 브랜치를 추가로 사용할 수 있다.

메모:

1.  위 브랜치명은 작업 분리 예시이다.
2.  실제 Git 작업은 사용자 승인 후, 각 팀 디렉토리 안에서만 진행한다.

## 7\. 팀원 A 상세 작업

### 7.3 협업 주의 사항

1.  지도 배치는 팀원 B 로직을 존중하되 최종 UI 배치는 팀원 A가 정리한다.
2.  현재 Team A 소스는 로컬 상태와 더미데이터 기준이며, 팀원 C API 규약이 붙기 전까지 이를 서버 구현 완료로 표현하지 않는다.
3.  최종 통합 기준은 팀원 A 화면에서 확인한다.

## 10\. 추천 작업 순서

실제 진행 순서는 아래 흐름을 권장한다.

1.  기준 문서 확정
2.  Team A 랜딩, 인증, friends, chat UI 구조 구현
3.  Team A 추천 입력과 결과 UI 정리
4.  Team C 인증/API/DB 및 추천 계산 foundation 정리
5.  Team B 지도 기준 연동과 결과 표현 정교화
6.  Team A 기준 문서와 화면 정합성 검토
7.  Team B, C 연동 결과를 Team A 화면에 통합
8.  통합 검증 및 문서 마감

이 순서를 지키면 화면만 먼저 만들고 데이터가 비거나, API만 먼저 만들고 화면이 없는 상태를 줄일 수 있다.
