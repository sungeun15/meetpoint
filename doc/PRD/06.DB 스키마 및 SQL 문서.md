# MeetPoint DB 스키마 및 SQL 문서

## 1. 문서 목적

이 문서는 MeetPoint의 현재 PostgreSQL 및 Supabase 기준 DB 스키마와 대표 SQL 흐름을 고정하기 위한 문서이다.

현재 구현에는 인증, 친구, 메시지, 위치 저장, 추천 연동을 위한 Route Handler 와 repository 계층이 이미 포함되어 있으므로, 본 문서는 실제 구현된 테이블 구조와 제약, 인덱스, 대표 조회/저장 SQL 을 코드 기준으로 정리하는 것을 목표로 한다.

---

## 2. 범위

현재 구현 기준으로 본 문서의 기본 범위는 다음 4개 테이블이다.

1. users
2. friends
3. messages
4. departure_locations

다음 항목은 후속 확장 범위로만 유지한다.

1. recommendations 테이블 생성
2. 추천 결과 이력 저장
3. WebSocket 기반 실시간 메시지 구조
4. 비밀번호 재설정용 토큰 테이블

### 2.1 현재 구현 대응 관계

현재 코드와 본 문서의 대응 관계는 다음과 같다.

1. users 는 인증 계정, 위치 공유 상태, 위치 공유 범위를 저장한다.
2. friends 는 친구 요청과 수락 상태를 저장한다.
3. messages 는 댓글형 채팅 메시지와 읽음 시각을 저장한다.
4. departure_locations 는 내 출발 위치와 친구 출발 위치용 저장 좌표를 함께 저장한다.
5. recommendations 는 현재 요청 시 계산 후 반환하며 DB 에 저장하지 않는다.

---

## 3. DB 설계 원칙

1. DB 엔진은 Supabase PostgreSQL 기준으로 설계한다.
2. 보호 API 는 JWT httpOnly 쿠키를 통해 현재 사용자를 식별하고, 요청 본문에 userId 를 받지 않는다.
3. 닉네임 중복 검사와 조회는 nickname 이 아니라 nickname_normalized 기준으로 수행한다.
4. users.lat, users.lng 는 마지막 공유 위치를 저장하고, 저장된 출발 위치는 departure_locations 에 분리 저장한다.
5. users.location_share_scope 와 location_share_target_user_id 로 현재 위치 공유 범위를 함께 저장한다.
6. friends 는 즉시 친구 추가가 아니라 pending 또는 accepted 상태를 갖는 친구 요청 구조를 사용한다.
7. messages 는 read_at 컬럼으로 읽음 시각을 추적한다.
8. departure_locations 는 owner_party, friend_id, friend_nickname 으로 내 출발 위치용 저장과 친구 출발 위치용 저장을 함께 관리한다.
9. departure_locations.is_selected 는 같은 사용자/소유 그룹 안에서 현재 선택된 저장 위치를 나타낸다.
10. 추천 결과는 DB 에 저장하지 않고 API 요청마다 계산 후 반환한다.

## 6. 현재 구현 기준 필수 DDL

### 6.1 users 테이블

```sql
create table if not exists public.users (
    id uuid primary key default gen_random_uuid(),
    nickname varchar(12) not null,
    nickname_normalized varchar(12) not null,
    password_hash text not null,
    lat double precision null,
    lng double precision null,
    location_updated_at timestamptz null,
    location_share_scope varchar(20) null,
    location_share_target_user_id uuid null,
    created_at timestamptz not null default now(),
    constraint users_nickname_normalized_key unique (nickname_normalized),
    constraint users_location_share_scope_check check (location_share_scope in ('friend', 'all_friends')),
    constraint users_location_share_target_user_id_fkey foreign key (location_share_target_user_id)
        references public.users (id)
        on delete set null
);
```

설계 포인트:

1. nickname 은 화면 표시용 원본 값을 유지한다.
2. nickname_normalized 는 중복 검사, 검색, 로그인 조회에 사용한다.
3. lat, lng, location_updated_at 은 현재 마지막 공유 위치 기준이다.
4. location_share_scope 는 friend 또는 all_friends 중 하나만 허용한다.
5. friend 범위 공유 시 location_share_target_user_id 에 대상 친구 id 를 저장한다.

### 6.2 friends 테이블

```sql
create table if not exists public.friends (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null,
    friend_id uuid not null,
    status varchar(20) not null default 'accepted',
    created_at timestamptz not null default now(),
    constraint friends_user_id_fkey foreign key (user_id) references public.users (id) on delete cascade,
    constraint friends_friend_id_fkey foreign key (friend_id) references public.users (id) on delete cascade,
    constraint friends_user_friend_unique unique (user_id, friend_id),
    constraint friends_not_self check (user_id <> friend_id),
    constraint friends_status_check check (status in ('pending', 'accepted'))
);
```

설계 포인트:

1. 친구 요청은 pending 으로 생성되고 수락 시 accepted 로 변경된다.
2. 수락 완료 후에는 양방향 관계 row 를 유지한다.
3. unique(user_id, friend_id) 로 중복 관계 생성을 방지한다.
4. 자기 자신 친구 추가는 check 제약으로 차단한다.

### 6.3 messages 테이블

```sql
create table if not exists public.messages (
    id uuid primary key default gen_random_uuid(),
    sender_id uuid not null,
    receiver_id uuid not null,
    content varchar(500) not null,
    read_at timestamptz null,
    created_at timestamptz not null default now(),
    constraint messages_sender_id_fkey foreign key (sender_id) references public.users (id) on delete cascade,
    constraint messages_receiver_id_fkey foreign key (receiver_id) references public.users (id) on delete cascade,
    constraint messages_content_not_blank check (char_length(btrim(content)) >= 1)
);
```

설계 포인트:

1. 댓글형 채팅 MVP 기준으로 본문은 최대 500자 제한을 전제로 둔다.
2. read_at 은 수신자가 해당 메시지를 읽은 시각을 나타낸다.
3. 메시지 조회는 created_at asc, id asc 기준으로 정렬한다.

### 6.4 departure_locations 테이블

```sql
create table if not exists public.departure_locations (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null,
    label varchar(100) not null,
    address text null,
    lat double precision not null,
    lng double precision not null,
    owner_party varchar(20) not null default 'me',
    friend_id uuid null,
    friend_nickname varchar(100) null,
    location_kind varchar(20) not null default 'recent',
    is_selected boolean not null default false,
    last_used_at timestamptz not null default now(),
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    constraint departure_locations_user_id_fkey foreign key (user_id) references public.users (id) on delete cascade,
    constraint departure_locations_friend_id_fkey foreign key (friend_id) references public.users (id) on delete set null,
    constraint departure_locations_owner_party_check check (owner_party in ('me', 'friend')),
    constraint departure_locations_kind_check check (location_kind in ('recent', 'preset')),
    constraint departure_locations_friend_metadata_check check (
        (owner_party = 'me' and friend_id is null and friend_nickname is null)
        or (owner_party = 'friend' and friend_id is not null and char_length(btrim(friend_nickname)) >= 1)
    ),
    constraint departure_locations_label_not_blank check (char_length(btrim(label)) >= 1)
);
```

설계 포인트:

1. departure_locations 는 내 출발 위치와 친구 출발 위치를 하나의 구조 안에서 관리한다.
2. owner_party 는 me 또는 friend 만 허용한다.
3. owner_party 가 friend 인 경우 friend_id 와 friend_nickname 이 반드시 필요하다.
4. address 는 저장 시 확정된 주소 스냅샷이다.
5. is_selected 는 같은 사용자/소유 그룹 내 현재 선택 위치를 표시한다.
6. location_kind 는 recent 또는 preset 으로 구분한다.

## 7. 권장 인덱스

```sql
create index if not exists users_nickname_normalized_idx
    on public.users (nickname_normalized);

create index if not exists users_location_updated_at_idx
    on public.users (location_updated_at);

create index if not exists users_location_share_scope_idx
    on public.users (location_share_scope, location_share_target_user_id);

create index if not exists friends_user_id_idx
    on public.friends (user_id);

create index if not exists friends_friend_id_idx
    on public.friends (friend_id);

create index if not exists friends_user_status_idx
    on public.friends (user_id, status);

create index if not exists friends_friend_status_idx
    on public.friends (friend_id, status);

create index if not exists messages_sender_receiver_created_at_idx
    on public.messages (sender_id, receiver_id, created_at);

create index if not exists messages_receiver_sender_created_at_idx
    on public.messages (receiver_id, sender_id, created_at);

create index if not exists messages_receiver_sender_read_at_idx
    on public.messages (receiver_id, sender_id, read_at);

create index if not exists departure_locations_user_last_used_at_idx
    on public.departure_locations (user_id, last_used_at desc);

create index if not exists departure_locations_user_kind_idx
    on public.departure_locations (user_id, location_kind);

create index if not exists departure_locations_user_friend_idx
    on public.departure_locations (user_id, owner_party, friend_id, last_used_at desc);

create index if not exists departure_locations_user_selected_idx
    on public.departure_locations (user_id, owner_party, friend_id, is_selected);
```

설계 포인트:

1. users.nickname_normalized 인덱스는 로그인과 닉네임 검색을 빠르게 한다.
2. friends 상태 인덱스는 친구 목록과 받은 요청/보낸 요청 조회를 분리하는 데 사용한다.
3. messages 인덱스는 양방향 대화 조회와 읽음 시각 조회를 단순화한다.
4. departure_locations 인덱스는 사용자별 저장 위치 조회, 선택 위치 조회, 친구별 위치 그룹 조회에 사용한다.

## 9. API 연동 기준 대표 SQL

아래 SQL 은 현재 Route Handler 와 repository 계층을 연결할 때 사용하는 대표 흐름 기준이다.

### 9.1 회원가입용 사용자 중복 검사

```sql
select id, nickname, nickname_normalized
from public.users
where nickname_normalized = $1
limit 1;
```

### 9.2 회원가입용 사용자 생성

```sql
insert into public.users (
    nickname,
    nickname_normalized,
    password_hash
) values (
    $1,
    $2,
    $3
)
returning id, nickname, lat, lng, location_updated_at;
```

### 9.3 로그인용 사용자 조회

```sql
select id, nickname, nickname_normalized, password_hash, lat, lng, location_updated_at
from public.users
where nickname_normalized = $1
limit 1;
```

### 9.4 친구 검색 대상 사용자 조회

```sql
select id, nickname, lat, lng, location_updated_at
from public.users
where nickname_normalized = $1
limit 1;
```

### 9.5 친구 요청 생성

```sql
insert into public.friends (user_id, friend_id, status)
values ($1, $2, 'pending')
returning id, user_id, friend_id, status, created_at;
```

### 9.6 친구 목록 및 요청 조회

```sql
select
    f.id as relation_id,
    f.status,
    u.id,
    u.nickname,
    u.lat,
    u.lng,
    u.location_updated_at
from public.friends f
join public.users u on u.id = f.friend_id
where f.user_id = $1
order by f.created_at desc, u.nickname asc;
```

### 9.7 메시지 저장

```sql
insert into public.messages (
    sender_id,
    receiver_id,
    content
) values (
    $1,
    $2,
    $3
)
returning id, sender_id, receiver_id, content, read_at, created_at;
```

### 9.8 메시지 조회

```sql
select id, sender_id, receiver_id, content, read_at, created_at
from public.messages
where (
        sender_id = $1 and receiver_id = $2
    )
    or (
        sender_id = $2 and receiver_id = $1
    )
order by created_at asc, id asc
limit $3;
```

### 9.9 커서 기반 polling 메시지 조회

```sql
select id, sender_id, receiver_id, content, read_at, created_at
from public.messages
where (
        (sender_id = $1 and receiver_id = $2)
        or (sender_id = $2 and receiver_id = $1)
    )
    and (
        created_at > $3
        or (created_at = $3 and id > $4)
    )
order by created_at asc, id asc
limit $5;
```

### 9.10 위치 저장

```sql
update public.users
set
    lat = $2,
    lng = $3,
    location_updated_at = now(),
    location_share_scope = $4,
    location_share_target_user_id = $5
where id = $1
returning lat, lng, location_updated_at, location_share_scope, location_share_target_user_id;
```

### 9.11 저장된 출발 위치 목록 조회

```sql
select
    id,
    label,
    address,
    lat,
    lng,
    owner_party,
    friend_id,
    friend_nickname,
    location_kind,
    is_selected,
    last_used_at,
    created_at,
    updated_at
from public.departure_locations
where user_id = $1
order by
    case when location_kind = 'preset' then 0 else 1 end,
    last_used_at desc,
    created_at desc
limit $2;
```

### 9.13 저장된 출발 위치 수정 또는 최근 사용 시각 갱신

```sql
update public.departure_locations
set
    label = coalesce($3, label),
    address = coalesce($4, address),
    lat = coalesce($5, lat),
    lng = coalesce($6, lng),
    owner_party = coalesce($7, owner_party),
    friend_id = $8,
    friend_nickname = $9,
    last_used_at = coalesce($10, last_used_at),
    updated_at = now()
where id = $1
  and user_id = $2
returning id, label, address, lat, lng, owner_party, friend_id, friend_nickname, location_kind, is_selected, last_used_at, updated_at;
```

## 10. 후속 확장 메모

1. 추천 결과는 현재 계산형 응답 구조이므로 recommendations 테이블은 아직 만들지 않는다.

4. 위치 공유 범위와 대상 친구 id 는 users 테이블 단일 row 안에서 관리하되, 장기적으로는 이력 테이블 분리 가능성을 열어 둔다.
