# MeetPoint DB 스키마 및 SQL 문서

## 1\. 문서 목적

이 문서는 MeetPoint MVP 1차 구현에 필요한 PostgreSQL 및 Supabase 기준의 DB 스키마와 실제 SQL 초안을 고정하기 위한 문서이다.

ERD 문서에서 정의한 데이터 구조를 실제 생성 가능한 DDL과 조회, 저장, 검증용 SQL 수준으로 내리고, API 명세서와 기술 설계 문서가 같은 데이터 기준을 사용하도록 맞추는 것을 목표로 한다.

---

## 2\. 범위

본 문서의 기본 범위는 다음 3개 테이블의 실제 생성과 조회 기준이다.

1.  users
2.  friends
3.  messages

다음 항목은 후속 확장 범위로만 다룬다.

1.  recommendations 테이블 생성
2.  추천 결과 이력 저장
3.  WebSocket 기반 실시간 메시지 구조
4.  비밀번호 재설정용 토큰 테이블

---

## 3\. DB 설계 원칙

1.  DB 엔진은 Supabase PostgreSQL 기준으로 설계한다.
2.  브라우저는 Supabase에 직접 쓰기 요청을 보내지 않고, 모든 쓰기 작업은 Next.js Route Handler를 통해 수행한다.
3.  닉네임 비교와 중복 검사는 nickname이 아니라 nickname\_normalized 기준으로 처리한다.
4.  인증은 DB 세션이 아니라 JWT httpOnly 쿠키 기준으로 처리한다.
5.  MVP 1차에서는 users, friends, messages 3개 테이블만 실제 생성 대상으로 본다.
6.  추천 결과는 요청 시 계산 후 반환하며 DB에는 저장하지 않는다.

## 6\. MVP 필수 DDL

### 6.1 users 테이블

```
create table if not exists public.users (
    id uuid primary key default gen_random_uuid(),
    nickname varchar(12) not null,
    nickname_normalized varchar(12) not null,
    password_hash text not null,
    lat double precision null,
    lng double precision null,
    location_updated_at timestamptz null,
    created_at timestamptz not null default now(),
    constraint users_nickname_normalized_key unique (nickname_normalized)
);
```

설계 포인트:

1.  nickname은 화면 표시용 값을 유지한다.
2.  nickname\_normalized는 중복 비교, 검색, 자기 자신 비교에 사용한다.
3.  password\_hash는 평문 저장을 금지하고 해시 값만 저장한다.
4.  lat, lng, location\_updated\_at은 위치 미공유 사용자를 위해 null 허용이다.

### 6.2 friends 테이블

```
create table if not exists public.friends (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null,
    friend_id uuid not null,
    created_at timestamptz not null default now(),
    constraint friends_user_id_fkey foreign key (user_id) references public.users (id) on delete cascade,
    constraint friends_friend_id_fkey foreign key (friend_id) references public.users (id) on delete cascade,
    constraint friends_user_friend_unique unique (user_id, friend_id),
    constraint friends_not_self check (user_id <> friend_id)
);
```

설계 포인트:

1.  친구 관계는 논리적으로 양방향이므로 A -> B, B -> A 두 row를 함께 유지한다.
2.  unique(user\_id, friend\_id)로 중복 저장을 방지한다.
3.  check(user\_id \<> friend\_id)로 자기 자신 친구 추가를 차단한다.

### 6.3 messages 테이블

```
create table if not exists public.messages (
    id uuid primary key default gen_random_uuid(),
    sender_id uuid not null,
    receiver_id uuid not null,
    content varchar(500) not null,
    created_at timestamptz not null default now(),
    constraint messages_sender_id_fkey foreign key (sender_id) references public.users (id) on delete cascade,
    constraint messages_receiver_id_fkey foreign key (receiver_id) references public.users (id) on delete cascade,
    constraint messages_content_not_blank check (char_length(btrim(content)) >= 1)
);
```

설계 포인트:

1.  댓글형 채팅 MVP 기준으로 본문은 최대 500자 제한을 전제로 둔다.
2.  sender\_id 와 receiver\_id 는 모두 users.id 를 참조한다.
3.  메시지 조회는 created\_at asc, id asc 기준으로 반환한다.

## 7\. 권장 인덱스

```
create index if not exists users_nickname_normalized_idx
    on public.users (nickname_normalized);

create index if not exists users_location_updated_at_idx
    on public.users (location_updated_at);

create index if not exists friends_user_id_idx
    on public.friends (user_id);

create index if not exists friends_friend_id_idx
    on public.friends (friend_id);

create index if not exists messages_sender_receiver_created_at_idx
    on public.messages (sender_id, receiver_id, created_at);

create index if not exists messages_receiver_sender_created_at_idx
    on public.messages (receiver_id, sender_id, created_at);
```

설계 포인트:

1.  users.nickname\_normalized 인덱스는 닉네임 검색과 중복 검사를 빠르게 한다.
2.  friends 인덱스는 현재 사용자 친구 목록 조회와 역방향 관계 확인에 사용한다.
3.  messages 양방향 인덱스는 두 사용자 간 대화 조회를 단순화한다.

## 9\. API 연동 기준 SQL

### 9.1 회원가입용 사용자 중복 검사

```
select id, nickname, nickname_normalized
from public.users
where nickname_normalized = $1
limit 1;
```

설명:

1.  $1 에는 정규화된 nickname\_normalized 값이 들어간다.
2.  결과가 있으면 회원가입 시 CONFLICT\_NICKNAME 처리 대상이다.

### 9.2 회원가입용 사용자 생성

```
insert into public.users (
    nickname,
    nickname_normalized,
    password_hash
) values (
    $1,
    $2,
    $3
)
returning id, nickname, lat, lng, location_updated_at as "locationUpdatedAt";
```

### 9.3 로그인용 사용자 조회

```
select id, nickname, nickname_normalized, password_hash, lat, lng, location_updated_at
from public.users
where nickname_normalized = $1
limit 1;
```

설명:

1.  비밀번호 검증은 애플리케이션 레이어에서 password\_hash 비교로 수행한다.
2.  DB는 조회와 저장 기준만 담당한다.

### 9.4 친구 추가 대상 사용자 조회

```
select id, nickname, lat, lng, location_updated_at
from public.users
where nickname_normalized = $1
limit 1;
```

### 9.5 친구 관계 양방향 upsert

```
insert into public.friends (user_id, friend_id)
values
    ($1, $2),
    ($2, $1)
on conflict (user_id, friend_id) do nothing;
```

설명:

1.  $1 은 현재 사용자 ID, $2 는 친구 대상 사용자 ID이다.
2.  친구 추가는 트랜잭션 안에서 처리하는 것을 권장한다.

### 9.6 친구 목록 조회

```
select
    f.id as relation_id,
    u.id,
    u.nickname,
    u.lat,
    u.lng,
    u.location_updated_at
from public.friends f
join public.users u
    on u.id = f.friend_id
where f.user_id = $1
order by u.nickname asc;
```

### 9.7 메시지 저장

```
insert into public.messages (
    sender_id,
    receiver_id,
    content
) values (
    $1,
    $2,
    $3
)
returning id, sender_id, receiver_id, content, created_at;
```

### 9.8 메시지 조회

```
select id, sender_id, receiver_id, content, created_at
from public.messages
where (
        sender_id = $1 and receiver_id = $2
    )
    or (
        sender_id = $2 and receiver_id = $1
    )
order by created_at asc, id asc
limit $3;
```

### 9.9 polling 메시지 조회

```
select id, sender_id, receiver_id, content, created_at
from public.messages
where (
        (sender_id = $1 and receiver_id = $2)
        or (sender_id = $2 and receiver_id = $1)
    )
    and created_at > $3
order by created_at asc, id asc
limit $4;
```

### 9.10 위치 저장

```
update public.users
set
    lat = $2,
    lng = $3,
    location_updated_at = now()
where id = $1
returning lat, lng, location_updated_at;
```

### 9.11 추천 전 위치 조회

```
select id, nickname, lat, lng, location_updated_at
from public.users
where id in ($1, $2);
```

### 9.12 친구 관계 검증

```
select 1
from public.friends
where user_id = $1
  and friend_id = $2
limit 1;
```

## 10\. 트랜잭션 권장 구간

다음 작업은 한 트랜잭션 안에서 처리하는 것을 권장한다.

1.  회원가입 시 사용자 생성과 후속 조회
2.  친구 추가 시 양방향 friends row 생성
3.  친구 추가 시 비정상 단방향 관계 복구

예시:

```
begin;

insert into public.friends (user_id, friend_id)
values
    ($1, $2),
    ($2, $1)
on conflict (user_id, friend_id) do nothing;

commit;
```

## 11\. recommendations 확장 SQL 초안

아래 SQL은 MVP 1차에서 실행하지 않고, 후속 확장 시 참고용으로만 보관한다.

```
create table if not exists public.recommendations (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null,
    friend_id uuid not null,
    midpoint_lat double precision not null,
    midpoint_lng double precision not null,
    place_name varchar(200) not null,
    place_lat double precision not null,
    place_lng double precision not null,
    category varchar(100) not null,
    score double precision not null,
    created_at timestamptz not null default now(),
    constraint recommendations_user_id_fkey foreign key (user_id) references public.users (id) on delete cascade,
    constraint recommendations_friend_id_fkey foreign key (friend_id) references public.users (id) on delete cascade
);

create index if not exists recommendations_user_friend_created_at_idx
    on public.recommendations (user_id, friend_id, created_at desc);
```

주의 사항:

1.  현재 MVP에서는 recommendations 테이블을 생성하지 않는다.
2.  추천 이력 UI와 조회 API가 필요할 때만 도입한다.

### 11.1 recommendations 후속 도입 판단 기준

아래 요구사항이 실제 기능 범위에 포함될 때 recommendations 테이블 도입을 진행한다.

1.  추천 결과 이력 보기
2.  최근 추천 재사용
3.  추천 통계 또는 분석
4.  추천 결과 공유 또는 즐겨찾기
5.  디버깅용 추천 로그 보관

운영 원칙:

1.  현재 MVP 단계에서는 기능 범위를 줄이기 위해 recommendations 테이블을 생성하지 않는다.
2.  추천 결과는 요청 시 계산 후 즉시 반환하는 구조로 유지한다.
3.  실제로 저장이 필요한 기능이 확정되는 순간에만 recommendations 테이블과 관련 API, 조회 화면, 마이그레이션을 함께 추가한다.
4.  즉, 테이블을 미리 만들어 두는 방식보다 필요한 시점에 목적을 분명히 하고 추가하는 방식을 기본 원칙으로 한다.

## 12\. 검증 체크리스트

1.  users.nickname\_normalized unique 제약이 정상 동작하는지 확인한다.
2.  friends 에서 자기 자신 추가가 check 제약으로 차단되는지 확인한다.
3.  friends 의 양방향 upsert 가 중복 없이 동작하는지 확인한다.
4.  messages.content 공백-only 입력이 차단되는지 확인한다.
5.  users 위치 갱신 후 location\_updated\_at 이 함께 바뀌는지 확인한다.
6.  메시지 조회가 created\_at asc, id asc 기준으로 안정적으로 정렬되는지 확인한다.
7.  recommendations 테이블이 MVP 초기 SQL에 포함되지 않았는지 확인한다.
