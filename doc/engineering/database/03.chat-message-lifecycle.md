# Chat Message Lifecycle 가이드

## 1. 문서 목적

이 문서는 MeetPoint의 채팅 메시지가 생성되고, 조회되고, 읽음 상태로 바뀌고, 친구 목록과 채팅 화면에 반영되기까지의 전체 흐름을 한 번에 설명하기 위한 기준 문서이다.

특히 이번 문서는 아래 항목을 함께 다룬다.

1. 메시지 저장 구조
2. 메시지 조회와 커서 페이징 규칙
3. 읽음 처리와 unread 집계 규칙
4. 친구 목록 마지막 메시지 미리보기 규칙
5. 채팅 화면의 읽음 표시 규칙

이 문서는 단순 UI 설명서가 아니라 DB, 서버, API 응답, 클라이언트 상태, 표시 규칙을 함께 묶은 기술 문서이다.

---

## 2. 현재 구현 범위와 전제

현재 MeetPoint 채팅은 아래 전제를 기준으로 동작한다.

1. 브라우저는 DB에 직접 접근하지 않는다.
2. 모든 메시지 읽기/쓰기는 Next.js Route Handler를 경유한다.
3. 서버의 DB 접근은 Supabase service role 기반이다.
4. 실시간 소켓이 아니라 polling 기반으로 새 메시지와 읽음 상태를 반영한다.
5. 읽음 상태는 `messages.read_at` 컬럼으로 관리한다.

즉, 현재 구조는 카카오톡처럼 보이는 UX를 polling 기반 서버 동기화로 흉내 내는 구조라고 이해하면 된다.

## 4. DB 기준

### 4.1 messages 테이블 핵심 컬럼

현재 메시지 저장에서 중요한 컬럼은 아래와 같다.

1. `id`: 메시지 고유 식별자
2. `sender_id`: 발신자 사용자 id
3. `receiver_id`: 수신자 사용자 id
4. `content`: 메시지 본문
5. `read_at`: 수신자가 읽은 시각
6. `created_at`: 메시지 생성 시각

읽음 여부는 별도 boolean 이 아니라 `read_at is null` 인지 여부로 판단한다.

### 4.2 관련 인덱스

메시지 조회와 읽음 처리 성능을 위해 아래 인덱스를 둔다.

1. `messages_sender_receiver_created_at_idx`
2. `messages_receiver_sender_created_at_idx`
3. `messages_receiver_sender_read_at_idx`

앞의 두 인덱스는 대화 조회와 커서 비교에 쓰이고, 마지막 인덱스는 특정 사용자 입장에서 안 읽은 메시지를 찾거나 읽음 처리할 때 사용된다.

## 5. 메시지 생성 흐름

### 5.1 클라이언트 요청

채팅 입력창에서 사용자가 메시지를 보내면 클라이언트는 `POST /api/messages`를 호출한다.

요청 본문에는 아래 값이 들어간다.

1. `friendId`
2. `content`

### 5.2 서버 검증

서버는 아래 순서로 처리한다.

1. `friendId` 형식 검증
2. `content` 공백/길이 검증
3. 현재 사용자와 대상 사용자의 친구 관계 검증
4. 검증 통과 시 메시지 저장

### 5.3 DB 저장 규칙

메시지를 저장할 때는 아래 규칙을 따른다.

1. `sender_id`는 현재 로그인 사용자 id로 고정한다.
2. `receiver_id`는 선택한 친구 id로 저장한다.
3. 새로 저장되는 메시지의 `read_at`는 기본적으로 `null`이다.
4. 저장 직후 생성된 행을 다시 읽어 API 응답으로 내려준다.

즉, 보낸 직후 메시지는 항상 아직 읽히지 않은 상태로 시작한다.

---

## 6. 메시지 조회 흐름

### 6.1 GET /api/messages 역할

`GET /api/messages`는 아래 역할을 동시에 수행한다.

1. 현재 사용자와 특정 친구 간 메시지 목록 조회
2. 수신 메시지 읽음 처리
3. 발신 메시지 쪽 읽음 커서 계산
4. polling 간격 반환

### 6.2 커서 파라미터

현재 메시지 조회는 아래 커서를 지원한다.

1. `after`, `afterId`: 최신 이후 새 메시지 polling
2. `before`, `beforeId`: 이전 메시지 더 불러오기
3. `limit`: 한 번에 가져올 메시지 수

`after`와 `afterId`, `before`와 `beforeId`는 각각 한 쌍으로만 유효하다.

한쪽만 오면 무시하고, `after`와 `before`가 동시에 유효하면 잘못된 요청으로 처리한다.

### 6.3 정렬 규칙

클라이언트 계약상 메시지 목록은 항상 오래된 메시지부터 오름차순으로 반환한다.

이를 위해 서버는 최신 기준으로 조회하더라도 최종 응답 전에 순서를 다시 맞춘다.

### 6.4 읽음 처리 시점

사용자가 특정 친구의 채팅방 메시지를 조회하면 서버는 조회 직전에 아래 update 를 수행한다.

1. `receiver_id = currentUserId`
2. `sender_id = friendId`
3. `read_at is null`

이 조건에 맞는 메시지의 `read_at`를 현재 시각으로 채운다.

즉, 채팅방 조회 자체가 읽음 처리 트리거이다.

---

## 7. 발신자 기준 읽음 상태 계산

읽음 처리만 하고 끝내면 수신자는 읽었지만 발신자 화면은 그 사실을 모를 수 있다.

현재 구조에서는 이 문제를 `lastReadOwnMessage`로 해결한다.

### 7.1 lastReadOwnMessage 의미

서버는 현재 사용자 기준으로 아래 조건을 만족하는 메시지 중 가장 최근 1건을 찾는다.

1. `sender_id = currentUserId`
2. `receiver_id = friendId`
3. `read_at is not null`

이 결과를 `lastReadOwnMessage`로 내려준다.

### 7.2 왜 한 건만 내려주는가

클라이언트는 메시지 배열 전체를 다시 받지 않아도 된다.

마지막 읽은 메시지의 `(createdAt, id)` 커서와 `readAt`만 알면, 그 이전의 내 메시지들은 모두 읽힌 것으로 간주해 상태를 보정할 수 있기 때문이다.

이 방식은 polling 환경에서 응답 크기를 줄이면서도 발신자 쪽 읽음 표시를 유지하는 데 유리하다.

---

## 8. 친구 목록 집계 흐름

친구 목록은 단순 친구 정보만 보여 주지 않고, 채팅 관련 요약도 함께 내려준다.

### 8.1 unreadCount

친구 목록 unread 집계는 현재 사용자 기준으로 아래 메시지를 센다.

1. `receiver_id = currentUserId`
2. `sender_id = friendId`
3. `read_at is null`

즉, 상대가 보냈고 내가 아직 읽지 않은 메시지 개수만 badge 로 표시한다.

### 8.2 lastMessagePreview

친구 목록 마지막 메시지 미리보기는 현재 사용자 기준으로 아래 메시지 중 최신 1건을 사용한다.

1. `sender_id = friendId`
2. `receiver_id = currentUserId`

중요한 점은 아래와 같다.

1. 내가 보낸 마지막 메시지는 친구 목록 미리보기에 쓰지 않는다.
2. 상대가 보낸 메시지가 하나도 없으면 미리보기 줄을 렌더링하지 않는다.
3. 본문은 공백을 정리한 뒤 일정 길이 이상이면 줄여서 사용한다.

이 규칙은 사용자가 요청한 “상대편 메시지가 없으면 아무것도 적지 말고, 있으면 마지막 메시지 일부분만 보여 주기” 기준을 따른다.

---

## 9. 클라이언트 상태 흐름

### 9.1 메시지 응답 타입

클라이언트는 메시지 목록 응답에서 아래 값을 받는다.

1. `messages`
2. `lastMessageCreatedAt`
3. `lastReadOwnMessage`
4. `pollingIntervalSec`

각 메시지에는 `readAt`가 포함된다.

### 9.2 applyReadCursor 역할

클라이언트는 `use-chat-screen-state.ts`에서 `applyReadCursor`를 사용해 `lastReadOwnMessage`를 로컬 메시지 상태에 반영한다.

규칙은 아래와 같다.

1. 내 메시지 중에서
2. 커서상 `lastReadOwnMessage`보다 이전이거나 같은 메시지는
3. `readAt`가 비어 있으면 `lastReadOwnMessage.readAt`으로 채운다.

이 덕분에 이전 polling에서 이미 내려온 메시지도 다시 전부 재조회하지 않고 읽음 상태를 보정할 수 있다.

### 9.3 초기 로드와 polling

현재 클라이언트는 아래 두 흐름으로 메시지를 갱신한다.

1. 채팅방 진입 시 초기 로드
2. 최신 메시지 기준 `after + afterId` polling

채팅방 진입이나 polling 성공 후에는 현재 친구의 `unreadCount`를 로컬 상태에서 0으로 맞춘다.

즉, 서버와 클라이언트 둘 다 읽음 상태를 같은 방향으로 수렴시키도록 설계되어 있다.

## 10. 채팅 화면 표시 규칙

### 10.1 시간 표시

메시지 시간은 같은 발신자, 같은 분 단위로 이어지는 연속 메시지에서 마지막 메시지에만 표시한다.

단, 읽음 경계가 생기는 메시지는 unread 숫자와 시간 메타가 같이 보여야 하므로 시간도 함께 노출할 수 있다.

### 10.2 읽음 숫자 표시

내가 보낸 메시지 중 아직 읽히지 않은 구간은 마지막 메시지에만 `1`을 표시한다.

규칙은 아래와 같다.

1. 내 메시지여야 한다.
2. `readAt`가 없어야 한다.
3. 다음 메시지가 없거나, 다음 메시지가 상대 메시지이거나, 다음 내 메시지는 이미 읽혀 있어야 한다.

즉, 안 읽은 메시지 여러 개에 모두 숫자를 찍는 것이 아니라 unread 경계의 마지막 메시지에만 숫자 `1`을 찍는다.

### 10.3 메타 배치

현재 내 메시지의 메타는 말풍선 왼쪽에 세로로 쌓는다.

1. 위: unread 숫자 `1`
2. 아래: 시간

이 배치는 카카오톡처럼 메시지 본문과 메타를 분리해 읽기 쉽게 만들기 위한 것이다.

## 11. 친구 목록 표시 규칙

친구 목록 카드에서는 아래 순서로 정보를 보여 준다.

1. 닉네임
2. unread badge
3. 위치 공유 상태 문구
4. 상대가 보낸 마지막 메시지 미리보기

추가 규칙은 아래와 같다.

1. 현재 선택된 친구 카드에서는 unread badge 를 숨긴다.
2. unread 개수가 100 이상이면 `99+`로 표시한다.
3. 마지막 메시지 미리보기는 한 줄만 보여 준다.
4. 상대 메시지가 없으면 미리보기 줄 자체를 렌더링하지 않는다.

## 12. 대표 시나리오

### 12.1 내가 메시지를 보낸 직후

1. 클라이언트가 `POST /api/messages` 호출
2. 서버가 `read_at = null` 상태로 저장
3. 내 화면에는 새 메시지가 즉시 추가됨
4. 상대가 아직 읽지 않았으므로 내 메시지 unread 숫자 `1` 후보가 생김

### 12.2 상대가 채팅방을 열었을 때

1. 상대 화면에서 `GET /api/messages` 호출
2. 서버가 나에게서 온 미읽음 메시지를 `read_at = now()`로 갱신
3. 서버가 상대 기준 `lastReadOwnMessage` 반환
4. 상대 클라이언트는 unread badge 를 0으로 내림
5. 내 화면은 다음 polling 에서 읽음 커서를 받아 unread 숫자 표시를 정리함

### 12.3 친구 목록에서 unread badge 가 올라가는 경우

1. 상대가 나에게 메시지를 보냄
2. 나는 아직 해당 채팅방을 열지 않음
3. 친구 목록 `unreadCount` 집계가 증가함
4. 해당 친구 카드에 badge 가 표시됨

### 12.4 친구 목록 마지막 메시지 미리보기

1. 상대가 나에게 메시지를 보냄
2. 친구 목록 집계 시 가장 최근 상대 메시지 1건을 찾음
3. 본문을 짧게 줄여 카드 하단에 표시함
4. 상대 메시지가 한 번도 없으면 이 줄은 표시하지 않음

## 13. 현재 한계와 주의점

현재 구조에서 알아둘 점은 아래와 같다.

1. 읽음 처리 트리거는 채팅방 조회이므로, 채팅방을 열지 않으면 unread 는 유지된다.
2. 실시간 소켓이 아니므로 읽음 상태 반영은 polling 주기에 따라 약간 늦을 수 있다.
3. 친구 목록 마지막 메시지 미리보기는 현재 상대가 보낸 마지막 메시지만 보여 준다.
4. unread 숫자는 카카오톡의 정밀한 사용자별 읽지 않은 사람 수가 아니라 현재 MVP 기준 `1` 표시 방식이다.
5. polling 응답 크기를 줄이기 위해 발신자 전체 읽음 상태를 매번 다시 받지 않고 마지막 읽음 커서만 내려준다.

즉, 현재 구현은 MVP 기준으로 충분히 자연스럽지만, 완전한 메신저 실시간 모델과는 다르다.

## 16. 한 줄 정리

현재 MeetPoint 채팅 메시지 생명주기는 아래처럼 요약할 수 있다.

1. 보낼 때는 `read_at = null`로 저장한다.
2. 읽을 때는 채팅 조회 시 상대가 보낸 미읽음 메시지의 `read_at`를 채운다.
3. 발신자 화면은 `lastReadOwnMessage` 커서로 읽음 범위를 복원한다.
4. 친구 목록은 `unreadCount`와 상대의 마지막 메시지 미리보기로 대화 상태를 요약한다.
