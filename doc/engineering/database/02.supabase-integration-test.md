# Supabase 연동 테스트

## 1. 문서 목적

이 문서는 MeetPoint에서 만든 Supabase 연동 테스트 스크립트와 헬스체크 경로를 쉽게 설명하기 위한 문서이다.

아래 명령이 각각 무엇을 확인하는지, 어떤 순서로 실행하면 되는지만 간단히 정리한다.

1.  `pnpm run test:supabase`
2.  `pnpm run test:supabase:schema`
3.  `pnpm run test:supabase:table`
4.  `pnpm run test:supabase:cleanup`

---

## 2. 테스트 스크립트 위치

현재 스크립트는 아래 경로에 있다.

1.  `03_husbbbf/scripts/test-supabase/connection.mjs`
2.  `03_husbbbf/scripts/test-supabase/schema.mjs`
3.  `03_husbbbf/scripts/test-supabase/table.mjs`
4.  `03_husbbbf/scripts/test-supabase/cleanup.mjs`

운영 헬스체크용 Route Handler는 아래 경로에 있다.

1.  `03_husbbbf/app/api/health/supabase/route.ts`

---

## 3. 테스트 전에 필요한 환경 변수

테스트를 실행하려면 `.env`에 아래 값이 있어야 한다.

```env
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
SUPABASE_SERVICE_ROLE_KEY=
SUPABASE_DATABASE_URL=
```

아주 짧게 설명하면 아래와 같다.

1.  `NEXT_PUBLIC_SUPABASE_URL`: 어떤 Supabase 프로젝트에 연결할지 알려 주는 주소
2.  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: 공개 API 확인에 쓰는 키
3.  `SUPABASE_SERVICE_ROLE_KEY`: 서버 전용 관리자 키
4.  `SUPABASE_DATABASE_URL`: PostgreSQL에 직접 붙는 연결 문자열

---

## 4. 실행 명령

프로젝트 루트 `03_husbbbf`에서 아래 순서로 실행한다.

```bash
pnpm run test:supabase
pnpm run test:supabase:schema
pnpm run test:supabase:table
pnpm run test:supabase:cleanup
```

---

## 5. 각 명령이 확인하는 내용

### 5.1 `pnpm run test:supabase`

이 명령은 Supabase 연결 자체가 정상인지 확인한다.

확인하는 내용은 아래와 같다.

1.  `NEXT_PUBLIC_SUPABASE_URL`이 실제 Supabase 엔드포인트로 연결되는지
2.  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`가 공개 엔드포인트에서 정상 응답을 받는지
3.  `SUPABASE_SERVICE_ROLE_KEY`가 관리자 권한이 필요한 REST 경로에서 정상 동작하는지

즉, URL과 키 3개가 맞는지 먼저 확인하는 테스트이다.

### 5.2 `pnpm run test:supabase:schema`

이 명령은 운영 Supabase DB에 MVP 스키마를 반영하고 핵심 테이블과 인덱스를 확인한다.

확인 순서는 아래와 같다.

1.  `supabase/meetpoint-mvp-schema.sql` 실행
2.  `users`, `friends`, `messages`, `departure_locations` 테이블 확인
3.  관련 인덱스 존재 여부 확인

즉, 설계한 스키마가 실제 DB에 반영되는지 확인하는 테스트이다.

### 5.3 `pnpm run test:supabase:table`

이 명령은 DB에 실제로 붙어서 테스트 테이블을 만들고, 데이터를 넣고, 다시 읽을 수 있는지 확인한다.

확인 순서는 아래와 같다.

1.  `public._meetpoint_script_test` 테이블 생성
2.  테스트 데이터 1건 insert
3.  row count 조회
4.  테이블이 실제로 존재하는지 다시 확인

즉, DB 연결 문자열과 SQL 실행이 정상인지 확인하는 테스트이다.

### 5.4 `pnpm run test:supabase:cleanup`

이 명령은 `test:supabase:table`이 만든 테스트 테이블을 삭제한다.

확인 순서는 아래와 같다.

1.  `public._meetpoint_script_test` 삭제
2.  삭제 후 테이블이 없어졌는지 다시 확인

즉, 테스트 후 DB를 다시 정리하는 명령이다.

## 7. 주의할 점

1.  `SUPABASE_SERVICE_ROLE_KEY`는 서버 전용 값이므로 브라우저로 보내면 안 된다.
2.  `test:supabase:schema`는 실제 운영 DB 스키마를 반영하므로 실행 대상을 반드시 확인해야 한다.
3.  `test:supabase:table`는 실제로 테스트 테이블을 만든다.
4.  테스트가 끝나면 `test:supabase:cleanup`까지 실행하는 것이 안전하다.
5.  `SUPABASE_DATABASE_URL`은 현재 환경에서는 direct URL보다 session pooler URL이 더 안정적으로 동작할 수 있다.

### 7.1 30분 주기 헬스체크

현재 프로젝트에는 `app/api/health/supabase/route.ts` 와 `vercel.json` 이 추가되어 있다.

1.  `/api/health/supabase` 는 users, friends, messages, departure_locations 접근 가능 여부를 확인한다.
2.  `vercel.json` 은 이 경로를 30분마다 호출하도록 `*/30 * * * *` 크론을 설정한다.
3.  `CRON_SECRET` 환경 변수를 설정하면 허가된 Vercel cron 요청만 통과시킬 수 있다.

## 8. 자주 막히는 경우

### 8.1 `pnpm lint` 또는 `pnpm exec eslint`가 안 되는 경우

로컬 의존성이 없으면 ESLint가 동작하지 않을 수 있다.

이때는 아래 명령으로 먼저 패키지를 설치한다.

```bash
pnpm install
```

### 8.2 `psql` 연결이 안 되는 경우

직접 DB 호스트 `db.<project-ref>.supabase.co`가 현재 네트워크 환경에서 바로 붙지 않을 수 있다.

이 경우에는 session pooler 방식의 `SUPABASE_DATABASE_URL`을 먼저 확인한다.

## 9. 한 줄 정리

1.  `test:supabase`: URL과 키 확인
2.  `test:supabase:schema`: 운영 스키마 반영 확인
3.  `test:supabase:table`: DB 생성 및 조회 확인
4.  `test:supabase:cleanup`: 테스트 테이블 정리
