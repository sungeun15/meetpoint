# MeetPoint 브랜치 전략 및 작업 흐름

## 1\. 문서 목적

이 문서는 MeetPoint 프로젝트에서 브랜치 전략과 실제 작업 흐름을 한 번에 이해할 수 있도록 정리한 문서이다.

Git 및 GitHub 사용법 문서가 명령 기준 설명이라면, 본 문서는 어떤 작업을 어떤 브랜치에서 시작하고 어떤 순서로 main 반영까지 가져가는지 설명하는 운영 문서이다.

즉, 01.Git 및 GitHub 사용법 문서가 실행 방법 중심 문서라면, 이 문서는 브랜치 선택 기준과 반영 순서를 정하는 운영 기준 문서로 본다.

---

## 2\. 기본 브랜치 전략

현재 프로젝트는 아래 전략을 기본으로 사용한다.

```
main
feature/login
feature/friend-list
feature/chat
feature/location-map
feature/place-recommend
feature/ui-alert
docs/readme
```

필요하면 docs/\* 브랜치를 추가로 만들 수 있다.

예시:

```
docs/planning-document
docs/structure-design
docs/technical-design
docs/screen-specification
```

단, docs/\* 브랜치는 문서만 독립적으로 정리하는 경우에 사용한다. 기능 구현과 그 기능 설명 문서가 함께 움직이는 경우에는 feature/\* 브랜치 하나에서 커밋을 나눠 관리할 수 있다.

---

## 3\. 브랜치별 의미

| 브랜치 종류 | 의미                  |
| ----------- | --------------------- |
| main        | 최종 통합 기준 브랜치 |
| feature/\*  | 기능 구현 브랜치      |
| docs/\*     | 문서 작업 브랜치      |

핵심 원칙은 아래와 같다.

1.  main 은 바로 작업하는 브랜치가 아니라 최종 반영 기준이다.
2.  기능 개발은 feature/\* 에서 한다.
3.  문서 작업은 docs/\* 에서 한다.
4.  한 브랜치에는 하나의 작업 목적만 담는다.
5.  이미 merge 된 브랜치는 다시 사용하지 않는다.

---

## 4\. 작업 성격별 브랜치 선택

브랜치는 사람 이름이나 임시 역할 이름보다 기능 이름을 우선 기준으로 잡는다.

### 4.1 화면 및 상호작용 중심 작업

1.  feature/login
2.  feature/friend-list
3.  feature/chat
4.  feature/ui-alert

### 4.2 지도 및 추천 중심 작업

1.  feature/location-map
2.  feature/place-recommend

### 4.3 데이터 연결 및 문서 작업

1.  기능과 직접 연결되는 데이터/API 작업은 해당 기능 브랜치 안에서 함께 처리한다.
2.  문서 작업은 docs/\* 브랜치에서 분리한다.

즉, 실제 운영에서는 담당자 기준보다 기능 기준 브랜치를 우선하고, 필요할 때만 세부 브랜치를 추가한다.

---

## 5\. 작업 시작 전 순서

작업 전에는 아래 순서를 권장한다.

1.  현재 담당 기능 확인
2.  작업 디렉토리의 Git 계정 확인
3.  main 으로 이동
4.  최신 origin/main 반영
5.  작업 목적에 맞는 새 브랜치 생성

실제 명령 예시와 점검 명령은 01.Git 및 GitHub 사용법 문서를 참고한다.

즉, 현재 feature 또는 docs 브랜치에서 단순히 git pull 을 하는 것만으로는 새 작업 시작 기준을 충족했다고 보지 않는다.

---

## 6\. 기능 작업 흐름

예를 들어 채팅 기능을 작업한다면 아래 흐름으로 보면 된다.

1.  feature/chat 브랜치 생성
2.  채팅 UI 또는 메시지 API 구현
3.  관련 테스트 또는 동작 확인
4.  feat: 타입 커밋 생성
5.  feature/chat 브랜치로 push
6.  GitHub에서 main 반영 준비

기능 설명 문서가 함께 따라오는 경우에는 같은 feature 브랜치에서 커밋만 분리할 수 있다.

예시:

1.  feat: 기능 구현 커밋
2.  docs: 기능 설명 문서 동기화 커밋

---

## 7\. 문서 작업 흐름

예를 들어 화면 명세서 문서를 정리한다면 아래 흐름으로 본다.

1.  docs/screen-specification 브랜치 생성
2.  문서 수정
3.  문서 오류 확인
4.  docs: 타입 커밋 생성
5.  docs/screen-specification 브랜치로 push

즉, docs/\* 브랜치는 문서 자체가 독립 작업일 때 가장 적합하다.

---

## 8\. 작업 중 최신화 기준

작업 중에는 매번 main 을 최신화할 필요는 없다.

하지만 아래 경우에는 중간 최신화를 권장한다.

1.  작업 기간이 길어졌을 때
2.  여러 명이 같은 파일을 동시에 수정할 가능성이 높을 때
3.  인증, API, 환경설정, 공용 레이아웃처럼 영향 범위가 큰 코드를 수정할 때
4.  Pull Request 생성 직전

즉, 실무 기준은 작업 중 main 최신화 신경 X 가 아니라, 필요할 때만 최신화를 수행한다에 가깝다.

---

## 9\. main 반영 흐름

main 은 직접 수정하기보다 아래 흐름으로 반영한다.

1.  작업 브랜치에서 기능 또는 문서 완성
2.  필요하면 최신 main 을 반영해 충돌 여부 확인
3.  작업 브랜치에 push
4.  GitHub에서 compare 화면 확인
5.  Pull Request 생성
6.  검토 또는 자체 확인
7.  main 으로 merge

즉, push 와 main 반영은 다른 단계이다.

---

## 10\. 중간 최신화와 머지 직전 최신화의 차이

중간 최신화는 오래된 브랜치가 main 과 너무 멀어지지 않게 관리하기 위한 작업이다.

머지 직전 최신화는 실제로 main 에 합치기 전에 최종 충돌 여부를 확인하는 작업이다.

둘은 목적이 다르므로 아래처럼 이해하면 된다.

1.  작업이 짧고 영향 범위가 작으면 머지 직전 최신화만으로 충분할 수 있다.
2.  작업이 길거나 공용 파일을 많이 수정하면 중간 최신화가 필요하다.
3.  어떤 경우든 main 반영 직전에는 최신 main 기준 확인이 필요하다.

---

## 11\. 브랜치 재사용 금지 원칙

이미 merge 된 feature 또는 docs 브랜치는 종료된 브랜치로 본다.

따라서 같은 주제의 후속 작업이라도 새 브랜치를 다시 만든다.

예시:

1.  docs/kakao-map-integration-guide 를 merge 했으면 다음 Kakao 작업은 새 브랜치로 만든다.
2.  feature/login 을 merge 했으면 로그인 수정은 feature/login-fix 또는 fix/login-bug 처럼 새 브랜치로 만든다.

이 원칙을 지키면 PR diff, 코드 리뷰, 작업 경계를 모두 분명하게 유지할 수 있다.

---

## 12\. 반영 확인 원칙

1.  main 브랜치 화면만 보고 반영 여부를 판단하지 않는다.
2.  실제 작업한 브랜치가 원격에 반영됐는지 먼저 확인한다.
3.  작업 브랜치 반영과 main 반영은 다른 단계로 이해한다.

세부 확인 명령과 GitHub 확인 방법은 01.Git 및 GitHub 사용법 문서를 참고한다.

---

## 13\. 실수 방지 체크리스트

1.  main 에서 바로 작업하고 있지 않은가
2.  브랜치 이름이 작업 목적을 설명하는가
3.  기능 작업인데 docs 브랜치에서 하고 있지 않은가
4.  문서 작업인데 feature 브랜치에서 하고 있지 않은가
5.  새 작업을 최신 main 기준에서 시작했는가
6.  merge 된 브랜치를 다시 사용하고 있지 않은가
7.  push 후 브랜치 기준으로 반영 여부를 확인했는가

---

## 14\. 최종 정리

MeetPoint 의 작업 흐름은 아래 한 줄로 정리할 수 있다.

1.  새 작업은 최신 main 기준에서 시작한다.
2.  작업 목적에 맞는 새 브랜치를 만든다.
3.  작업 중 최신화는 필요할 때만 수행한다.
4.  merge 직전에는 최신 main 기준을 반드시 다시 확인한다.
5.  GitHub에서는 branch 기준으로 먼저 확인한다.
6.  merge 된 브랜치는 다시 사용하지 않는다.
