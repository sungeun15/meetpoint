# MeetPoint Git 및 GitHub 사용법

## 1\. 문서 목적

이 문서는 MeetPoint 프로젝트에서 Git과 GitHub를 사용할 때 필요한 기본 작업 흐름을 정리한 문서이다.

특히 현재 프로젝트 기준으로 어떤 브랜치를 만들고, 어떤 커밋 메시지를 쓰고, 어디에 push 하며, push가 되었는지 어떻게 확인하는지까지 한 번에 이해할 수 있도록 정리한다.

브랜치 전략 자체와 운영 원칙은 02.브랜치 전략 및 작업 흐름 문서를 기준으로 보고, 이 문서는 실제 명령과 확인 방법을 바로 참고하는 실행용 가이드로 사용한다.

---

## 2\. 기본 원칙

1.  main 브랜치에 직접 작업하지 않는다.
2.  기능 작업은 feature/\* 브랜치에서 진행한다.
3.  문서 작업은 docs/\* 브랜치에서 진행한다.
4.  새 작업은 최신 main 기준에서 시작한다.
5.  push 후에는 GitHub 알림이 아니라 브랜치와 커밋으로 직접 확인한다.
6.  이미 merge 된 브랜치는 다시 재사용하지 않는다.

---

## 3\. 작업 전 확인

현재 작업 디렉토리에서 아래 순서로 확인한다.

```
git config user.name
git checkout main
git pull origin main
git branch --show-current
git status --short --branch
```

각 명령의 목적은 아래와 같다.

1.  git config user.name: 현재 작업 디렉토리의 Git 계정 확인
2.  git checkout main: 최신 기준 브랜치로 이동
3.  git pull origin main: 원격 main 최신 변경 반영
4.  git branch --show-current: 현재 브랜치 확인
5.  git status --short --branch: 변경 파일과 원격 추적 상태 확인

즉, 새 작업을 시작할 때는 현재 작업 브랜치에서 바로 pull 하는 것이 아니라, 먼저 main 을 최신 상태로 만든 뒤 새 브랜치를 만드는 흐름을 기본으로 사용한다.

---

## 4\. 새 작업 시작 방법

새 작업은 아래 순서를 기본으로 사용한다.

```
git config user.name
git checkout main
git pull origin main
git checkout -b feature/chat
```

문서 전용 작업이라면 아래처럼 만든다.

```
git config user.name
git checkout main
git pull origin main
git checkout -b docs/screen-specification
```

작업 브랜치를 오래 끌었다면, 새 작업을 시작할 때는 기존 feature 또는 docs 브랜치를 재사용하지 말고 최신 main 기준으로 새 브랜치를 다시 만든다.

---

## 5\. 브랜치 생성 기준

### 5.1 기본 브랜치 전략

현재 MeetPoint 프로젝트는 아래 브랜치 전략을 기본으로 사용한다.

```
main
feature/login
feature/friend-list
feature/chat
feature/location-map
feature/place-recommend
feature/ui-alert
docs/readme
```

### 5.2 브랜치 이름 짓는 방법

브랜치 이름은 작업 목적이 바로 드러나게 만든다.

예시:

```
feature/login
feature/friend-list
feature/chat
feature/location-map
feature/place-recommend
feature/ui-alert
docs/planning-document
docs/screen-specification
docs/readme
```

### 5.3 브랜치 생성 명령

예를 들어 채팅 기능 브랜치를 만든다면 아래처럼 사용한다.

```
git checkout -b feature/chat
```

문서 브랜치를 만든다면 아래처럼 사용한다.

```
git checkout -b docs/screen-specification
```

---

## 6\. 작업 중 확인과 최신화 기준

작업 중에는 매번 main 을 다시 pull 할 필요는 없다.

대신 아래 상황에서는 최신 main 기준을 다시 반영하는 것이 좋다.

1.  작업 기간이 길어졌을 때
2.  여러 명이 같은 파일이나 같은 기능을 함께 건드릴 때
3.  인증, API, 환경설정, 공용 컴포넌트처럼 충돌 가능성이 높은 코드를 수정할 때
4.  Pull Request 생성 직전

예시는 아래와 같다.

```
git checkout main
git pull origin main
git checkout feature/chat
git merge main
```

팀에서 rebase 를 쓰지 않는다면 위처럼 merge 방식으로 최신 main 을 반영하는 것이 가장 이해하기 쉽다.

---

## 7\. 커밋 메시지 작성 방법

### 7.1 기본 형식

커밋 메시지는 아래 형식을 기본으로 사용한다.

```
feat: 작업 설명
fix: 작업 설명
docs: 작업 설명
refactor: 작업 설명
test: 작업 설명
chore: 작업 설명
```

### 7.2 브랜치별 권장 타입

| 브랜치 종류 | 기본 타입 |
| ----------- | --------- |
| feature/\*  | feat:     |
| docs/\*     | docs:     |
| 버그 수정   | fix:      |
| 구조 개선   | refactor: |
| 테스트 작업 | test:     |
| 설정 변경   | chore:    |

### 7.3 커밋 메시지 예시

```
feat: add nickname login page
feat: implement friend add feature
feat: add chat message UI
feat: implement location sharing button
docs: add PRD test checklist
docs: add PRD deployment guide
docs: add PRD WBS document
fix: resolve map marker rendering bug
```

같은 기능 브랜치 안에서 코드와 문서를 함께 다뤄야 할 때는 브랜치는 하나로 두고 커밋을 분리할 수 있다.

예시:

```
feat: add kakao validation scripts
docs: sync kakao guide and test script usage
```

### 7.4 커밋 전 확인

커밋 전에 아래 명령으로 변경 범위를 확인하는 것이 좋다.

```
git status --short --branch
git diff --staged
```

필요한 파일만 올리고 싶으면 아래처럼 한다.

```
git add "파일명"
git commit -m "커밋메시지"
```

---

## 8\. push 방법

### 8.1 기본 push 명령

현재 브랜치에 커밋을 만든 뒤에는 같은 브랜치 이름으로 push 한다.

예시:

```
git push origin feature/chat
git push origin feature/location-map
git push origin docs/screen-specification
```

### 8.2 전체 작업 흐름 예시

```
git config user.name
git checkout main
git pull origin main
git checkout -b docs/screen-specification
git add .
git commit -m "docs: add screen specification"
git push origin docs/screen-specification
```

즉, 브랜치를 만들었으면 그 브랜치 이름으로 push 하는 것이 기본이다.

---

## 9\. push 확인 방법

GitHub 알림만 보고 push 여부를 판단하지 않는 것이 좋다.

### 9.1 터미널에서 확인

```
git status --short --branch
git log --oneline --decorate -5
git ls-remote --heads origin
```

확인 포인트는 아래와 같다.

1.  현재 브랜치가 맞는지
2.  최신 커밋 메시지가 방금 만든 것인지
3.  원격 브랜치가 실제 존재하는지

### 9.2 GitHub에서 확인

1.  main 브랜치 화면만 보지 않는다.
2.  방금 push 한 브랜치로 브랜치를 바꿔서 본다.
3.  최신 커밋과 파일 변경이 방금 작업한 것인지 확인한다.

예를 들어 docs/screen-specification 브랜치에 push 했다면, main 화면에 바로 안 보이는 것이 정상이다.

---

## 10\. 왜 main 에 바로 안 보이는가

보통은 아래 흐름으로 작업하기 때문이다.

1.  작업 브랜치 생성
2.  작업 브랜치에서 구현
3.  작업 브랜치에 commit
4.  작업 브랜치에 push
5.  GitHub에서 main 으로 merge 요청
6.  merge 후 main 반영

즉, main 에 바로 안 보여도 브랜치에 push 되어 있으면 정상이다.

---

## 11\. Pull Request 전 확인

Pull Request 를 만들기 전에는 아래 항목을 다시 확인한다.

1.  현재 브랜치가 맞는지
2.  최신 main 기준을 반영했는지
3.  충돌이 없는지
4.  테스트 또는 문서 검토를 끝냈는지
5.  PR 제목이 작업 목적을 설명하는지

즉, push 를 했다고 바로 main 반영 준비가 끝난 것은 아니다.

---

## 12\. Pull Request 개념

GitHub에서 Pull Request는 작업 브랜치를 main 에 합쳐 달라고 요청하는 절차이다.

보통 아래 순서로 진행한다.

1.  브랜치에 push
2.  GitHub compare 화면 확인
3.  Pull Request 생성
4.  리뷰 또는 자체 확인
5.  main 으로 merge

즉, push 와 main 반영은 같은 개념이 아니다.

---

## 13\. 브랜치 재사용 금지 원칙

이미 merge 된 브랜치는 다시 사용하지 않는 것이 원칙이다.

예를 들어 docs/kakao-map-integration-guide 가 이미 merge 되었다면, 다음 Kakao 작업은 아래처럼 새 브랜치를 만들어 진행한다.

```
git checkout main
git pull origin main
git checkout -b feature/kakao-test-docs
```

이유는 아래와 같다.

1.  과거 작업과 이번 작업의 경계가 분명해진다.
2.  PR diff 가 깔끔해진다.
3.  리뷰 범위를 이해하기 쉬워진다.

---

## 14\. 실수 방지 체크리스트

1.  현재 브랜치가 맞는지 확인했는가
2.  새 작업 시작 전에 main 을 최신화했는가
3.  브랜치 목적과 커밋 메시지 타입이 맞는가
4.  merge 된 브랜치를 다시 재사용하고 있지 않은가
5.  main 이 아니라 작업 브랜치에 push 했는가
6.  GitHub에서 브랜치를 바꿔서 실제 반영 여부를 확인했는가

---

## 15\. 최종 정리

MeetPoint에서 Git과 GitHub를 쓸 때 가장 중요한 원칙은 아래와 같다.

1.  main 에 직접 작업하지 않는다.
2.  새 작업은 최신 main 기준에서 시작한다.
3.  작업 목적에 맞는 새 브랜치를 만든다.
4.  브랜치 목적에 맞는 커밋 메시지를 쓴다.
5.  같은 브랜치로 push 한다.
6.  main 이 아니라 브랜치 기준으로 push 결과를 확인한다.
